Two things to say up front so nobody has to ask. The state bucket and the lock table predate this repository — they were not created by it and are not managed by it. And OpenTofu, not Terraform: the code is written to required_version >= 1.6 and the commands in the README are tofu.

If the room is mixed, tell them slide 4 through 6 are the core. The rest is context and honest accounting.

One account, three brands

Separation without an Organization

Oxagen, Stella and the Context Graph Protocol bill to one account. Separate accounts isolate harder and cost a payer account, cross-account roles and per-account bootstrapping. The separation here is carried by three mechanisms that cost nothing.

1. A Brand tag

Applied through each stack's provider default_tags, so a newly added resource cannot miss it.

2. A Resource Group

One per brand, querying that tag. It turns the tag into a browsable collection in the console and a target for Systems Manager.

3. A state key

One per brand. Applying one brand's stack can neither read nor write another's resources.

The fourth mechanism is not in the code. Brand has to be activated as a cost allocation tag in the Billing console before Cost Explorer will group by it. That API is not exposed to Terraform. Until make activate-cost-tags runs, per-brand spend is invisible even though every tag is correct.

Estate02 / 13

Speaker notes

The point to land is that these are three different separations doing three different jobs, and people routinely collapse them. The tag is for the bill. The Resource Group is for a human looking for something. The state key is for blast radius. Only the last one is a safety control, and it is the one an Organization would also give you.

Expect the question "why not AWS Organizations". The honest answer is that it is the better long-term shape and it was declined on cost and setup weight, not on merit. If someone pushes, agree with them — the mitigation is that everything here is per-brand state already, so lifting a brand into its own account later is a migration, not a rewrite.

The cost-allocation gap is the one to flag to whoever owns the bill. It fails silently: the console shows correct tags and Cost Explorer shows nothing, and it reads like a bug in the tagging rather than an unactivated setting.

The data node

Three engines, one box

One instance — i-023d002d6e44f8f84, a t4g.medium on arm64 in us-east-1a — runs all three databases as Docker containers, sized explicitly so none of them can starve the other two.

PostgreSQL

pgvector/pgvector:pg16

user oxagen · db oxagen · port 5432

mem_limit 768m. The extension ships in the image; the bootstrap still runs CREATE EXTENSION IF NOT EXISTS vector, retried until Postgres is accepting connections.

Neo4j

neo4j:5-community

user neo4j · bolt 7687 · browser 7474

mem_limit 1536m, heap and page cache pinned at 512m each. Community 5.11+ for native vector indexes, so an embedding is a property queried by the same language as the graph around it.

ClickHouse

clickhouse/clickhouse-server:24.8

user oxagen · db oxagen · HTTP 8123 · native 9000

mem_limit 1280m. Left uncapped it sizes its caches from total host RAM and takes the memory the other two need.

Every default in these images assumes it owns the machine. On a shared box that assumption is the outage, so each limit is set rather than inherited — and a 2 GB swapfile turns a transient spike from an OOM kill into a slowdown.

Data plane04 / 13

Speaker notes

The memory limits are the part to dwell on if the audience is operational. The Linux OOM killer resolves a spike by killing the largest process, which on this box is always a database. The swapfile exists to convert that crash into a slowdown — and the code says outright that it is not a substitute for memory: if this instance is regularly swapping, it is too small.

t4g.small is offered as a variable and halves the cost. It boots. It also OOM-kills ClickHouse under any real query load, and the module's own words are that a database that dies is not cheaper than one that runs. Do not let anyone take that trade without also dropping an engine.

arm64 is not incidental. An artifact built on an x86 runner installs green, tests green, and then fails to load a native module on the first request. Build jobs that target this node run on ubuntu-24.04-arm.

The trade, stated in the code

A single instance in a single AZ with no automatic failover. It trades availability for an order of magnitude in cost.

That is the correct trade for a pre-customer platform and the wrong one the day real traffic depends on it — at which point Postgres moves to Aurora, and this module's job is to have kept the schema portable until then.

The same arithmetic decides the network. A private subnet would need a NAT gateway at roughly $32/month, more than the instance it serves. A public IPv4 address costs about $3.60. Nothing can connect inbound either way — which is the next slide.

The exit condition is the part worth being explicit about, because it is the promise that makes the trade defensible: keep the schema portable. If someone asks what "portable" means concretely, the honest answer is that it is a discipline in the application repositories, not something this infrastructure enforces. That is a real gap.

The access model

No open ports. None.

The security group has no inbound rules at all, and there is no SSH key. Every database port is additionally bound to 127.0.0.1 on the instance. Access is by SSM — a session, or a port-forward through one.

Two independent controls, not one. The empty ingress block is the security control, not an oversight — and because the ports are also bound to loopback, a future rule opening one by mistake still does not expose a database. tofu -chdir=stacks/oxagen-data output connection_help prints the exact commands.

Access06 / 13

Speaker notes

The direction of the arrow is the whole idea, and it is what people miss when they hear "SSM". The instance opens the channel outbound through the agent; nothing dials in. That is why there is no bastion, no VPN, no SSH key to rotate and no port to leave open on a Friday. It also removes the entire class of "exposed database" incident rather than mitigating it, and it costs nothing.

Amazon Linux 2023 is chosen for exactly this: the SSM agent is preinstalled, so the no-inbound design needs no bootstrap of its own. If the AMI ever changes to something without the agent, the box becomes unreachable and the only way back is to replace it.

Authorization is IAM, so access is CloudTrail-auditable per principal, and revoking someone is removing a policy rather than rotating a shared key. Worth saying if anyone asks how you take access away from a departing engineer.

The honest caveat: this makes the SSM control plane and the instance role the thing that matters. If you can assume a role with ssm:StartSession on that instance, you are on the box. Slide 9 is why CI does not have it.

Secrets

Generated, stored, never output

Terraform generates each engine's password and writes it to SSM Parameter Store as a SecureString:

/oxagen-data/postgres/password
/oxagen-data/neo4j/password
/oxagen-data/clickhouse/password

Parameter Store rather than Secrets Manager because standard parameters are free where Secrets Manager bills $0.40 per secret per month. Application secrets live under /oxagen/production/, a different subtree from the database passwords — so a service compromised through its own configuration does not enumerate the database credentials.

The module does not output the values

It outputs the paths. Reading a value is an explicit aws ssm get-parameter --with-decryption, which is auditable in CloudTrail.

A Terraform output writes the secret into the state file in plaintext, for anyone who can read the bucket.

The same reasoning runs through the bootstrap. Passwords are read from Parameter Store at boot rather than baked into user data, which anything on the box can read out of the metadata service. The instance's IAM policy is scoped to its own parameter prefix, and its kms:Decrypt grant is conditioned on kms:ViaService = ssm — so it cannot decrypt anything it could not already read as a parameter.

tools/migrate-secrets.py --plan sorts a .env file into four buckets and writes nothing until --apply — and even then writes only the first. migratesupersededrotateconfig

Secrets07 / 13

Speaker notes

If you take one thing from this slide it is the asymmetry: an output is convenient once and readable forever by everyone with access to the state bucket, while get-parameter --with-decryption is slightly less convenient every time and leaves a record of who read it. Convenience was the wrong side to optimise.

The four buckets in the migration tool are worth naming individually, because ROTATE is the one people argue with. It never writes, deliberately — copying a known-exposed credential into a system of record makes it look clean without making it secret. SUPERSEDED is the quieter hazard: carrying across a credential for infrastructure this migration replaced installs a second, wrong answer that works often enough to be confusing.

If asked about rotation: nothing here rotates automatically. Changing a password is a Terraform-side change plus a container restart, and that is unbuilt as a routine. Say so rather than implying it is handled.

Durability

The instance is disposable; the volume is not

A separate volume

50 GB gp3, encrypted, prevent_destroy, in the same AZ as the instance that mounts it. The AMI can be replaced, the instance type changed, the box rebuilt — the databases are not in that blast radius.

The bootstrap is keyed on user_data, so editing it replaces the instance. That is only safe because the data is elsewhere.

Detachment stops the instance first, because forcibly detaching a mounted filesystem is how a volume comes back needing repair.

Daily snapshots, off the machine

Data Lifecycle Manager at 07:00 UTC, 7 kept, targeted by tag so a restored volume of the same name is picked up without editing the policy.

DLM rather than a cron job on the instance: a backup that runs on the machine it is backing up stops running at exactly the moment it is needed.

The refuse-to-start guard

The volume attaches asynchronously and races the bootstrap on a cold boot, and NVMe renames /dev/sdf. So the script waits — up to five minutes, finding the device by listing candidates rather than trusting a name — and if it never appears:

FATAL: data volume never appeared;
refusing to start databases on the root disk

An empty database that starts is worse than one that does not, because the application will happily write into it.

Re-runnable rather than assumed-once. The volume is formatted only when blkid finds no filesystem; Compose converges containers rather than recreating them; fstab carries nofail so a missing volume degrades to an unbooted database rather than an instance wedged in emergency mode with no agent to log in through.

Durability08 / 13

Speaker notes

Name what this does not give you before someone else does: there is no point-in-time recovery. A snapshot is a crash-consistent image, so a restore loses up to a day and the engines replay their write-ahead logs on start. That is precisely the property a managed database would sell you, at the price floor on slide 5.

The nofail choice is a nice one to explain if there is an operator in the room. Without it a missing volume drops the instance into emergency mode — and on a box whose only door is the SSM agent, that means no door. Failing into "databases down, box reachable" is strictly better than "everything down, box unreachable".

One number to remember from elsewhere in the module: provisioned IOPS above the gp3 baseline bill separately, and this account was already spending around $91 a month on volumes attached to stopped instances. Check before raising either the IOPS or the throughput here.

CI and deploys

Four repositories deploy. None holds an AWS key.

Each assumes a role over GitHub's OIDC provider. A key is a bearer credential that lives until someone rotates it, and it carries no context — a policy written against one cannot tell the deploy job from anything else holding it. A token carries the repository, the ref and the environment as claims.

RepositoryPublishes
macanderson/stellastella.oxagen.sh (node)
macanderson/cgp-websitecontextgraphprotocol.org
macanderson/context-graph-protocolthat site's /schema and /spec
macanderson/oxagenoxagen.sh; docs, app, api, mcp on the node

The subject is exact, and it names an environment

StringEquals, not the StringLike most examples use. A wildcard subject accepts a token from a pull request opened by anyone, on a fork, running their own workflow file. These repositories are public.

And environment:production, not ref:refs/heads/main. A branch subject would let any workflow on main assume the role; entry to an environment is a repository setting, revocable without a code change.

No CI role has a shell on the node. Each may write one S3 object per service it owns and send one document, oxagen-deploy-service, whose single argument is constrained at the API by allowedPattern ^[a-z][a-z0-9-]{0,30}$ — which cannot express a shell metacharacter. AWS-RunShellScript here is root, and this box holds every database.

Speaker notes

The detail that earns its place in a review: each role trusts two subject spellings, the documented repo:owner/name:environment:production and the immutable-id form where owner and repository each carry their numeric database id. That is not defensive guessing. The first real deploy failed with "Not authorized to perform sts:AssumeRoleWithWebIdentity", and CloudTrail's principalId for the denied call carried the id form verbatim. Both are literal strings — listing two is still exact matching, not a wildcard.

Same record settled a second thing: the environment name in the claim is lowercase production, even though these repositories carry a capitalised Production environment left over from Vercel.

The IAM thumbprint field is legacy. IAM stopped verifying it against GitHub's leaf certificate in 2023 and validates against its own CA bundle, but the API still requires the field — so both published intermediates are listed, because that is the failure this field can still cause.

Worth pausing on the deny in the CGP policy: the website syncs with --delete, so the protocol repository's prefixes are protected in IAM rather than by --exclude flags in a workflow. Those flags are one edit from being dropped and the failure is silent — a green deploy and every schema URL 404ing.

Sites and DNS

Three ways to answer a request

static-site

Private S3 origin, CloudFront, ACM certificate, Route 53 records. Every cost knob at its cheapest useful value: PriceClass_100, no access logging, no WAF, no bucket versioning.

oxagen.sh · contextgraphprotocol.org

nextjs-site

An OpenNext build: Lambda on arm64 behind a Function URL, assets in S3, CloudFront deciding which answers. Used where routes genuinely execute rather than rewriting the product to fit the hosting.

stella.oxagen.sh · docs.oxagen.sh

redirect-site

A CloudFront Function on viewer-request, returning a 301 with no origin at all. The distribution's origin deliberately does not exist.

oxagen.ai → oxagen.sh

oxagen.ai is retired as a website and still carries live mail. Apex and www answer every route with a 301 to the oxagen.sh homepage, path discarded — the domains never shared a URL structure, so a path-preserving redirect would 404 most old links. The zone also holds inbound mail routing, outbound DKIM for five senders, SPF and DMARC, six names served from a Google Cloud load balancer this migration never touched, and six domain-ownership proofs.

Some hostnames skip CloudFront entirely. app, api and mcp are plain A records at the node, with Caddy routing by hostname and taking its own certificates from Let's Encrypt. They hold sessions and read all three databases over loopback, which is the only way to reach them. A VPC-attached Lambda in front would need a NAT gateway costing more than everything else in the account combined.

Sites10 / 13

Speaker notes

The failure mode across that oxagen.ai zone is quiet, which is why the README spends so long on it. A zone missing an MX record does not error, it bounces mail. A missing DKIM key bounces nothing and starts landing mail in spam folders days later, with nothing pointing back at the change that caused it. The import tool drops every A record on the reasoning that an A record is the old website — true for oxagen.sh, false here, which is why those six names are declared explicitly.

Stella's site is on Lambda in the module because three of its routes genuinely execute — the install counter, the install-script proxy and the docs search index. It is served from the node today; see the next slide.

If asked why the redirect is 301 rather than 302: 301 consolidates the retired domain's search reputation onto the surviving one, and it is expensive to reverse, because clients may cache it indefinitely regardless of Cache-Control. The module defaults to 301 and documents 302 for a provisional move.

Paid for once already

The traps, written down

CAA silently blocks ACM

The migrated zones authorised pki.goog, sectigo.com and letsencrypt.org, and not amazon.com. There is no error. The request stays PENDING_VALIDATION forever.

Certificate ordering

ACM validates by DNS, so it cannot issue until Route 53 is authoritative. Apply the zone and certificates with -target, repoint the nameservers, then apply the rest — or watch validation block for its full 75-minute timeout and fail.

CloudFront in front of a Lambda Function URL returns 403

Every request, in this account. Ruled out: the resource policy, RESPONSE_STREAM invoke mode, a stale URL, org SCPs — the account is in no Organization. A brand-new Function URL with authorization disabled entirely still returned 403. Both functions render correctly under direct lambda invoke.

arm64 all the way down

An artifact built on an x86 runner installs and tests green, then fails to load a native module at first request. Build jobs targeting the node run on ubuntu-24.04-arm.

pnpm's default layout breaks the bundle

--node-linker=hoisted is not cosmetic. A bundler following the symlink for next reaches the package and stops, leaving its transitive dependencies behind — the bundle imports fine locally and dies on first cold start.

Never apply oxagen or stella untargeted

Both hold a CloudFront alias record for a site now served from the node. Applying reverts a working site to the 403 above.

Honest accounting

What this design gives up

One instance, one AZ, no failover

Every database is on one box. If it fails, all three are down, and recovery is manual: restore the volume from a snapshot and bring an instance up in the same AZ.

Mitigated by: nothing, structurally. The mitigation is the exit — Postgres to Aurora when traffic justifies the floor.

No point-in-time recovery

Snapshots are crash-consistent and daily. A restore loses up to 24 hours.

The default VPC, and a public subnet

No purpose-built network. The instance needs outbound reach for images and updates, and a private subnet would need a NAT gateway costing more per month than the instance.

Mitigated by: no inbound rule exists, and every port is bound to loopback as well. The exposure a public subnet normally implies is not present.

Deliberate DNS drift

stella.oxagen.sh and docs.oxagen.sh are alias records Terraform owns and wants back, repointed by hand at the node. Terraform's plan is wrong about production and known to be. It is not repaired because rewriting a live record for a serving site is a bigger change than it looks.

One account is one blast radius

Tags, Resource Groups and separate state keys separate three brands for grouping and for apply scope. They are not an account boundary, and IAM in this account is not partitioned by brand.

Thin memory margin

Three engines on 4 GiB with explicit limits and a swapfile. It works. It has no headroom, and the swapfile is a shock absorber, not capacity.

Trade-offs12 / 13

Speaker notes

Say plainly that these are the authors' own acknowledged trade-offs, quoted from the module comments rather than found by review. That matters: a design that writes down what it gave up is reviewable, and this one does. The right argument to have is not "were these known" but "is the balance still correct today".

The public subnet is the one that draws reflex objections. Meet it directly — the usual argument against a public subnet is exposure, and there is no inbound rule and no listening socket on a routable address. What a private subnet would additionally buy is defence against a misconfiguration that opens one, and the answer to that is the loopback binding, which is a second independent control.

The DNS drift is the item most likely to bite a new engineer, because Terraform will confidently propose the wrong thing and the plan looks routine. It belongs on a runbook, not in someone's memory.

If pressed on when the single instance stops being acceptable: the trigger is the first customer whose traffic depends on it, not a date and not a load number.
