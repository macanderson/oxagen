Optimization Opportunities — Process-Level
What to fix before considering a language rewrite
Thesis: The current TypeScript implementation has at least 3–4 high-impact process-level improvements that could reduce cost by 40–60% and wall time by 30–40% before any language-level optimization is warranted. Rust would speed up the scaffold code, which is not the bottleneck — the bottleneck is LLM round-trips and redundant tool calls.
🔁
1. Loop-termination budget — the biggest single win
The agent ran the same test command 8+ times after the fix was already confirmed. A deduplication check on tool calls (hash the command + cwd + stdin) and a max-verify-iterations cap (e.g. 3 identical test runs → stop) would eliminate ~280k tokens (~55% of the total budget) from this task alone. The completeness-judge already exists in the pipeline — it needs a hard budget that fires earlier and blocks redundant re-runs.
HIGH IMPACT — est. 40–55% token reduction
⏱️
2. Container warm-start / Node pre-install
Agent setup takes 110s — 26% of total wall time — almost entirely spent installing Node 22 via NodeSource and uploading the oxagen.mjs bundle. Two fixes: (a) Pre-bake a Harbor base image with Node 22 already installed so setup drops to <10s. (b) Use Harbor's upload_file cache — the bundle hash hasn't changed between runs, so Harbor can skip the upload if the content hash matches. Both are harness-level changes, not CLI changes.
HIGH IMPACT — est. 100s wall time saved per task
📦
3. Prompt caching — already partially wired, needs full activation
The CLI has perf(cli): SWE-bench speedups — bounded enhance, prompt caching, verification budget already merged (commit 53475a38). However, the smoke run shows no cache tokens reported (n_cache_tokens: null). This means prompt caching is either not being activated for the Vercel AI Gateway route, or the system prompt is not being marked as cacheable. Activating Anthropic's cache_control: ephemeral on the system prompt + tool definitions would save ~60% on input tokens for long sessions.
HIGH IMPACT — est. 30–60% input token cost reduction
🧠
4. Completeness-judge fires too late
The verifier returned 0.0 because the agent's patch was incomplete relative to the hidden test spec — it fixed the regex but didn't add the expected test case that SWE-bench's FAIL_TO_PASS list required. The completeness-judge runs at the end but not mid-session to check "have I covered all the acceptance criteria from the issue?". Adding a mid-session completeness check after the first confirmed fix (at step ~15 of 35) would catch the missing test case and prompt the agent to add it before terminating.
HIGH IMPACT — directly improves resolved-rate
🗜️
5. Context window management — history trimming
At 35 steps and 507k tokens, the context window is carrying the full conversation history including verbose bash outputs (test runner output, pip install logs). The CLI's history depth is configurable but not dynamically trimmed. Implementing rolling summarization of tool outputs older than N steps (keeping only the summary + result) and truncating large bash outputs to the last 200 lines would reduce context size by 30–40% for long-running tasks without losing signal.
MEDIUM IMPACT — est. 20–35% context reduction
🔀
6. Model routing on SWE-bench — use Haiku for exploration steps
The smoke run used a pinned claude-sonnet-4.5 for all 35 steps. The cost-aware router already exists but is disabled when a model is pinned. In SWE-bench mode, exploration steps (file reads, grep, bash probes) could use Haiku while only the fix-generation and test-analysis steps use Sonnet. The router's classifyTier function has the right heuristics — it just needs a per-step routing mode rather than per-task routing. Estimated savings: 30–40% cost at similar accuracy.
MEDIUM IMPACT — est. 30–40% cost reduction
⚡
7. Parallel tool execution — independent reads
The agent performs many sequential file reads that are independent of each other. The AI SDK's tool layer supports parallel tool calls (experimental_toolCallStreaming) but the CLI's loop serializes them. Batching independent read_file + code_graph calls into a single model turn would reduce the number of round-trips from ~35 to ~20 for a task like this, saving ~30–40% of wall time.
MEDIUM IMPACT — est. 25–35% wall time reduction
The Rust Question — Should We Port?
Architecture verdict and recommendation
🦀 Verdict: Not yet — and maybe never for the core loop

The data is unambiguous: the bottleneck is not TypeScript execution speed. It is LLM round-trips, redundant tool calls, and container setup overhead. A Rust rewrite of the scaffold would speed up the parts that take milliseconds while leaving the parts that take seconds and minutes unchanged.

❌ Where Rust would NOT help
  • LLM API latency (~200–400ms per call) — network, not CPU
  • Token generation speed — model, not scaffold
  • Container setup (110s) — Docker + NodeSource, not Node.js
  • Redundant test-run iterations — logic, not language
  • Prompt caching activation — API config, not CPU
  • Context window size — prompt engineering, not language
✅ Where Rust WOULD help
  • CLI startup time (~300–600ms Node.js cold start → <10ms)
  • DuckDB query throughput for the context engine
  • Tree-sitter parsing (already WASM, Rust-native would be faster)
  • Bundle size (oxagen.mjs is large; a Rust binary is self-contained)
  • Memory footprint in long-running daemon mode
  • Parallel file I/O for code-graph indexing
The right architecture: Keep TypeScript as the source of truth for the agent scaffold, prompt engineering, and pipeline logic — this is where iteration speed matters and where the team's expertise lives. Extract the performance-critical inner loop (tool execution, file I/O, context-engine queries) into a Rust native addon (napi-rs) or a separate Rust binary called via IPC. This gives Rust's speed where it matters without abandoning the TS codebase.

TS-First, Rust-Derived Strategy
How to get Rust speed without abandoning the TS foundation

The requirement is clear: "we want it to always be derived from a TS package." This is the right call. Here is the architecture that delivers Rust performance while keeping TypeScript as the authoritative source:

TS
TypeScript core stays as-is
Agent scaffold, prompt engineering, model routing, pipeline orchestration, completeness-judge, settings, session management — all TypeScript. This is where the team iterates fast. The published @oxagen/cli npm package continues to be the canonical distribution.
🦀
Rust native addon via napi-rs — hot paths only
Extract the performance-critical inner loop into a Rust napi-rs addon: parallel file I/O, tree-sitter parsing, DuckDB query batching, and the tool-call execution dispatcher. The TS layer calls into Rust via the same require() / import interface — no IPC, no subprocess. The Rust code is generated from the TS type definitions (codegen from Zod schemas), so TS remains the source of truth.
📦
Pre-built binaries shipped in the npm package
The @oxagen/cli package ships pre-built .node binaries for macOS (arm64/x64), Linux (x64/arm64), and Windows (x64) — the same pattern used by esbuild, swc, and @napi-rs/canvas. Users get Rust speed with a plain npm i -g @oxagen/cli. No Rust toolchain required at install time.
✓
Graceful fallback — pure JS when .node is absent
The TS layer checks for the native addon at startup and falls back to pure-JS implementations if it is absent (benchmark containers, CI without pre-built binaries, unsupported platforms). This is the same pattern as node-gyp optional deps. The bundle (oxagen.mjs) remains the benchmark distribution path with no native dep required.

Key Observations
What the data actually tells us
✅ The scaffold works. The agent correctly diagnosed and fixed the Django regex vulnerability on the first attempt, in the right file, with the right change. The failure was a completeness gap (missing test case), not a reasoning failure. This is a much better failure mode than a wrong fix.
⚠️ 507k tokens for a 2-line fix is too much. The correct fix is 2 lines. The agent used 507k tokens to get there. Even accounting for exploration and verification, 150–200k should be sufficient. The loop termination fix alone would get us there.
📊 One data point is not a benchmark. We need at least 50 tasks to get a stable resolved-rate estimate. Run TASK_IDS="..." N_CONCURRENT=4 ./compare.sh with 50 tasks from SWE-bench Verified to get a number worth publishing.
🜂 The cost-aware router is the right idea. Routing exploration steps to Haiku and fix steps to Sonnet is exactly the right architecture for SWE-bench. The infrastructure exists — it just needs per-step activation rather than per-task activation.
