# Transactional email templates and SaaS send-point wiring

Five new email templates (verification, invitation, low-balance alert, payment failed, payment receipt) added to `@oxagen/notifications`, plus wiring into Better Auth's email verification callback, the workspace invitation handler, and billing dunning/low-balance flows. Templates are pure functions returning `{subject, text, html}`, sent via the existing SMTP transport (Resend via `smtp.resend.com`). All email sends use a fire-and-forget pattern so the critical path (DB writes, auth flow) is never blocked by notification failures.

**Watch for:** `notifyLowBalance` is exported but never called anywhere — the alert function exists but no code path invokes it (confirmed). `paymentReceiptTemplate` is similarly orphaned — no send point uses it (confirmed). The billing notification paths pass raw org IDs (UUIDs) as org names in email subjects (confirmed).

## High-level view

Two of the five templates are dead code: `notifyLowBalance` has no caller in the codebase (the UI calls `isLowBalance` for banner rendering but nothing dispatches the email), and `paymentReceiptTemplate` has no send point (the `invoice.paid` webhook grants credits and resets dunning but never emails a receipt). This leaves the SaaS email coverage incomplete at the delivery layer despite the template layer being fully built out.

Both billing notification paths (`notifyLowBalance` and dunning's `onInvoicePaymentFailed`) pass the raw `orgId` UUID as the `orgName` template field. The resulting email subjects read "Payment failed for 550e8400-e29b-..." — the invitation handler demonstrates the correct pattern of resolving the org name from DB before templating.

The auth config tests for email verification are tautological — they construct local objects with hardcoded values and assert on those values, providing no regression protection against changes to the actual `auth.ts` config. The handler-level and billing tests don't mock `@oxagen/notifications`, so the new email wiring has zero test coverage at the integration boundary.

## Dead send points: `notifyLowBalance` and `paymentReceiptTemplate`

The implementation creates `notifyLowBalance` as an exported async function in `autoreload.ts`:

```typescript
export async function notifyLowBalance(orgId: string, result: LowBalanceResult): Promise<void> {
  if (!result.low) return;
  // ... sends via notifyOrgManagers
}
```

Searching the entire codebase for callers returns zero results outside the definition itself. `isLowBalance` is called from the Next.js org layout and billing subscription page — but purely for rendering a `<LowBalanceBanner>` in the UI. No background job, webhook handler, or scheduled function invokes `notifyLowBalance`.

The same gap exists for `paymentReceiptTemplate`. The Stripe webhook handler processes `invoice.paid` events by calling `grantPlanCreditsForInvoicePaid` and `onInvoiceRecovered`, but never sends a receipt email. The template exists, is tested, is exported — but has no send point.

Two of the five "SaaS transactional emails" are templates-only with no delivery path.

## `orgId` passed as `orgName` in billing email subjects

In `autoreload.ts`:

```typescript
const template = lowBalanceAlertTemplate({
  orgName: orgId,  // <-- UUID, not a human name
  balanceCents: result.balanceCents,
  ...
});
```

And in `dunning.ts`:

```typescript
const template = paymentFailedTemplate({ orgName: orgId, graceDays: DUNNING_GRACE_DAYS, billingUrl });
```

Both pass the raw org ID as the org name. The invitation handler demonstrates the correct pattern: query `schema.organizations` for the `name` column via `withSystemDb`. The billing paths should do the same. Since these run outside tenant scope (webhook context / background job), `withSystemDb` is the appropriate access pattern.

## Auth config tests: testing the test, not the code

The "email verification config invariants" describe block constructs local objects:

```typescript
it("requireEmailVerification is configured as true (policy constant)", () => {
  const emailAndPasswordConfig = {
    requireEmailVerification: true,
  };
  expect(emailAndPasswordConfig.requireEmailVerification).toBe(true);
});
```

This is a tautology. If someone removes `requireEmailVerification` from `auth.ts` or changes it to `false`, this test continues to pass. The existing `sendResetPassword config invariants` block uses the same pattern (pre-existing), but extending that pattern to email verification doubles down on tests that provide false confidence.

## Test coverage gap at the notification integration boundary

The existing `workspace.invite.send.test.ts` mocks `@oxagen/database` but does not mock `@oxagen/notifications`. The test cannot verify that `sendEmail` is called after a successful invite, nor can it verify the error isolation. Since the email send happens in a `void (async () => { ... })()` IIFE, the test would need to mock `sendEmail` and flush microtasks to observe the call.

The dunning tests don't mock `@oxagen/notifications` either. The `notifyOrgManagers` call inside the fire-and-forget IIFE will attempt `withSystemDb` against the test's DB mock, likely throw (the mock doesn't set up the query paths `notifyOrgManagers` needs), and be silently swallowed by the outer try-catch. The notification wiring in `onInvoicePaymentFailed` is effectively invisible to the test suite.
