# Pluggable storage driver selection via STORAGE_DRIVER env var

The storage package is decoupled from Vercel Blob as its sole backend. A `resolveAdapter()` function in `client.ts` reads the `STORAGE_DRIVER` env var (defaulting to `"vercel-blob"`) and dispatches to the appropriate factory. `StorageNotFoundError` moves to a shared `errors.ts` so all future drivers throw a consistent error type. A comprehensive authoring guide documents the full extension path. The public API surface (`@oxagen/storage` exports) is unchanged -- this is invisible to consumers.

**Watch for:** The `STORAGE_DRIVER` enum in the Zod schema and the `SUPPORTED_DRIVERS` tuple in `client.ts` are independent constants that must stay in sync manually (confirmed). The singleton has no reset mechanism in production, meaning a process that initializes storage before a hot-reload of env vars will keep the stale adapter (likely intentional but worth noting for serverless cold-start assumptions).

## High-level view

The refactoring applies the standard strategy + factory pattern at the right level. `resolveAdapter()` reads `STORAGE_DRIVER`, switches on it, and each case pulls its own credentials. The default branch throws with the supported list. Env-driven, fail-closed, one extension point.

The backward-compat re-export of `StorageNotFoundError` from `vercel-blob.ts` prevents breakage for any internal code that imported from the file path directly rather than through the barrel.

The authoring guide covers the interface contract, env registration, test patterns, and a full S3 skeleton. One gap: the skeleton's `toBuffer` throws for `Blob` inputs in an `async` function where `await blob.arrayBuffer()` is the correct path, which could mislead a future author into thinking `Blob` isn't a supported body type.

## The resolveAdapter dispatch and SUPPORTED_DRIVERS drift risk

The `SUPPORTED_DRIVERS` tuple exists purely for the error message in the default branch. It has no type-level relationship with the Zod enum in `env.ts`. If a developer adds `"s3"` to the Zod enum but forgets the switch case, `resolveAdapter` hits the default branch at runtime -- fail-closed, fine. The reverse (adding a switch case without the Zod enum) means Zod rejects the env value before `resolveAdapter` runs -- also fine. The risk is confusion: two places to update, no compile-time enforcement that they agree.

## S3 skeleton in the authoring guide

The guide provides a ~100-line S3 adapter as a copy-paste starting point. The `toBuffer` helper throws synchronously for `Blob` inputs:

```typescript
if (body instanceof Blob) {
  throw new Error("Blob bodies require async conversion. Use Uint8Array or ArrayBuffer.");
}
```

Since `put()` is `async`, the correct pattern is `Buffer.from(await blob.arrayBuffer())`. A future author who reads the skeleton literally will either avoid `Blob` inputs or add unnecessary complexity. The comment mentions "use streaming upload for large objects" but doesn't show how.

## Test coverage gaps

The new driver-selection tests cover the happy path (default, explicit vercel-blob, unknown driver throws). The interaction of driver selection + missing credentials (STORAGE_DRIVER=vercel-blob but BLOB_READ_WRITE_TOKEN absent) is covered implicitly by the pre-existing "missing token" tests that now flow through the switch case, but it's not explicitly labeled as a driver-selection scenario. Not a gap per se, but a reviewer reading only the driver-selection block wouldn't see that path exercised.

No shared contract test harness exists. When a second driver lands, there's no `runAdapterContractTests(factory)` function to ensure behavioral parity across implementations.
