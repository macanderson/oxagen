# Shared lessons

- [2026-07-11] `pnpm exec <bin> ...` runs a dependency-staleness check first; if the lockfile/node_modules drifted at all it tries an interactive `pnpm install` and aborts with `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` in any non-interactive agent shell. Skip the wrapper and call the binary directly (`node_modules/.bin/vitest run --coverage`) instead of `pnpm exec vitest run --coverage` when working non-interactively. (source: test-engineer/reflections/2026-07-11-plugins-branch-coverage-gate.md, agent: test-engineer)
- [2026-07-11] V8/Istanbul branch coverage (`BRF`/`BRH` in lcov) only enumerates branches that were *reached* at least once at runtime — a big if/else chain inside a function that's always short-circuited by an early return can show as having near-zero "branches found" for the untaken code, not just zero "hit". A file's reported branch % can therefore understate the true size of the untested surface; don't trust the percentage alone, read the raw `lcov.info` BRDA/DA records (or just the source) at the reported uncovered-line range before estimating how much test-writing is needed. (source: test-engineer/reflections/2026-07-11-plugins-branch-coverage-gate.md, agent: test-engineer)
- [2026-07-11] Before pushing to a shared branch with an already-open PR, verify the PR is still open (`gh pr view <branch> --json state`) and that the local branch tip is still what you think — a PR can merge mid-session on a contested branch. If it merged, check `git merge-base --is-ancestor <old-tip> origin/main` and `git log --oneline origin/main..HEAD` before pushing/opening a new PR, so you know your push is a clean single-commit delta rather than accidentally reopening the old diff. (source: test-engineer/reflections/2026-07-11-plugins-branch-coverage-gate.md, agent: test-engineer)
- [2026-07-11] Run `git status`/`git log -3` as the literal FIRST tool call in any shared-worktree/coverage-gate task, before reading even one source file — on this codebase "an automated optimizer + other sessions work the same tree in parallel" is not theoretical: a coverage-gate-fix worktree had its own concurrent process staging (then mid-session committing+pushing) fixes to the exact same files I was targeting, AND a wholly separate PR landed on `main` fixing the identical apps/api functions/branches gate independently — making the whole branch/PR redundant with real merge conflicts. Re-check for fresh concurrent commits every few files, not just once at session start, and if the coordinator reports a competing PR already merged, stop immediately, leave uncommitted work in place exactly as instructed, and report precise `git status`/`git log` state rather than pushing, committing, or self-cleaning. (source: test-engineer/reflections/2026-07-11-apps-api-coverage-gate-superseded.md, agent: test-engineer)
