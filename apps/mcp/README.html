The Model Context Protocol server

An xmcp server that exposes every Oxagen platform capability over the Model Context Protocol — so Claude, IDEs, and autonomous agents can drive the platform with the same fidelity as the REST API and the interactive app.

oxagen-v2-mcp.vercel.app/mcp xmcp 0.6.10 Streamable HTTP stdio transport Vercel deployed

What this is

apps/mcp is the Model Context Protocol surface of the Oxagen platform. Tools are thin wrappers around the same @oxagen/handlers and @oxagen/oxagen capability contracts that back the REST API — there is zero business logic in this package, and therefore zero drift between surfaces. Any MCP client that can send an authenticated request to /mcp gains the full capability set.

Org + workspace scope is resolved from the API key, just as in the REST API. No path segments or session parameters are needed.

Zero drift

Tools are generated from the same @oxagen/oxagen contracts that back the API. Adding a capability once propagates to all three surfaces automatically.

◎

Two transports

Streamable HTTP for remote clients (Claude.ai, cloud agents). Stdio for local MCP clients and IDE extensions — same tools, different wire format.

⌁

API-key scope

The Bearer key resolves org and workspace at the middleware boundary. No per-call tenant parameters are needed in any tool input schema.

Connecting a client

Choose HTTP for remote or cloud-hosted clients. Choose stdio for local MCP clients and IDE extensions running on the same machine.

Add to your MCP client configuration. The endpoint is /mcp over streamable HTTP — not /mcp/sse, not /v1/mcp.

// MCP client config (e.g. Claude Desktop / claude_desktop_config.json)
{
  "mcpServers": {
    "oxagen": {
      "transport": "http",
      "url": "https://oxagen-v2-mcp.vercel.app/mcp",
      "headers": {
        "Authorization": "Bearer oxa_live_xxxxxxxxxxxxxxxx"
      }
    }
  }
}

Replace oxa_live_xxxxxxxxxxxxxxxx with a real API key from the Oxagen workspace settings. The key encodes your org and workspace — no additional config is needed.

For local clients (VS Code MCP extension, local agent harnesses). Build first, then point the client at the stdio entry.

# build the server
pnpm --filter @oxagen/mcp build
# dist/stdio.js is the stdio transport entry

# example: run directly (the client spawns this as a subprocess)
OXA_API_KEY=oxa_live_xxxxxxxxxxxxxxxx node dist/stdio.js
// VS Code / local MCP config
{
  "mcpServers": {
    "oxagen": {
      "command": "node",
      "args": ["/path/to/oxagen-monorepo/apps/mcp/dist/stdio.js"],
      "env": { "OXA_API_KEY": "oxa_live_xxxxxxxxxxxxxxxx" }
    }
  }
}

Architecture

Source layout

  • src/tools/ — one file per MCP tool, each a thin wrapper over the matching @oxagen/handlers export
  • src/context.ts — per-request auth resolution; reads the Bearer key, resolves org + workspace, attaches to xmcp context
  • src/middleware.ts — IAM check and telemetry instrumentation applied before every tool invocation

FAQ & gotchas

▸ Is the endpoint /mcp or /mcp/sse?

It is /mcp — streamable HTTP transport. There is no /mcp/sse path on this server, and there is no MCP endpoint at all on oxagen-v2-api.vercel.app (that host is the Hono REST service only). The single correct production URL is:

https://oxagen-v2-mcp.vercel.app/mcp

SSE-style long-poll is not used. xmcp implements the MCP streamable HTTP transport spec directly.

▸ How are tools kept in sync with the REST API?

Both the MCP tools (src/tools/) and the REST routes (apps/api/src/routes/) call the same handler functions from @oxagen/handlers. The input schemas are derived from the same Zod definitions in @oxagen/oxagen. Adding a capability means: (1) add the handler in @oxagen/handlers, (2) add a route in apps/api, (3) add a tool in apps/mcp/src/tools/. Missing any step is a parity violation and will be flagged in code review.

▸ Do I need to pass org or workspace in each tool call?

No. src/context.ts reads the Authorization: Bearer <api-key> header once per request, resolves org and workspace from the key via @oxagen/auth, and makes them available to all tool handlers through the xmcp request context. Tool input schemas do not include tenant fields.

▸ How do I test a tool locally without a full MCP client?

Use the xmcp dev server (pnpm --filter @oxagen/mcp dev), which starts an inspector UI at http://localhost:3002 (default xmcp dev port). You can invoke any tool directly from the inspector with a test API key. Alternatively, run the stdio transport and point a local Claude Desktop config at dist/stdio.js.

▸ What happens if a tool throws an error?

The middleware in src/middleware.ts catches handler errors and returns a structured MCP error response — including a trace-id that threads through to the telemetry and pino logs. Unhandled exceptions at the xmcp framework level are caught by the framework and returned as MCP protocol errors. Never let tool code throw raw untyped errors — wrap in typed error objects from @oxagen/handlers.
