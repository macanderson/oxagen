A founder's story

One person built Oxagen in seven months, while learning to manage a fleet of coding agents.

Before he built Oxagen, Mac Anderson built an agent, a benchmark, a protocol, a verifier, a fleet, and a memory system. He wrote little of it by hand. He directed coding agents, six at a time. Over the summer he learned how much work it takes to manage that many agents. He built Oxagen to do that work, and his agents sent their work through Oxagen while they built it. This page tells the seven months from the record: his GitHub history, his git history, and the 8,133 prompts he typed to Claude Code.

The baseline counts lines changed, not lines added. No credible source publishes lines added per developer apart from lines removed. The same Google study does publish change size. The median change modifies 24 lines. A median developer makes 3 changes a week, so that developer changes about 72 lines a week. That figure multiplies two medians, so read it as a rough scale, not as a statistic. A tenth of Google's changes modify a single line, but a few changes are huge. So the real average is higher than 72. He changed about 328,000 source lines a week. That is thousands of times more. The two figures count different things, so this page does not quote an exact multiple.

Google removed changes made by automated tools before it counted anything. So Google's baseline counts what people wrote by hand. His number counts what his agents wrote.

He did not type this code. Agents wrote it. He directed them, reviewed their work, and merged it. So this compares one person managing agents with one person writing by hand. That comparison is the subject of this page. Two more facts count against him. These repositories are four months old. They have no release schedule, no on-call rotation, and no other engineers to work with. So a commit here takes less work than a commit at Google. Also, when he opened and merged a pull request himself, no second person reviewed it.

What he had to learn

Learning to manage a fleet

With one agent, you give it a task, watch it work, and read the diff. With six agents at once, the job changes, and this page is about that job. It was the hardest thing he learned in seven months, and none of it was about prompting.

He started with one agent on one branch, and he watched it work. That setup works, but it cannot grow, because he can only watch one thing at a time. So he added more agents. In the setup he ended with, 6 agents work in parallel, each in its own git worktree. Background agents are on, so work continues while he reads something else.

More agents caused problems he had not expected. Two agents edited the same branch. A branch merged into main with no conflicts, but it still did not work with code that had merged beside it. He had to repair a broken main three separate times before he understood the cause. A merge with no conflicts says nothing about whether the code works. Agents also finished, reported success, and left their work uncommitted. These problems happened between agents, not inside any one agent.

What running many agents needed

  • A separate worktree for each agent, so two agents cannot edit the same files.
  • A written definition of done. Without one, an agent decides for itself what finished means.
  • Checks that run without him. There are 21 of them, so he does not have to review six agents’ work by hand.
  • A trial merge before the real one, because a merge with no conflicts can still break the code.

What he still could not answer

  • What each agent did, in order, and what it read.
  • What that cost, and which piece of work it paid for.
  • Who allowed each action, and under which rule.
  • Which of the six agents is stuck right now, and on what.

He could build the first list himself. The second list is a management problem, and it got worse with every agent he added. He built Oxagen to answer it.

A human reviewer notices when a file imports across a boundary it should not. Six agents working in parallel do not notice. Each may break the same rule in a different place on the same afternoon. A test that fails the build checks every change, however many agents make them. So with many agents, the architecture tests matter most.

The audit

In September he had the operator console checked against its own specification. The reviewer was told to look hard for problems and to assume the work was incomplete. The review returned 14 findings. Two of them must be fixed before a release. Its summary said:

The app has substantial working foundations, but it does not yet close the core operator workflows.

The audit is published, with every finding, its acceptance criteria, and the repository it checked. The audit sits in a different repository from the code. So nobody can quietly edit the findings to match what shipped.

This audit shows how the work is checked. It does not show that the work is finished. The work must still clear the two release blockers the audit named.

How this was made

Oxagen was built using Oxagen

This claim can sound like marketing, so here is how it works.

The agent's base URL points at 127.0.0.1:51781. That address is Oxagen's own gateway, running on his laptop. So every model call made from this repository goes through the gateway, and there is no other path. Oxagen sees each call, measures its cost, and records it. So Oxagen governed and priced the runs that built Oxagen.

Tool calls work the same way. A hook checks each tool call and can refuse it before it runs. Without a rule, each of six agents would start its own full test build. So this repository has a hook that denies an agent a full test build. This is Oxagen's main idea: the agent asks, and a rule answers. Here it applies to the agents writing Oxagen.

The prompts that wrote this page went through the same gateway. The prompt log this page uses is the record the gateway kept.

Scope: this is the local gateway and its record, which is what a single operator runs. It uses the same code as the hosted control plane. It is not a separate demo build. But one laptop is not a deployment, and this page does not claim it is.

What it became

Why Oxagen

He built the agent, the benchmark, the protocol, the verifier, and the fleet. Then he found that the hardest part was knowing what each agent did, what it cost, and who allowed it.

Oxagen is workforce management for autonomous agents. You give each agent its own identity. You set its authority, budget, tools, and skills in one mandate. For actions routed through Oxagen, the agent asks, a rule your team wrote answers, and Oxagen records the answer with its cost.

AccessThe identity the agent acts as, and what it may request.
Budget and rulesWhat it may spend, and the rules it works under.
EquipmentThe tools, skills, and business context it may use.
RecordWhat each governed run read, changed, and cost, and which rule answered each request.

Oxagen shows you every governed action, the rule that answered it, the person who approved it, and which agent spent what, on whose behalf.

This page was written from the same kind of record that Oxagen keeps.
