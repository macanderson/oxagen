## The contract model

Every capability is declared once, in the platform contract registry. A declaration says:

- The capability's `name` (for example, `recall_memory`)
- Its input and output schemas (Zod)
- The surfaces it is on: `api`, `mcp`, and `agent`, in any combination
- Its risk level, and whether a person must approve it before it runs
- Its default IAM roles and effects

The registry is the one source of truth. Every API route and every MCP tool reads from it, so a capability behaves the same way on every surface it declares. Surface adapters are wired separately, and repository checks detect missing routes and tools.

`pnpm check:manifest` compares the registry against the routes and tools that exist and reports each gap as a warning.

## Capability naming

A capability name is **verb first, snake_case**: an imperative verb, then the
thing it acts on, joined by underscores. Two or three words is the norm. A
fourth appears only when it is the one way to keep the name unique.

| Shape | Examples |
|---|---|
| `verb_noun` | `list_conversations`, `recall_memory`, `upload_asset` |
| `verb_noun_qualifier` | `list_agent_tools`, `resolve_mcp_consent`, `set_plugin_secret` |

Names are unique across the registry, and a capability's name is the
same string everywhere: REST route dispatch, MCP tool name, model-facing tool
name, IAM grants, audit records, and metering. There is no separate
model-facing spelling.

**Names are stable, and there is no alias layer.** If a capability is
renamed, the old name stops resolving. The registry carries no
compatibility alias, so a rename is a breaking change. Check the current contract and release notes before upgrading.

## Capability list

Inspect `packages/oxagen/src/contracts/` for a capability's input, output, surfaces, and approval metadata. The generated [Architecture atlas](/docs/architecture) includes the contract catalog. Per-capability reference pages live in the repository at `docs/capabilities/`.

An MCP client's `tools/list` response describes the tools that server exposes. Use the returned schemas instead of assuming API, MCP, and agent expose identical sets.

## REST route convention

Capability routes live under `/v1/{orgSlug}/{workspaceSlug}/`, and each capability's path is chosen for it, not derived from the name. For example, `list_agent_tools` is mounted at `/v1/{orgSlug}/{workspaceSlug}/agent/tools` and `revoke_api_key` at `/v1/{orgSlug}/{workspaceSlug}/api-keys/revoke`.

Two rules hold everywhere:

- **Every capability route requires the org and workspace slug segments.** Use the slugs your API key is scoped to.
- **Most capability routes are `POST`,** including ones that only read. The request body is the capability's input, so even a list call sends a JSON body (`{}` when there is nothing to pass).

Run `pnpm check:manifest --json` in the monorepo to print the full route and tool parity table. There is no runtime `/v1/capabilities` endpoint.

## Browser flows

Some operations need a browser redirect or a live approval interaction in addition to a capability call. Read the operation's contract and route reference. The presence of an API route does not imply an identical MCP interaction.
