---
title: Authentication
description: "Create, use, rotate, and revoke workspace API keys, and distinguish machine credentials from CLI logins."
---

Create a workspace-scoped API key for a script or MCP client at **Organization → API keys** (`/{org}/api-keys`). Select the workspace, create the key, and copy it when shown. Oxagen stores a hash, so the raw key cannot be recovered.

Keys use the `ox_` prefix followed by a base64url-encoded random value. Keep them in a secret store or environment variable.

## Use a key

```http
POST /v1/{orgSlug}/{workspaceSlug}/agent/tools
Host: api.oxagen.sh
Authorization: Bearer ox_…
Content-Type: application/json

{}
```

For MCP, send the same Bearer header to `https://mcp.oxagen.sh/mcp`. The key resolves the organization and workspace. Use the matching slugs for API routes.

## Key purposes

Not every `ox_` credential has the same authority:

| Kind | Authority |
|---|---|
| Ordinary API key | Workspace-scoped API principal. Enterprise IAM resolves the creator's grants. There is no arbitrary capability allowlist for this key. |
| CLI login, `cli_session_v1` | Resolves to the person who authorized `oxagen login`. Authentication rechecks organization and workspace membership. |
| Host key, `tacho_host_v1` | Event ingestion, policy-bundle reads, and command polling only |
| Gateway key, `tacho_gateway_v1` | MCP-exposed, nonmutating capabilities that are not high-sensitivity |
| Stella telemetry key | Operational telemetry ingestion only |

Machine-purpose checks apply before the plan-dependent IAM resolver. An unknown purpose is denied. `create_api_key` refuses reserved purposes, so callers cannot mint a host, gateway, or CLI-login key through the generic create call.

The agent registration credential has its own purpose and exchange flow. It is not a general API or MCP bearer credential. The credential for a mediated downstream connection is separate again: Oxagen holds that credential and uses it on the agent's behalf.

[RBAC and roles](/docs/governance/rbac) explains the plan-dependent resolver. Do not assume a generic `scope` object creates a capability allowlist.

## Rotate or revoke

Use **Organization → API keys** to rotate or revoke a key. Rotation replaces the key and revokes its predecessor. Update the integration with the new value. Revocation causes subsequent authenticated requests with the old key to fail.

The API also exposes `revoke_api_key`:

```http
POST /v1/{orgSlug}/{workspaceSlug}/api-keys/revoke
Authorization: Bearer ox_…
Content-Type: application/json

{ "keyId": "uuid" }
```

Inspect the key's expiry when creating or rotating it. Different provisioning flows set different lifetimes. Revocation writes `api_key.revoked` to the security record.

## Store credentials

Keep keys out of source control, browser bundles, prompts, and shared terminal output. Revoke a key if an unauthorized person may have copied it. Use `oxagen login` for a person's terminal access and the enrollment flow for a registered agent's host.
