## API keys

An Oxagen API key authenticates a call to the REST API or the MCP server. You create it, and it acts as you. It is the credential a person, a script, or a service you run uses to call Oxagen. It is not a key an agent holds to reach other systems: those connections stay in Oxagen, and the agent requests them at the moment of use.

Each key is tied to one organization and one workspace when you create it. There is no org-only key that applies across workspaces.

Keys use the format `ox_…` (the prefix `ox_` followed by a base64url-encoded 32-byte random value). There is no test-mode key variant.

## Creating an API key

1. Go to **Organization → Developer → Tokens**.
2. Click **Create API key**.
3. Enter a descriptive name (for example, "CI integration" or "Slack bot").
4. Click **Create**. Copy the key. Oxagen shows it only once.

A key acts with the roles of the person who created it. See [What a key is allowed to do](#what-a-key-is-allowed-to-do).

## Using the key

Send the key in every request as a Bearer token. Every capability route also carries your org and workspace slug in the path:

```http
POST /v1/{orgSlug}/{workspaceSlug}/agent/tools
Host: api.oxagen.sh
Authorization: Bearer ox_…
Content-Type: application/json

{}
```

For the MCP server:

```http
POST /mcp
Host: mcp.oxagen.sh
Authorization: Bearer ox_…
```

## Scope and org/workspace resolution

The key carries the org and workspace scope. You do not pass `orgId` or `workspaceId` in request bodies or query strings. The API resolves them from the key.

When a request arrives with a key:

1. The API validates the key (signature, expiry).
2. The API resolves the org and workspace tied to the key.
3. IAM authorizes the capability call as the person who created the key (see below).

## Revoking a key

Go to **Organization → Developer → Tokens** and click **Revoke** next to the key. Revocation takes effect at once: the next request with the revoked key returns `401 Unauthorized`. Oxagen writes an `api_key.revoked` security event.

You can also call the `revoke_api_key` capability:

```http
POST /v1/{orgSlug}/{workspaceSlug}/api-keys/revoke
Authorization: Bearer ox_…
Content-Type: application/json

{
  "keyId": "uuid"
}
```

## What a key is allowed to do

A key has no permissions of its own. IAM authorizes every call made with it as the person who created the key:

- **Enterprise organizations** run the full IAM resolver against that person's role grants. If the creator no longer resolves in the org (for example, they were removed), IAM denies every call with the key.
- **Free, Build, and Scale organizations** do not restrict people at the IAM layer, so a key can call any capability its surface offers. Plan, credit, and budget checks still apply.

A key cannot be narrowed to a subset of capabilities. The create call accepts a `scope` field, but the field is reserved and does not restrict what the key can call. Treat every key as carrying its creator's full roles, and create each key from an account whose role matches what the integration needs.

## Key rotation

Keys do not expire on their own. To rotate a key, click **Rotate** next to it in **Organization → Developer → Tokens**. Rotation issues a replacement key (shown once), carries over the old key's expiry, and revokes the old key in the same step. The old key stops working at once, so update your integration with the new key right away.

## Security notes

- Never commit an API key to source control. Use environment variables.
- Keep keys out of client-side browser code. A key carries org and workspace scope and belongs on a server.
- Never paste an Oxagen API key into an agent's prompt or configuration. An agent under Oxagen holds an identity and a mandate, not a key.
- If you suspect someone has a copy of a key, revoke it and create a new one.
