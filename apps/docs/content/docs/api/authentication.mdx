## API keys

API keys are the authentication mechanism for the REST API and MCP server. Each key is tied to a specific organization and workspace at creation time — there is no concept of an "org-only" key that applies across workspaces.

Keys use the format `ox_…` (the prefix `ox_` followed by a base64url-encoded 32-byte random value). There is no test-mode key variant.

## Creating an API key

1. Go to **Organization → Developer → Tokens**.
2. Click **Create API key**.
3. Enter a descriptive name (e.g., "CI integration", "Slack bot").
4. Click **Create**. Copy the key — it is shown only once.

A key acts with the access of the user who created it. See [What a key is allowed to do](#what-a-key-is-allowed-to-do).

## Using the key

Include the key in every request as a Bearer token. Every capability route also carries your org and workspace slug in the path:

```http
POST /v1/{orgSlug}/{workspaceSlug}/agent/tools
Host: api.oxagen.sh
Authorization: Bearer ox_…
Content-Type: application/json

{}
```

For the MCP server:

```http
POST /mcp
Host: mcp.oxagen.sh
Authorization: Bearer ox_…
```

## Scope and org/workspace resolution

The key carries org and workspace scope. You do not pass `orgId` or `workspaceId` in request bodies or query strings — the API resolves them from the key automatically.

When a key is used:

1. The key is validated (signature, expiry).
2. The org and workspace associated with the key are resolved.
3. The capability call is authorized as the user who created the key (see below).

## Revoking a key

Go to **Organization → Developer → Tokens** and click **Revoke** next to the key. Revocation is immediate — the next request with the revoked key returns `401 Unauthorized`. An `api_key.revoked` security event is written.

Alternatively, use the `revoke_api_key` capability:

```http
POST /v1/{orgSlug}/{workspaceSlug}/api-keys/revoke
Authorization: Bearer ox_…
Content-Type: application/json

{
  "keyId": "uuid"
}
```

## What a key is allowed to do

A key has no permissions of its own. Every call made with it is authorized as the user who created the key:

- **Enterprise organizations** run the full IAM resolver against that user's role grants. If the creator can no longer be resolved in the org (for example, they were removed), every call with the key is denied.
- **Free, Build, and Scale organizations** do not restrict people at the IAM layer, so a key can call any capability its surface exposes. Plan, credit, and budget checks still apply.

Keys cannot yet be narrowed to a subset of capabilities. The create call accepts a `scope` field, but it is reserved and does not restrict what the key can invoke. Treat every key as carrying its creator's full access, and create keys from an account whose role matches what the integration needs.

## Key rotation

Keys do not expire automatically. To rotate a key, click **Rotate** next to it in **Organization → Developer → Tokens**. Rotation issues a replacement key (shown once), carries over the old key's expiry, and revokes the old key in the same step — so update your integration with the new key immediately, because the old one stops working at once.

## Security notes

- Never commit an API key to source control. Use environment variables.
- Keys should not be used in client-side browser code — they carry org and workspace scope and must be kept server-side.
- If you suspect a key has been compromised, revoke it immediately and create a new one.
