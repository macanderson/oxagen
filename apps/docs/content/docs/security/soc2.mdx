The controls on this page are properties of the platform's architecture. This page maps Oxagen capabilities to the SOC 2 Trust Service Criteria (TSC), so your security team, auditors, and procurement reviewers have a concrete starting point.

## CC6: Logical and physical access controls

### CC6.1: Access control policies and procedures

Oxagen enforces role-based access control through a single IAM resolver that runs at the `invoke()` boundary. On Enterprise organizations, and for every agent principal on any plan, the resolver decides a capability call in this order:

1. The principal's role grants for the capability. Across roles, deny wins over require-approval, which wins over allow.
2. The system org Owner role, if no role grant decided.
3. The capability's declared `defaultEffect`, which is `deny` for most capabilities.

On Free, Build, and Scale, the IAM layer allows human and API-key calls and records `tier_gate` as the deciding rule. The resolver also contains rules for workspace grants and org-enforced policies, but their tables were removed, so they decide nothing today. There is no policy editor. **Governance → Policies** lists roles and their grants, read-only. See [RBAC and roles](/docs/governance/rbac).

**Auditor evidence:** `capability.invoke_allowed` and `capability.invoke_denied` events in `security.security_events`. Oxagen also writes every IAM decision to ClickHouse `audit_events` with the resolver's decision log, which names the rule that decided.

### CC6.2: New user provisioning

People join through the invite flow at **Organization → Members**. An invite cannot be sent without a role (Owner, Admin, Member, or Billing). No one can raise their own role. Only an Owner or Admin can change a role. SSO and SCIM provisioning are not available.

**Auditor evidence:** `org.member_invited` and `org.role_changed` events in `security.security_events`.

### CC6.3: Role assignment and modification

A role change (`change_member_role`) needs the acting person to hold the Owner or Admin role, checked against their role assignments. The change soft-deletes the previous assignment, recording who removed it and when, and inserts a new one, so earlier assignments stay on record. Oxagen refuses a change that would leave the organization without an Owner.

**Auditor evidence:** `org.role_changed` security events.

### CC6.5: Access revocation

Owners and Admins can sign out any member at **Organization → Access → Sessions**. Revoke API keys at **Organization → Developer → Tokens** (the `revoke_api_key` capability). Revocation is immediate. The next request with a revoked token returns 401.

**Auditor evidence:** `security.session_revoked` and `api_key.revoked` events. The revocation record names the acting person, the revoked login's id, and the time. It does not record an IP address or user agent.

### CC6.6: Authentication mechanisms

Supported authentication factors:

- Email and password, hashed with Better Auth's default password hasher (scrypt). Passwords are never logged.
- Google OAuth and GitHub OAuth (social sign-in).

MFA enforcement, passkeys (WebAuthn), SSO via SAML 2.0 or OIDC, and SCIM directory sync are not wired. The `org_security_policy` table has an `mfa_required` column, but no middleware enforces it, and Better Auth's `twoFactor` plugin is not registered.

**Auditor evidence:** `auth.sign_in`, `auth.sign_in_failed`, and `auth.sign_out` events. `auth.token_refreshed`, `auth.password_changed`, and `auth.email_verified` are reserved names with no emitter yet, so querying them returns nothing.

### CC6.7: Data transmission protection

All data travels over TLS 1.2 or higher. The API and MCP server enforce HTTPS. There is no unencrypted path to customer data.

### CC6.8: Malicious software and unauthorized code prevention

Oxagen is a control plane, not an agent runtime. It holds no sandbox, no file system, and no surface that runs arbitrary code (ADR-043, `docs/adr/ADR-043-runtime-excision.md`). The agents Oxagen governs run in a customer's own infrastructure or in the reference coding agent (Stella), and Oxagen never runs their code. A call to a third-party MCP server tool through the governed gateway passes the same IAM, entitlement, and audit checks as any other capability call. There is no unmediated code path into the platform.

## CC7: System operations and monitoring

### CC7.1: Detection of anomalies and security events

Oxagen keeps two independent audit stores, each built for a different query pattern:

- **Postgres `security.security_events`**: relational, queryable, and indexed by org and event kind. 7-year retention through monthly RANGE partitions. Used for compliance dashboards and point lookups.
- **ClickHouse `audit_events`**: `ReplacingMergeTree`, one row per IAM decision, 7-year TTL. Each row stores a SHA-256 chain hash over the previous row's hash (for the same org and capability), its own event id, and the capability, so a removed or inserted row breaks the chain. The hash does not cover the other fields, concurrent calls can fork the chain, and there is no built-in verifier yet.

A single source of truth (`packages/compliance/src/security-event-types.ts`) defines 54 typed security event kinds. Adding an event type is a one-file edit. A test fails if the database CHECK constraint drifts from the file. Eight of the 54 are reserved names that nothing emits yet, and the list below marks them. The taxonomy covers:

- Auth lifecycle: `auth.sign_in`, `auth.sign_in_failed`, `auth.sign_out`. Reserved: `auth.token_refreshed`, `auth.password_changed`, `auth.email_verified`.
- API key lifecycle: `api_key.created`, `api_key.revoked`, `api_key.used`
- Billing mutations: `billing.access_denied`, `billing.checkout_initiated`, `billing.credits_purchased`, `billing.plan_changed`, `billing.subscription_canceled`, `billing.budget_updated`, and six additional billing events
- Capability authz: `capability.invoke_allowed`, `capability.invoke_denied`, `capability.invoke_error`
- Org management: `org.member_invited`, `org.member_removed`, `org.role_changed`
- Org lifecycle: `organization.created`, `workspace.created`
- Plugin governance: `plugin.installed`, `plugin.uninstalled`, `plugin.enabled_changed`, `plugin.credential_set`, `plugin.credential_revoked`. Reserved: `plugin.denylist_added`, `plugin.denylist_removed` (there is no plugin denylist).
- Secrets: `secret.revealed`, `secret.exported`, `secret.value_changed`, `secret.key_deleted`
- Security policy: `security.mfa_policy_updated`, `security.session_revoked`
- Data planes and model credentials: `data_plane.updated`, `model_credential.set`, `model_credential.revoked`
- Agent run integrity: `agent_run.event_sequence_conflict`. Reserved: `agent_run.forged_decision_reference`, `agent_run.stale_deny_generation`, `agent_run.finalization_grant_misuse`.
- Access review: `access.review_completed`, `access.member_access_confirmed`
- Privacy / GDPR: `privacy.export_requested`, `privacy.erasure_requested`, `privacy.org_erasure_requested`

**Auditor evidence:** **Organization → Security → Audit** shows `security.security_events` and exports it as an HMAC-signed CSV or NDJSON file (Owner or Admin, Enterprise plan). The app does not show ClickHouse `audit_events`. Query it directly.

### CC7.2: Security incident monitoring and response

**Organization → Security → Audit** shows audit logs as they are written, filtered by event kind, principal, or time range. There is no incident register in the app, and no per-event-kind alert subscriptions. The one alert setting is MCP authentication alerts, under **Governance → Policies**.

SIEM export (Splunk, Datadog, S3, or a JSONL webhook) is not available. Query audit events with `POST /v1/{orgSlug}/{workspaceSlug}/audit/log/query` (`query_audit_log`) and pull them into an external SIEM on a schedule.

### CC7.3: Security event analysis

Every IAM decision row in ClickHouse `audit_events` carries the resolver's decision log, which names the rule that decided (including `tier_gate` on plans where the resolver does not run). An access-control investigation reads why a call was allowed or denied from the stored log rather than reconstructing it.

## CC8: Change management

### CC8.1: Authorized changes to infrastructure and software

Versioned migrations apply every schema change. Migrations follow the expand-then-contract pattern: additive changes first, then removal in a later migration once all callers are updated. No migration is edited after it has been applied, and CI verifies checksums.

Code changes to the audit, IAM, and billing paths need explicit review. The codebase marks the SOC 2 controls path (the `invoke()` boundary, the RLS migration, and the security event emitter) as security-critical.

## CC9: Risk mitigation

### CC9.1: Risk assessment

The contract registry tags high-risk capabilities (deleting an agent definition, changing a member's org role, and publishing a steering context record or tool declaration) with `riskLevel: high`. A capability that declares `requiresApproval` pauses the in-app agent's turn and routes the call to the person in the conversation as an approval card. The person allows or denies it, and an unanswered request expires after five minutes. A high-risk, destructive, or approval-required capability is never in the tool set an agent receives by default.

### CC9.2: Vendor and third-party risk

[Data handling](/docs/security/data-handling) lists the sub-processors. Oxagen uses vendor-neutral adapters for its storage and compute dependencies, so it can move off a sub-processor without application code changes.

## Availability

Oxagen targets 99.9% uptime on the Scale tier with a documented SLA. The application processes hold no durable state. Postgres (Aurora PostgreSQL, with 35 days of point-in-time backups), ClickHouse, and Neo4j hold it.

Audit and security event writes do not block the capability handler. A telemetry write failure does not fail a capability call. The audit write path has its own retry logic.
