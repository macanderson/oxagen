Every workspace has a **governed context graph**: a tenant-isolated Neo4j graph that holds approved entities and relationships from connected sources, agent memories, and stable provider metadata. Oxagen checks every read in workspace scope, so an agent can ground answers in shared context without Oxagen becoming a remote copy of a developer's checkout.

Search it with `oxagen graph search` or the graph capabilities over API or MCP. The current app has no Knowledge explorer page.

## What lives in the graph

| Node kind | Examples | Origin |
|---|---|---|
| Entities | `Person`, `Company`, `Deal`, `Topic` | Connected sources, document ingestion, agent extraction |
| Provider metadata | Repository, configured refs, commits, pull requests, workflow runs, changed-file paths | [GitHub connections](/docs/connections/github) and verified provider events |
| Memories | Observations, rules, facts | [Agent memory](/docs/agent/memory) |
| Run metadata | Agent runs, steps, approvals, tool calls, and metering facts | The durable run record and audit events |
| Documents & assets | Ingested documents and uploaded files | Uploads and connector ingestion |

Oxagen flags product-owned nodes (runs, memories, generated assets) `is_system`, so the graph explorer can show your business ontology on its own.

## Code and evidence boundary

The **exact live code graph stays local** to the checkout or worktree the agent works in. Oxagen does not upload source text, symbols, chunks, code embeddings, imports, or uncommitted branch state into the workspace graph.

Oxagen keeps stable Git-provider metadata for governance and replay: provider and repository identity, refs and commits, pull requests, workflow runs, and changed-file paths. Two richer projections are explicit follow-ups, not launch claims:

- **Canonical repository topology**, derived only from a configured protected or default ref after the provider confirms that ref advanced.
- **A typed evidence ledger** that binds a run to a commit, artifact, test result, or file claim, with provenance and verification, before any graph projection.

Until that evidence ledger exists, Oxagen does not infer or promote run-to-file lineage.

## Sources

`list_connections` lists the source connections that feed the graph. Each connection maps its source record types to your entity types (a mapping step you confirm at setup), then syncs on a cadence: webhook, polling, or manual. You can pause a connection, re-sync it incrementally or in full, or delete it in one of three modes: connection only (keep data), data only (keep config), or full.

## Searching the graph

Two searches work together:

- **Semantic search** embeds a natural-language query and ranks eligible shared knowledge (entities, memories, documents, messages, and provider metadata) by vector similarity. It excludes repository source text, symbols, chunks, and code embeddings.
- **Lexical search** matches substrings in node names and descriptions. Use it when you know what something is called.

From any node you can walk its neighbors one hop at a time, or traverse several hops along named relationship types. Reads support bitemporal queries: "as of" a valid time (what was true in the world) and "as known at" a transaction time (what Oxagen had recorded).

## Semantic relationship inference

Semantic relationship inference is not a launch surface. Oxagen materializes no model-generated relationship through a confidence threshold, and the retired infer, list, suggest, and approve capability family is not available.

A future candidate system must carry attributable producer provenance, explicit authorized approval, durable audit history, and revocation before a proposed relationship can become shared context.

## Citation analytics

`get_citation_stats` summarizes recorded citations and their influence and compliance judgments. Run `oxagen memory citations` for the same data from the terminal. See [Citations](/docs/knowledge/citations).

## Governing the graph's shape

The workspace [schema registry](/docs/knowledge/schema-registry) sets the graph's vocabulary: which entity types, properties, and relationship types it allows.
