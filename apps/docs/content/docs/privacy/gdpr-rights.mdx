## Overview

Oxagen provides self-service controls for the two most operationally significant GDPR rights:

| Right | Article | Scope | Surface |
|---|---|---|---|
| Data portability | Art. 20 | User-level and Org-level | Account → Privacy, Org Settings → Privacy, in-app agent |
| Right to erasure | Art. 17 | User-level and Org-level | Account → Privacy, Org Settings → Privacy, in-app agent |

Both rights can be exercised without contacting support.

Both requests are tied to a person: the handlers reject any call that carries no signed-in user. The REST routes below therefore work with an app session, but not with an `ox_…` API key, because an API key carries org and workspace scope and no user. The MCP server authenticates with API keys only, so the `export_data` and `erase_data` MCP tools are registered but currently reject every call.

## Data export (Article 20)

An export produces a ZIP archive containing:

| File | Contents |
|---|---|
| `user-profile.json` | The requesting user's profile. If this read fails, the whole export fails. |
| `conversations/<id>.json` | One file per conversation, with its messages |
| `api-keys.json` | Key metadata only (name, prefix, created, last used, scopes). Never key material. |
| `audit-log.json` | Security events for the user (user scope) or the org (org scope) |
| `members.json`, `workspaces.json` | Org scope only |

Every file except `user-profile.json` is read independently. If one of those reads fails, it is logged and skipped, and a partial export still ships.

Exports are assembled asynchronously. The request returns immediately with `status: "queued"`. Poll `GET /v1/:org_slug/:workspace_slug/privacy/export/:exportId` as the job moves through `processing` to `ready` (or `failed`). When the export is `ready`, the response includes a `downloadUrl`. The archive is stored as a private object and served only through an authenticated path, never a public URL. A user can poll only their own exports.

### API

```http
POST /v1/:org_slug/:workspace_slug/privacy/export
Content-Type: application/json

{ "scope": "user" }
```

```json
{ "exportId": "…", "status": "queued" }
```

An org-scope export sends `{ "scope": "org", "orgId": "<uuid>" }` and requires the Owner or Admin role on that org.

### Capability

`export_data` (domain `privacy`). The in-app agent can call it without an approval card.

### CLI

CLI support for privacy commands is not yet implemented.

## Account and org erasure (Article 17)

Erasure is requested at two scopes. Any authenticated user may request erasure of their own account (`scope: "user"`). An org-scope request (`scope: "org"`) requires the Owner role; Admin is not enough. In the in-app agent, `erase_data` always pauses for an approval card before it runs.

### What happens at request time

1. The erasure request is recorded with `status: "queued"`. **In the same transaction**, every active session of the requesting user is deleted, so access ends immediately.
2. A `privacy.erasure_requested` (user scope) or `privacy.org_erasure_requested` (org scope) security event is written.
3. A `privacy/erasure.execute` job is dispatched for `scheduledAt`, the end of the grace period.

### What the erasure job does today

For **user scope**, once the grace period has passed, the job:

- anonymises the user's identity row: display name `Deleted User`, email replaced with an `@deleted.invalid` address, avatar removed;
- deletes the user's linked accounts, including OAuth tokens and the password hash;
- deletes the user's personal preferences.

For **org scope**, no data is erased by the job yet.

The job then marks the request `failed` rather than `completed`. This is deliberate. The full cross-store cascade is not implemented, so personal data can remain in these places:

- ClickHouse telemetry rows that store the user's email;
- Neo4j nodes owned by the user (there is no delete-by-owner path yet);
- generated-asset blobs;
- Postgres `created_by` / `updated_by` references.

Oxagen will not tell a data subject that erasure is complete while data remains. A `failed` request is the signal for an operator to follow up.

### Grace period

The default grace period is 30 days (`PRIVACY_ERASURE_GRACE_DAYS=30`). Set it to `0` for immediate erasure in test environments; a missing or unparseable value falls back to 30. The grace period exists to allow cancellation of an accidental request — contact `privacy@oxagen.ai` within the grace period to cancel.

### API

```http
POST /v1/:org_slug/:workspace_slug/privacy/erase
Content-Type: application/json

{ "scope": "user", "confirm": true }
```

```json
{ "requestId": "…", "status": "queued", "effectiveAt": "2026-07-09T…" }
```

`confirm` must be the literal `true`. An org-scope request also sends `orgId`.

### Job event

`privacy/erasure.execute` is an internal Inngest event that drives the job above. Its payload is:

```json
{
  "requestId": "<uuid>",
  "userId": "<userId>",
  "orgId": "<orgId>",
  "scope": "user",
  "scheduledAt": "2026-07-09T..."
}
```

There is no customer-facing webhook subscription for this event.

## Security events

All privacy requests are recorded as immutable security events in the `security.security_events` table:

| Action | Event type |
|---|---|
| Export requested | `privacy.export_requested` |
| User erasure requested | `privacy.erasure_requested` |
| Org erasure requested | `privacy.org_erasure_requested` |

These events appear in the audit log and can be used as evidence in GDPR audit responses.
