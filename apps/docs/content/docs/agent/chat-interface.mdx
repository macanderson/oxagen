The in-app chat composer does more than send text. This page covers the features that shape how a turn is scoped and how its results are shown: pinning a repository and environment to the conversation, slash commands, the generative UI card registry, and the citation strip that grounds an answer in the knowledge graph. Oxagen has no coding runtime. Chat cannot open a sandbox or edit a repository. It can only read what a connected repository reports (CI status, PR diffs, and PR metadata).

## Pinning repo + environment context

A context bar sits directly above the composer. It lets you choose a connected GitHub repository and a workspace environment and **pin** them to the conversation. Once they are pinned, the agent knows which repository and environment you mean on every later turn in that conversation, so you don't repeat "in the billing repo" on every message.

- The repository and environment selections are independent. Pin one, both, or neither.
- Pinning is optional. It matters only for the read-only repository tools (`get_pr`, `get_ci_status`, `get_pr_diff`, …) and the `/pr`, `/diff`, and `/ci` slash commands below. If nothing is pinned and a command needs a repository, the agent asks you to pin one rather than guessing.

## Slash commands

Typing `/` in the composer opens an autocomplete menu of slash commands. A slash command is not a client-side router. The composer sends the literal text (for example, `/ci main`), and the agent, which its system prompt tells about each command, maps it to the right capability. The one exception is `/pin`, which the composer intercepts and handles locally.

| Command | Arguments | What it does |
|---|---|---|
| `/pr` | `<pr-number>` | Shows pull-request stats: comments, checks, and files changed (renders the PR stats card). |
| `/diff` | `<pr-number>` | Shows the git diff (file patches) for a pull request (renders the code diff card). |
| `/ci` | `[ref]` | Shows CI and check status for a branch, commit, or PR head. Defaults to the pinned repository's default branch. |
| `/repos` | none | Lists the GitHub repositories connected to the workspace, so you can pick one to pin. |
| `/pin` | none | Pins the selected repository and environment to this chat (handled locally by the composer, not sent as a message). |

The `/pr`, `/diff`, and `/ci` commands act on whichever repository is [pinned](#pinning-repo--environment-context) to the conversation. If nothing is pinned, the agent asks you to pin one instead of guessing.

## Generative UI cards

Tool results that benefit from a purpose-built view render as cards instead of plain text. The model returns structured output (`generateObject`), and the client maps the component type to a React renderer from a shared card registry. The server never renders a React tree. Cards for the chat features above:

| Card | Shown for |
|---|---|
| Code diff card | `/diff`, `get_pr_diff`, or any tool returning a unified diff. Shows per-file patches with add and remove counts. |
| PR stats card | `/pr` or `get_pr`. Shows comments, review status, checks, and a files-changed summary. |
| CI status card | `/ci` or `get_ci_status`. Shows check-run and commit-status results for a ref. |

These sit alongside the approval and memory-recall cards. See [Tools and capabilities](/docs/agent/tools-and-capabilities) for the tool surface that produces them.

## Graph-grounded citations

When a turn recalls workspace memories to ground its answer, chat shows a **"Grounded in"** citation strip beneath the agent's response. The strip names the knowledge-graph facts that backed the answer.

- Each recalled memory is cited by the knowledge-graph node it is **about**, using the shared `NodeRef` chip: a colour-coded label, a hover or click property popover, and a copyable id. The chip never shows a bare UUID, which matches how the UI cites a node or edge everywhere else.
- Each citation includes a **"View in graph"** link that opens the graph explorer focused on that node (`?focus=<publicId>`), so a cited fact is one click from its live graph context.
- Recall runs alongside the model's turn, best effort. Resolving citations never delays the first streamed token. The strip survives a page refresh because Oxagen stores it as a message content block rather than recomputing it on each render.

An answer that cites a fact links you to the node and edge that produced it.
