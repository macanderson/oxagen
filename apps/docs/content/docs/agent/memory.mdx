## What agent memory is

Agent memory is persistent, queryable knowledge scoped to a workspace, stored by Oxagen's memory engine, **Engram**. Conversation history is a linear sequence of messages. Memories are discrete facts, rules, and observations stored as nodes in the workspace knowledge graph (Neo4j). They carry across runs, across conversations, and across every agent working in the same workspace, including the [CLI](/docs/cli/memory).

Each memory has two independent axes:

- **Class**: the ladder from tentative to settled, **OBSERVATION → RULE → FACT**. A confidence score (0–100) tracks how likely the memory is to be *true* and decays over time. A RULE also carries an enforcement score (1–100) for how strongly it should be followed. Promotion up the ladder records an auditable event, and promotion to FACT needs a person to confirm it.
- **Kind**: the content domain, an open label. Common kinds:

| Kind | Description |
|---|---|
| `routine-change` | A process or convention change the agent should carry forward |
| `constraint` | A hard boundary the agent must respect |
| `bug-root-cause` | Root cause of a known bug or failure pattern |
| `convention-deviation` | A departure from a project convention that has been intentionally accepted |
| `gotcha` | A known trap or non-obvious behavior to watch out for |

## Recalling memories

The agent calls `recall_memory` to query the knowledge graph at the start of a turn or during it. The query is semantic. It finds memories by meaning, not by keyword match.

```
recall_memory({ query: "brand guidelines for external communications" })
```

The result is a list of memory nodes ranked by relevance score. The agent adds them to its response context.

You can ask the agent to recall memories explicitly:

- "What do you know about our pricing structure?"
- "Recall anything relevant about the Spencer account before we start."

## Writing memories

The agent calls `write_memory` to persist a new memory. The agent can propose one during a conversation ("I'll remember that for next time"), or you can ask it to:

- "Remember that we use Stripe for billing and Inngest for background jobs."
- "Add a rule: all agent-generated documents must be reviewed by a human before sending."

Each written memory includes:

- The memory content (text)
- The kind (`routine-change`, `constraint`, `bug-root-cause`, `convention-deviation`, or `gotcha`)
- A weight bucket (`low`, `high`, or `critical`) for how salient the memory is. The `save_memory` capability infers the bucket from free text.
- Graph node attachments (for example, a link to a specific entity in the ontology)

## Viewing and managing memories

**Workspace → Knowledge → Memory** shows every workspace memory. You have the full lifecycle on that page:

- Browse and filter memories by class, kind, confidence, and text
- Create, edit, and delete individual memories
- Promote a memory up the ladder, demote it back down, or change its lifecycle status (`ACTIVE` / `SUPERSEDED` / `RETRACTED` / `ARCHIVED`)
- Dismiss promotion suggestions you don't want to see again
- See which agent or person created each memory, and when
- Attach evidence and review agent-proposed memories before accepting them

Memories are scoped to the workspace. They are not shared across workspaces, and other organizations cannot see them.

## The promotion lifecycle

*Promotion moves a memory up the ladder, and FACT needs a person's confirmation. Demotion is the audited inverse. Dismissal removes a candidate from the queue without changing its class.*

Observations that keep proving useful surface as **promotion candidates**, a queue on the Memory page ranked by citation pressure. For each candidate you can:

- **Promote** it to RULE or FACT. A written rationale is *optional*. The human gate for FACT is the confirmation checkbox, which locks enforcement at 100 and records you as the confirmer. When you want a rationale on record, the promote dialog offers a short list of drafted reasons, built from the memory's lesson and its citation history by a low-cost model. Pick one, or choose "Write my own…".
- **Dismiss** the suggestion. The memory stays active and recallable, but it leaves the candidate queue, and the next-highest-signal observation takes its slot. An Undo toast restores it immediately, and `restore: true` on the capability reverses it later.
- **Demote** a RULE or FACT that no longer deserves its standing (from its detail sheet). Demotion is the audited inverse of promotion. It only moves down. Demoting to OBSERVATION clears enforcement, and leaving FACT clears the human confirmation. The same optional-rationale picker applies.

Oxagen records every promotion and demotion as an auditable event node in the graph, so you can reconstruct a memory's class history.

## Citation analytics

**Workspace → Knowledge → Citations** shows how memories and graph nodes get used. Every time an agent's answer is grounded by a recall or an `@`-mention, Oxagen records a citation with an *influence* level (`DECISIVE` / `CONTRIBUTING` / `CONSIDERED` / `IGNORED`). For rules, the citation also carries a *compliance* outcome (`COMPLIED` / `DISCRETION` / `VIOLATION`). The dashboard aggregates these over a 7, 30, or 90-day window:

- **Most cited**: the memories carrying the most weight.
- **Least useful**: recalled repeatedly but never influential. These are the first candidates to demote or retire.
- **Most violated rules**: where agents break promoted rules. Tighten enforcement or demote the rule.
- **Top cited nodes**: the graph entities agents lean on most.

## Memory in the knowledge graph

Oxagen stores memories as `AgentMemory` nodes in Neo4j, with a vector index for semantic retrieval. Graph edges connect them to other ontology nodes (people, companies, projects, and documents), which gives them relational context beyond text similarity.

A workspace's memories travel with the workspace. If your organization moves to different infrastructure, the graph moves with you. It is not locked to Oxagen's internal storage format.

## Governance

The same IAM model governs memory writes as every other capability. `write_memory` needs at least the `Member` role in the workspace. Viewers cannot write memories.

Every memory write produces an audit record. When the agent writes a memory in delegated context, the record names both the person and the agent.
