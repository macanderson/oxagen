Oxagen governs the agents your organization builds and runs; it does not run
a coding agent of its own. The sandbox layer, subagent fan-out, background
tasks, plan mode, skills authoring, and content-generation tools have been
excised (ADR-043, `docs/adr/ADR-043-runtime-excision.md` in the repository).
What remains is one conversational surface: a governed turn
(`runGovernedTurn`) whose job is to interrogate the **fleet record** and
the **knowledge graph** — what did my agents do, what context did they have,
what did it cost, what is pending approval.

It has no sandbox, no file system, no browser, and no subagents. Every tool
call it makes is a capability contract invoked through the same
`kernel.invoke()` boundary as the REST API and the MCP gateway — IAM-checked,
metered, and audit-logged identically regardless of which surface triggered
it.

The turn loop itself runs on Stella's headless engine, `stella-serve`
(ADR-053). The engine owns the step cap, loop detection, compaction, and
cancellation, but it holds no model key and runs no tool. Every completion and
every tool call it wants comes back to Oxagen as a request, and Oxagen answers
it under governance. There is no in-process fallback: if the engine is
unreachable, the turn fails before anything streams.

The engine sees tool results; it never sees a credential. A denied approval
fails the tool call before `invoke()` runs, and the handler always runs inside
the kernel's tenant scope.

## What the agent can do

The agent tool surface is derived from the contract registry. Any capability
declared with `surfaces: ['agent']` is available as a tool in a chat session,
filtered by:

1. Whether the capability is enabled in the workspace tool policy.
2. Whether the current principal (user or delegated agent) has the required
   grant.

The agent selects tools autonomously based on the user's request. It cannot
call a capability it does not have access to — the IAM check happens before
the handler runs, not inside it.

## Delegated context

When a user is in chat, the agent operates in delegated context. The agent
borrows the user's effective grants for the session. The audit record
captures both: the human principal and the agent acting on their behalf.

This is the "chain of custody" model: an auditor reviewing an audit log can
always trace any agent action back to the human who authorized it, or to the
service identity configured for an automated trigger.

## Tool categories

| Category | Examples |
|---|---|
| Fleet & registry | Look up agent definitions, roles, deployments, and environment bindings |
| Run history | List and inspect past agent runs, traces, and citations |
| Memory | Recall and write memories from the workspace knowledge graph |
| Knowledge | Query the ontology, search the graph, browse nodes and relationships |
| Approvals | Resolve a pending tool-call or MCP-consent approval |
| Billing & budgets | Read spend, usage, and budget policy |
| MCP gateway | List registered external MCP servers and their tools |
| Repository observability | CI status, PR diffs, PR metadata for connected repos (read-only) |

See [Tools and capabilities](/docs/agent/tools-and-capabilities) for the full
list.

## Observability

Every agent turn produces:

- Streamed SSE events: `text` (the response), `tool-call-start` and
  `tool-call-end` (tool calls), `approval-required` (an approval card), and
  `usage`.
- One `agent.agent_tool_calls` row in Postgres per tool invocation (durable
  record).
- One ClickHouse `tool_invocations` row per tool invocation (analytics).
- A `capability.invoke_allowed` or `capability.invoke_denied` security event
  per IAM decision.
- A credit delta event at turn end (credits charged for the turn).

Token usage, tool call latency, and error rates are available in
**Workspace → Activity**.
