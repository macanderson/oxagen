---
title: Plugin governance
description: How a workspace controls which plugin tools its agents can request, where plugin credentials live, and how the audit record and role requirements work.
---

Oxagen plugins add external tools and first-party capabilities that an agent can request. Every plugin install is **workspace-scoped**. A plugin installed in one workspace is not visible to any other workspace, which gives security and compliance teams a narrow control surface.

## Workspace-scoped plugin model

```
Workspace A    → plugins installed here are available only in Workspace A
Workspace B    → independent plugin list; no visibility into Workspace A's plugins
Workspace C    → ...
```

Org Owners and Admins can install plugins from the marketplace into any workspace they belong to. Workspace Owners and Admins can install plugins into their own workspace. Every install, connection, and enable or disable action applies to one workspace.

## Installing plugins

See [Plugin marketplace](/docs/plugins/marketplace) for the full installation guide.

In summary:

1. Open **Marketplace** from the workspace sidebar.
2. Choose a section: **Agent Tools → MCP Servers**, **Agent Tools → Capabilities**, or **Integrations**.
3. Review the plugin's tools, README, and authentication requirements.
4. Click **Install**. The plugin is enabled immediately in this workspace.

An MCP server or integration plugin that needs authentication also needs a connection step. Click **Authenticate** for OAuth, or **Enter API key** for a secret. Its tools stay out of every agent's tool list until the connection is done.

## Enable and disable

One capability, **`set_plugin_enabled`**, turns a plugin on and off. It toggles the `enabled` flag on the plugin listing. For an MCP server or integration plugin, it also creates or deactivates the workspace-level MCP server connection.

A disabled plugin's tools leave every agent's tool list. For an MCP server, disabling also blocks reconnection until you enable it again.

## Credential security

The credential a plugin needs stays in Oxagen, held by the workspace. The agent never sees it. Oxagen encrypts OAuth tokens and API keys at rest with AES-256-GCM. If an OAuth token expires or is revoked, org managers get an in-app notification, and someone must authenticate again before the plugin's tools come back.

## Uninstalling

Go to **Tools → MCP Servers** and uninstall the server from its row. Uninstalling stops every new call to the plugin's tools in this workspace immediately. The audit log keeps existing tool call records that reference the plugin. Oxagen does not delete content the plugin generated (images, documents, and videos).

## The record

Oxagen records plugin governance actions in `security.security_events` (Postgres):

| Event | When it fires |
|---|---|
| `plugin.installed` | Plugin installed into a workspace. |
| `plugin.uninstalled` | Plugin uninstalled from a workspace. |
| `plugin.enabled_changed` | Plugin listing enabled or disabled, or a workspace MCP server connection activated or deactivated (`set_plugin_enabled`). |
| `plugin.credential_set` | A plugin credential stored. |
| `plugin.credential_revoked` | A plugin credential revoked. |
| `plugin.denylist_added` | Reserved name. There is no plugin denylist, so nothing emits it. |
| `plugin.denylist_removed` | Reserved name. There is no plugin denylist, so nothing emits it. |

## Role requirements

| Action | Required role |
|---|---|
| Browse marketplace | Any workspace member |
| Install or uninstall a plugin | Workspace Owner, Workspace Admin, or Org Owner/Admin |
| Connect OAuth or set API key | Org Owner or Org Admin only |
| Add custom MCP server or registry | Workspace Owner or Org Owner/Admin |
| Enable or disable a plugin | Workspace Owner or Org Owner/Admin |

For more information, see the [Plugin marketplace](/docs/plugins/marketplace) and [Workspace plugins](/docs/plugins/workspace-plugins) guides.
