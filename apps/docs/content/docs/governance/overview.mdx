## Where you are

People across your organization already use AI tools and agents. Nobody can say what data they share, which models they call, or what they do on the organization's behalf. Procurement, legal, and security are asked to write rules for tools they cannot see.

Oxagen is the agent control plane for that work. Every governed action passes through the same `invoke()` boundary, whether a person takes it in the app, an agent takes it on a schedule, or an MCP client in a developer's IDE calls it. When a task needs a capability, the agent asks. A rule answers: allowed, denied, or routed to a person. A denied action does not run, and the record keeps every answer.

## Three scopes

Governance in Oxagen has three scopes:

```text
Organization → governance rails, billing, global policies
   └── Workspace → operational units where agents work
          └── Principal → human, agent, or service account
```

**The organization** is the customer entity. It owns billing and the member roster, and it sets the outer bounds for every workspace. The IAM resolver has an org-enforced policy tier that workspaces cannot override, but that tier is not live today. See [RBAC and roles](/docs/governance/rbac).

**Workspaces** are operational units, one per team, project, or environment. Each workspace has its own member roster, model defaults, and plugin installs. A workspace can narrow what the organization allows and never widen it.

**Principals** are people, agents, and Oxagen API keys. The same role and grant model governs all three, so an agent's grants are as visible and auditable as a person's.

## What every action passes through

Every capability call, from the app, the REST API, the MCP server, or an agent run, enters the same `invoke()` kernel. The checks run in this order, and the first one that refuses ends the call before the handler runs:

<Mermaid
  chart={`
flowchart TD
  A["invoke(capability, input)"] --> S{{"Exposed on this surface?"}}
  S -- no --> SD["surface_denied"]
  S -- yes --> V{{"Input matches contract?"}}
  V -- no --> VI["invalid_input"]
  V -- yes --> I{{"IAM decision"}}:::accent
  I -- deny --> D["authz_denied"]
  I -- "check errored" --> D
  I -- pending_approval --> P["Access request recorded,<br/>call refused"]
  I -- allow --> G{{"Credit, budget, entitlement<br/>and decision-rule gates"}}
  G -- refused --> R["insufficient_credits,<br/>budget_exceeded, ..."]
  G -- pass --> H["Handler runs"]
  H --> O{{"Output matches contract?"}}
  O -- no --> IO["invalid_output"]
  O -- yes --> AU["Security event: allow"]
  AU --> M["Governed action metered"]
`}
/>

Three properties of this path matter for a governance review:

- **An IAM check that cannot be evaluated denies.** A database outage or resolver bug during the check fails closed with `authz_denied`. It never lets the call through.
- **A call that needs approval is refused now and recorded.** A `pending_approval` outcome refuses the call and records an access request (`arq_…`). There is no in-app screen for answering these requests yet.
- **Every refusal is recorded.** Each denied branch writes a security event with its error code, so the audit log shows refused calls, not only allowed ones.

## Key governance controls

### Role-based access control

Seven built-in human roles cover most enterprise access patterns. Four are org-scoped (Owner, Admin, Compliance, and Billing), and three are workspace-scoped (Owner, Member, and Viewer). Agents get three roles of their own (Agent Observer, Agent Contributor, and Agent Operator). See [Agent roles](/docs/governance/agent-roles). **Governance → Policies** lists roles and their grants, read-only. There is no custom-role builder yet. See [RBAC and roles](/docs/governance/rbac).

### Plugins

Every plugin install is workspace-scoped. A plugin installed in one workspace is not visible to any other workspace. The credential a plugin needs stays in Oxagen, held by the workspace, and no agent sees it. There is no org-level plugin denylist today. See [Plugin governance](/docs/governance/plugins-governance).

### Model governance

Your subscription plan decides which models are on offer. A workspace Owner or Admin sets the workspace's default text tier and model. There is no per-workspace model allowlist yet, so a default chooses a model but does not forbid others. See [Model governance](/docs/governance/byok-and-models).

### Access reviews

**Organization → Access → Reviews** lists every member with their role and last activity, with **Confirm** and **Revoke** actions. Each action writes an audit event, so the page is also the evidence for a quarterly access review.

## What you cannot do from the app

Some governance controls need your infrastructure administrator:

- Changing the `TENANT_RLS_ENFORCEMENT_ENABLED` environment variable, which controls database-layer RLS enforcement (`true` in production).
- Provisioning the non-superuser database role.

SIEM export is not available. Pull audit events into an external SIEM on a schedule with `query_audit_log`. See [Audit logging](/docs/security/audit-logging).

Contact success@oxagen.sh for infrastructure-level governance changes.
