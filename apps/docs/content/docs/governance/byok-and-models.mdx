## Model access by plan

Oxagen routes all AI inference through the Vercel AI Gateway. No provider API keys are held in the Oxagen codebase or deployment — the gateway handles provider authentication.

Available models depend on your subscription tier:

| Model | Starter | Growth | Scale |
|---|---|---|---|
| Claude Haiku 4.5 | Yes | Yes | Yes |
| Claude Sonnet 4.6 | Yes | Yes | Yes |
| Claude Opus 4.7 | — | Yes | Yes |
| Image generation (gpt-image-1, flux-2-max) | — | Yes | Yes |
| Video generation (veo-3.0) | — | — | Yes |

All model calls are metered in credits at the per-token rate defined in the billing pricing table. See the [full cost table](/docs/enterprise/use-cases#metered-spend) for per-model credit rates.

## Bring your own keys (BYOK)

Organizations on the Scale tier can provide their own model API keys at the workspace level. BYOK keys are used in preference to the Oxagen-managed gateway for any model the key supports.

**Why BYOK matters for enterprise:**

- Use your existing commercial agreements with Anthropic or OpenAI.
- Route inference to your own Azure OpenAI or AWS Bedrock endpoints.
- Apply your organization's data residency requirements to model traffic.
- Maintain your own rate limits and quotas independently of the Oxagen platform.

**To configure BYOK:**

1. Go to **Workspace settings → Model Keys**.
2. Click **Add key**.
3. Select the provider (Anthropic, OpenAI, Azure OpenAI, AWS Bedrock, or a custom endpoint).
4. Paste your API key. The key is encrypted with AES-256-GCM before being stored.
5. Map the key to the model handles you want it to serve.

BYOK keys are stored per workspace. Different workspaces can use different keys — for example, a production workspace can use a dedicated API key with its own usage limits, while a development workspace uses the Oxagen-managed gateway.

**Audit trail:** BYOK key creation, updates, and deletions are recorded as security events.

## Restricting model access per workspace

Workspace administrators can restrict which models are available to agents in their workspace, regardless of what the org subscription tier allows. This is useful for:

- Preventing high-cost models from being used in cost-sensitive workspaces.
- Restricting model access in workspaces that handle sensitive data to only pre-approved models.
- Enforcing consistent model behavior across a team.

Model restrictions are configured at **Workspace settings → Model Keys → Allowed models**. Agents attempting to use a disallowed model receive a capability denied response, which is recorded in the audit log.

## Model governance and org-enforced policies

Org administrators can set enforced policies on model access at **Organization → Access → Policies**. An enforced policy cannot be overridden at the workspace level. For example, an org can enforce that `agent.code.execute` only runs on Haiku (lower cost, lower capability) — workspaces cannot upgrade the model used for code execution without an org Admin changing the policy.

## Model handle stability

Oxagen uses model handles (e.g., `claude-sonnet-4-6`) rather than hard-coded model slugs. Handles are resolved to the current gateway slug at request time via `modelIdOf()`. This insulates your agents from model naming changes in the underlying provider APIs.

If a gateway model slug is updated or renamed, handle resolution is updated centrally — your agents and playbooks continue to work without changes.
