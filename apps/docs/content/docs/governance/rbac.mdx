## Built-in roles

### Org-scoped roles

| Role | Capabilities |
|---|---|
| **Owner** | Everything — including billing, org deletion, and ownership transfer. |
| **Admin** | All operations except destructive org-level actions (delete org, transfer ownership). |
| **Compliance** | Security and privacy policy management; no access to operational surfaces or billing. |
| **Billing** | Billing and subscription management only. No access to operational surfaces or IAM. |

Org roles govern the organization-level surfaces: members, access (IAM), security, billing, and developer settings.

### Workspace-scoped roles

| Role | Capabilities |
|---|---|
| **Owner** | Manage grants within this workspace; workspace settings; full operational access. |
| **Member** | Run agents, resolve approvals, edit memories, configure agent triggers. |
| **Viewer** | Read-only across the workspace. |

Workspace roles are assigned per workspace. A user can be a **Member** in one workspace and a **Viewer** in another within the same organization.

## IAM resolution order

When a principal invokes a capability, the IAM resolver (`packages/oxagen/src/iam/resolve.ts`) decides it. This is the path a live request takes today:

<Mermaid
  chart={`
flowchart TD
  T{"Enterprise org?"} -- "no, human or API key" --> TG["ALLOW<br/>recorded as tier_gate"]
  T -- "yes, or any agent principal" --> R7{"Role grants for<br/>this capability?"}
  R7 -- "any deny" --> D7["DENY"]
  R7 -- "else any require approval" --> P7["PENDING APPROVAL"]
  R7 -- "else allow" --> A7["ALLOW"]
  R7 -- none --> R75{"System org Owner role?"}
  R75 -- yes --> A75["ALLOW"]
  R75 -- no --> R8["Contract defaultEffect"]
`}
/>

What the chart shows and leaves out:

- **The resolver runs for Enterprise organizations.** On Free, Build, and Scale, a human or API-key call is allowed at the IAM layer without consulting grants, and the audit record names `tier_gate` as the deciding rule. Surfaces that must stay Owner- or Admin-only on those tiers carry their own checks (see [Gate functions](#gate-functions)). Agent principals skip the tier gate and are resolved on every plan.
- **An API key acts as the user who created it.** If that user cannot be resolved in the org, the call is denied outright rather than falling through to the contract default.
- **Across roles, deny wins.** A principal in several roles with conflicting grants for one capability gets deny over require-approval over allow. A role grant is decided on its effect alone; conditions such as time windows or IP ranges are not evaluated.
- **Owner is a floor, not an override.** The Owner rule applies only to the system-provisioned org Owner role (`isSystemDefault=true`), and only when no role grant decided. An explicit deny on one of the principal's roles still binds an Owner; a user-created role named "Owner" gets nothing from this rule.
- **The last step is per capability.** Most contracts declare `defaultEffect: "deny"`; some declare `allow` or `require_approval`.
- **Direct grants and org policies are not live.** The resolver still contains rules for workspace grants, org-enforced policies and org grants (rules 1–6), but the tables behind them were removed, so they decide nothing on a live request. The one exception is internal: when the IAM tables are missing or an API key's creator cannot be resolved, the resolver is handed a synthetic org-enforced deny so the call fails closed.

The resolver returns a structured trace alongside the decision. The trace is stored in the audit record and is viewable in **Organization → Security → Audit** for every `capability.invoke_denied` event.

## Capability domains

Capabilities are organized into domains. Role grants are listed by domain:

| Domain | Example capabilities |
|---|---|
| `agent.*` | Define, deploy, and govern agents; recall and write memory; resolve approvals |
| `chat.*` | Send messages, manage conversations |
| `knowledge.*` | Manage graph, sources, memories |
| `billing.*` | Purchase credits, change subscription |
| `org.*` | Manage members, roles, and org settings |
| `workspace.*` | Create workspaces, manage workspace settings |
| `plugin.*` | Install, enable, and govern plugins |

## Agents as principals

Every agent configuration is also a principal with its own grant matrix. An agent run is resolved against two principals at once — the agent's own, and the authenticated human who started the run — and the more restrictive outcome wins:

<Mermaid
  chart={`
flowchart LR
  C["Agent calls a capability"] --> AG["Resolve the agent principal<br/>(rules 1–8)"]
  C --> HU["Resolve the initiating human<br/>(rules 1–8)"]
  AG --> M{"Merge: deny beats<br/>pending approval beats allow"}
  HU --> M
  M --> OUT["Effective outcome"]
`}
/>

The human side is the user who started this run, never the agent's creator — otherwise anyone able to trigger an agent would borrow its creator's access. A run with no initiating user resolves the human side as a principal with no roles and no grants, which can only narrow the result. A subagent is further narrowed by its parent run's scope. Both principals are recorded in the audit event.

Agents get their own roles, separate from the human ones above — three built-in postures, intersected with the agent's own configuration, and bounded by a delegation ceiling so an agent can never outgrow the person it acts for. See [Agent roles](/docs/governance/agent-roles).

This is what makes AI automation auditable: every action is attributable to either a human chain of custody or a configured service identity.

## Seeing and changing access

### Roles and grants

**Governance → Policies** lists every role in the org and the capability grants each one carries. The list is read-only: there is no in-app editor for roles, custom roles, or grants yet, and changes are made by provisioning. A member's org role is changed from **Organization → Members**.

### Approval requests

When the resolver returns `require approval`, the call is refused with `pending_approval` and the kernel records an access request (`arq_…`) naming the principal and capability. There is no in-app screen for approving these requests yet.

### Access reviews

**Organization → Access → Reviews** lists every member with their role and last activity. **Confirm** records `access.member_access_confirmed`; **Revoke** removes the member and records `org.member_removed` and `access.review_completed`. Use it as the evidence for a quarterly access review.

## Gate functions

`apps/app` exposes five app-layer guard functions for sensitive server paths. These are **not** part of the `@oxagen/iam` kernel — they query `org_users.role` directly and bypass the full IAM resolver chain. Each takes `(orgId: string, userId: string)` and calls `notFound()` on failure (404, not 403 — to avoid existence leaks).

- `assertOrgMember(orgId, userId)` — confirms the principal is a member of the org.
- `assertBillingManager(orgId, userId)` — confirms the principal holds Owner, Admin, or Billing role.
- `assertMcpManager(orgId, userId)` — confirms the principal holds Owner or Admin role for plugin governance.
- `assertWorkspaceMember(workspaceId, userId)` — confirms the principal is a member of the given workspace.
- `assertSecurityManager(orgId, userId)` — confirms the principal holds Owner or Admin role for audit evidence export.
