---
title: Permissions
description: Write rules that allow an external MCP tool, deny it, or ask a person to confirm before it runs.
---

Permission rules decide what an external MCP tool may do, without any change to the MCP server itself. The rules live in the same settings files as the server definitions and match tool names with glob patterns.

## Three answers

A rule gives every tool call one of three answers:

| Policy | Behavior |
|--------|----------|
| `allow` | The tool runs without asking anyone |
| `deny` | The tool is withheld: the model never sees it and it never runs |
| `ask` | The person running the turn confirms before the tool runs (default) |

## Configuration

```json
{
  "permissions": {
    "defaultMcpPolicy": "ask",
    "mcpServers": {
      "github": {
        "defaultPolicy": "allow",
        "deny": ["delete_repository", "delete_branch"]
      },
      "internal-api": {
        "allow": ["query_*", "get_*", "list_*"],
        "deny": ["delete_*", "drop_*", "truncate_*"]
      },
      "filesystem": {
        "defaultPolicy": "allow"
      }
    }
  }
}
```

## Evaluation order

The runtime checks rules in this order, and the first match wins:

1. **Per-server deny rules**: a tool that matches any deny pattern is denied
2. **Per-server allow rules**: a tool that matches any allow pattern is allowed
3. **Per-server `defaultPolicy`**: applies when no specific rule matches
4. **Global `defaultMcpPolicy`**: the fallback when no server-level config exists

At the same scope, deny wins over allow. So you can write:

```json
{
  "defaultPolicy": "allow",
  "deny": ["delete_*"]
}
```

This allows every tool except those that start with `delete_`.

## Glob patterns

Patterns support wildcards:

| Pattern | Matches |
|---------|---------|
| `*` | Everything (any tool) |
| `delete_*` | Any tool starting with `delete_` |
| `*_dangerous` | Any tool ending with `_dangerous` |
| `get_user` | Exactly `get_user` |
| `admin_*_force` | Tools like `admin_delete_force`, `admin_reset_force` |

## How denied tools work

The model is **never shown a denied tool**. Tool materialization filters denied tools out before the model sees the tool list. As a result:

- The model cannot call a denied tool
- No consent card appears for a denied tool
- A denied tool takes no context window space
- The person running the turn never sees the tool in the chat interface

## Scope precedence for permissions

When the same server has permission rules in more than one scope:

- `deny` and `allow` lists **append** across scopes (every rule applies)
- `defaultPolicy` follows the standard override order: local > project > user

Example with two scopes:

```json
// .oxagen/settings.json (project)
{
  "permissions": {
    "mcpServers": {
      "github": {
        "defaultPolicy": "allow",
        "deny": ["delete_repository"]
      }
    }
  }
}
```

```json
// .oxagen/settings.local.json (local)
{
  "permissions": {
    "mcpServers": {
      "github": {
        "deny": ["force_push"]
      }
    }
  }
}
```

Effective result: `defaultPolicy: "allow"`, deny: `["delete_repository", "force_push"]`.

## Tool visibility

Separate from permissions, **tool visibility** decides which tools the model sees at all, including tools a permission rule would allow:

```json
{
  "toolVisibility": {
    "github": {
      "include": ["create_pull_request", "list_issues", "get_file_contents"]
    },
    "noisy-server": {
      "exclude": ["internal_*", "debug_*"]
    }
  }
}
```

| Field | Behavior |
|-------|----------|
| `include` | Only these tools are shown (allowlist). Glob patterns. |
| `exclude` | These tools are hidden (denylist). Applied after include. Glob patterns. |

If a server exposes 40 tools and you need 3, use `include` to keep the model's context focused.

## Interaction with platform IAM

When file-based permissions and platform IAM policies both apply (for example, on the platform runtime), the stricter answer wins:

- File-based config says `allow` and platform IAM says `deny` → denied
- File-based config says `deny` → denied, whatever platform IAM says
- File-based config says `ask` and platform IAM says `allow` → ask

File-based permissions are the developer's control. Platform IAM is the org admin's control. Each one is enforced on its own.
