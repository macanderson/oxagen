title: External MCP servers

Oxagen connects **outbound** to the external MCP servers registered in a workspace. The agent can request their tools alongside built-in capabilities, and a rule answers each request. This is the inverse of [connecting](/docs/mcp/connecting), which covers MCP clients calling the Oxagen MCP server.

## How it works

You register external MCP servers per workspace. Once a server is registered and authenticated, the agent can request its tools during a turn. IAM policies, consent rules, and permission settings answer each request.

There are two ways to configure external MCP servers:

| Method | Best for | Requires API? |
|--------|----------|---------------|
| [File-based configuration](/docs/mcp/file-config) | Local development, CI/CD, offline work, version-controlled configs | No |
| Platform registration (web app / API) | Teams using the marketplace, OAuth flows, org-level rules | Yes |

Both methods feed tools into the same runtime pipeline. Permissions, telemetry, and audit logging apply the same way however the server was registered.

## Supported transports

| Transport | Status | Notes |
|-----------|--------|-------|
| Streamable HTTP | Fully supported | The current MCP standard. GitHub MCP, Linear, and most hosted servers use it. |
| SSE (Server-Sent Events) | Supported | Older MCP servers still use this transport. |
| WebSocket | Supported | For servers that need a persistent bidirectional connection. |
| stdio | CLI-only (local) | Spawns a local process. Not available in the cloud runtime. |

## Authentication strategies

| Strategy | Use case |
|----------|----------|
| `none` | Public or locally running MCP servers |
| `bearer` | Static API keys or tokens |
| `header` | Any header-based auth (e.g. `X-API-Key`) |
| `oauth` | OAuth 2.1 with PKCE (GitHub MCP, enterprise SSO) |

See [Credentials](/docs/mcp/credentials) for where the credential is held and how it is refreshed.

## Architecture

```
┌──────────────────────────────────────────────────────┐
│  Agent Runtime (materializeTools)                     │
├──────────────┬───────────────────────────────────────┤
│  DB-backed   │  File-based (@oxagen/mcp-config)      │
│  servers     │  servers                              │
│  (mcp.mcp_   │  (.oxagen/settings.json +             │
│   servers)   │   ~/.config/oxagen/settings.json)     │
├──────────────┴───────────────────────────────────────┤
│  Uniform wrapping: IAM gate, telemetry, consent      │
├──────────────────────────────────────────────────────┤
│  Model receives merged tool set                      │
└──────────────────────────────────────────────────────┘
```

Both contributor types produce `ContributedRawTool` entries, and every entry passes the same IAM gate and ClickHouse telemetry before the model sees it. Tools from DB-backed servers also go through first-use consent and approval. Tools from file-based servers skip the consent card: the settings file is the trust anchor, because whoever can write it already controls the process.

## Configure a server

Register a workspace server with `register_mcp_server`, or configure the runtime host's files as [File-based configuration](/docs/mcp/file-config) describes. Files belong to the process that materializes tools. Creating a file on your laptop does not configure the hosted workspace.

The `oxagen mcp` command group is retired. It prints a retirement notice and makes no configuration change.
