---
title: Credentials
description: How external MCP server credentials are stored, resolved, and refreshed.
---

External MCP servers that require authentication need credentials — bearer tokens, API keys, or OAuth tokens. Credentials are held by the platform, scoped to the workspace that registered the server, and never travel in a repository.

## OAuth flow

For servers with `"auth": "oauth"` (like GitHub MCP), the full OAuth 2.1 + PKCE flow runs in the browser:

1. Navigate to **Workspace → Settings → Integrations**
2. Click the server's "Connect" button
3. Complete the OAuth authorization in your browser
4. Tokens are stored encrypted on the platform

## Static tokens and headers

Servers using `bearer` or `header` authentication take their token when the server is registered. The stored record carries the resolved values the runtime sends on each connection:

| Field | Description |
|-------|-------------|
| `accessToken` | The bearer/access token sent in the Authorization header |
| `refreshToken` | OAuth refresh token for automatic renewal |
| `tokenType` | Token type (default: `"Bearer"`) |
| `expiresAt` | ISO timestamp when the access token expires |
| `scopes` | OAuth scopes that were granted |
| `headers` | For header-auth servers: the resolved header key-value pairs |
| `updatedAt` | When this credential was last written |

## Token expiry and refresh

The runtime checks token expiry before connecting to a server:

- **Not expired**: uses the token as-is
- **Expired + has refresh token**: the OAuth refresh watcher (runs every 30 minutes) renews it automatically
- **Expired + no refresh token**: the server is skipped with a warning, and the integration shows as needing re-authentication

## Security considerations

- Credentials are encrypted at rest with AES-256-GCM
- A credential is scoped to the workspace that registered its server — another workspace in the same organization cannot read or use it
- Rotating a token is a re-connect, not an edit: the previous value is replaced, never appended
- Every connection that uses a credential is metered and audited like any other capability invocation
