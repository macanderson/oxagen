title: Capability registry
description: "Every governed action in Oxagen is a typed capability contract: declared once, enforced on every surface, and listed in the governance catalog."
---

A **capability** is the unit of action in Oxagen. The in-process registry declares each one once as a typed contract, and Oxagen exposes it the same way on every surface it opts into: the REST API, the MCP server, the in-app agent, and the CLI. If an action exists, it exists as a capability. Every call runs through the `invoke()` kernel, which applies IAM, metering, and audit. There is no side door.

## What a contract declares

| Field | Meaning |
|---|---|
| Name | Verb-first snake_case identifier, for example `query_audit_log`. See [Capability naming](/docs/api/capabilities#capability-naming). |
| Domain | Functional grouping (billing, graph, agent, …) |
| Surfaces | Where it is mounted: `api`, `mcp`, `agent`, `cli` |
| Sensitivity | `low`, `medium`, `high`, or `destructive`. A destructive capability waits for a person's approval before it runs. |
| IAM grants | Default role grants, each with one effect: allow, deny, or require_approval |
| Entitlement gate | Which plan or entitlement pack unlocks it |
| Input/output specs | Typed field schemas, validated on every call |
| Layers | Declared coverage: schema, api, mcp, unit, e2e, docs, app |

## Browsing the catalog

Org admins browse the full registry in **Organization → Governance → Capabilities**. Filter by domain, surface, sensitivity, or coverage gaps (capabilities missing a declared layer). The same catalog is queryable over the API and MCP. An agent reads it to learn which capabilities it may request.

## Per-capability reference

The governance catalog is the authoritative reference for every capability's surfaces, inputs, and outputs. Oxagen generates it from the live registry, so it stays current. A hand-maintained mirror of the same data lives in the repository at `docs/capabilities/`, one page per capability.
