## How the tool list is built

At the start of each agent turn, the runtime materializes the tool list by:

1. Taking all capabilities that declare `surfaces: ['agent']` (or `['api', 'mcp', 'agent']`).
2. Filtering to capabilities enabled by the workspace tool policy.
3. Filtering to capabilities the current principal has grants for.
4. Adding tools contributed by enabled workspace plugins (external MCP servers whose tools are injected into the workspace toolchain).

The result is a Vercel AI SDK `tools` map passed to `streamText`. The agent selects from this map; it cannot use a tool not in the map.

## Built-in agent tools

### Memory

| Tool | Description |
|---|---|
| `recall_memory` | Query the workspace knowledge graph for relevant memories. Returns scored matches by semantic similarity. |
| `write_memory` | Persist a new memory (kind: `routine-change`, `constraint`, `bug-root-cause`, `convention-deviation`, or `gotcha`) to the workspace knowledge graph, attached to a graph node with a weight bucket (`low`, `high`, or `critical`). |

Memories persist across sessions and are visible in **Workspace → Knowledge → Memories**.

### Subagents

| Tool | Description |
|---|---|
| `dispatch_subagent` | Dispatch one or more subagents in parallel. Each subagent runs a scoped capability and returns its result to the parent. Long-running subagents run as durable Inngest jobs. `riskLevel: medium` — requires user approval before the fanout is created. Maximum 100 tasks per dispatch call. |
| `aggregate_subagents` | Collect the results of an earlier `dispatch_subagent` fanout into one payload. |

### Code execution

| Tool | Description |
|---|---|
| `execute_code` | Execute Node 20, Python 3.12, or shell code in a hardened sandbox. Streams stdout/stderr back to the chat. `riskLevel: high` — requires user approval by default. |

See [Code execution](/docs/platform/agent/code-execution) for full details on the sandbox environment.

### Deterministic coding tools

Every coding-agent turn — the CLI, the in-app [Code mode](/docs/platform/agent/chat-interface#code-mode) sandbox, an API-triggered agent run, or the MCP sandbox agent — also gets a fixed set of **structured, deterministic tools**.

Without them, an agent doing a mechanical chore — run the tests, typecheck, read a diff, check repo health — shells out and reads the raw scrollback. These tools do the same work with **zero model calls**: a plain function works out the scope, a shell command runs, and a parser squeezes the result into a small typed object before the model sees anything. The agent then spends its context on the handful of failures that matter instead of a 500-line reporter dump it would have to re-read for structure.

Four of them are **engine-internal**: unlike the capability-backed tools elsewhere on this page, they have no REST route and no standalone MCP tool. They live only in the coding agent's tool map (`buildWorkspaceTools` in `packages/agent-engine/src/tools.ts`), alongside the primitive `read_file` / `bash` / `code_graph` tools, so they behave identically on every surface that runs the turn loop.

The fifth, `debug_execution`, is a full capability with its own API route and MCP tool, so you can also call it directly, outside a turn.

| Tool | Surface | Purpose |
|---|---|---|
| `test_unit_run` | Agent turn only | Runs vitest over only the sibling and importing tests implicated by a set of changed files (or an explicit `scope.package` / `scope.files`), and returns a typed pass/fail summary — counts, duration, and the first failing assertions with file:line — instead of the reporter's raw output. It never runs the whole repo: an empty selection, or `scope.all`, returns a hint rather than sweeping every test. |
| `build_package_run` | Agent turn only | Typechecks (default `mode: "typecheck"`) or builds a package or file scope, and returns deduplicated, file-grouped compiler errors as a typed list instead of raw `tsc` output. |
| `git_diff_summarize` | Agent turn only | Summarizes the working diff per file — change type, added and removed line counts, and which enclosing symbols were touched (read straight from git's hunk headers, no AST). Cheap orientation before reading the actual patch. |
| `workspace_health_check` | Agent turn only | One compact snapshot of repo state: git branch, dirty-file count, and ahead/behind against upstream (always cheap), plus optional typecheck and lint summaries capped to a small sample. |
| `debug_execution` | Full capability (API, MCP, agent) | Explains why an agent execution failed, as a structured failure frame: the failing step, the error class, the top parsed stack frames, related trace spans, and suspect files ranked deterministically. Set `summarize: true` to add exactly one LLM call for a root-cause diagnosis; every other field is produced without a model. |

The tools share a few argument conventions, so the model learns them once. `verbosity` (`minimal` by default, or `standard` or `verbose`) caps how much detail comes back. An optional numeric `limit` bounds list length directly. Repo-scoped tools take a `scope` that is exactly one of `{ package }`, `{ files }`, or `{ all }`. Tool names follow the same verb-first snake_case standard as every other capability — see [Capability naming](/docs/platform/api/capabilities#capability-naming).

### Planning

| Tool | Description |
|---|---|
| `create_plan` | Enter plan mode. The agent proposes a structured plan before executing any side-effectful tools. |
| `approve_plan` | Approve the proposed plan. The agent proceeds to execute. |

### Skills

| Tool | Description |
|---|---|
| `list_agent_skills` | List available skills (built-in filesystem skills + workspace prompt templates). |
| `load_skill` | Load a specific skill into the agent's context for the current turn. |

Skills are file-based knowledge artifacts (canonical `skill.toml` bundles) that give the agent specialized domain knowledge or instructions. Workspace administrators can define custom skills via **Workspace → Knowledge** prompt templates.

### Background tasks

| Tool | Description |
|---|---|
| `start_background_task` | Start a long-running Inngest job. Returns a task ID immediately. The task runs asynchronously. |
| `get_background_task` | Poll the status of a background task. |
| `cancel_background_task` | Cancel a running background task. |

Background tasks appear in **Workspace → Activity → Runs** with live status updates.

### Approvals

| Tool | Description |
|---|---|
| `resolve_approval` | Approve or deny a pending approval request (used programmatically; in the app UI, approval cards render inline in chat). |

### MCP server management

| Tool | Description |
|---|---|

| `list_agent_tools` | List all tools available in the current session (built-in + plugin tools). |

## Plugin tools

When a workspace enables an external MCP server plugin, that server's tools are injected into the workspace toolchain. Plugin tools appear in the agent's tool list alongside built-in tools. They are governed by the same IAM and audit infrastructure — calling a plugin tool produces the same audit record as calling a built-in tool.

Plugin tool names are namespaced by the plugin's server ID to prevent collisions.

## Tool permissions and risk levels

Every tool has a `riskLevel` field: `low`, `medium`, or `high`.

- **Low:** No approval required by default.
- **Medium:** May require approval depending on workspace policy.
- **High:** Requires explicit user approval before execution (stream pauses; approval card rendered).

`execute_code` is the primary high-risk tool. The workspace tool policy can customize risk thresholds — see **Workspace → Settings → General → Tool policy**.

Default-deny applies to high-risk tools. A workspace that has never configured a tool policy has code execution disabled by default.
