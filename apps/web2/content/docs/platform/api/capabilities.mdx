## The contract model

Every capability is declared once, in the platform contract registry. A declaration says:

- The capability's `name` (for example, `execute_code`)
- Its input and output schemas (Zod)
- Which surfaces it is exposed on: `api`, `mcp`, and/or `agent`
- Its risk level, and whether it needs approval before it runs
- Its default IAM roles and effects

The registry is the single source of truth. Every API route and every MCP tool reads from it, so a capability behaves the same way on every surface it declares. Parity is structural — nobody keeps the surfaces in sync by hand.

`pnpm check:manifest` compares the registry against the routes and tools that exist and reports any gap as a warning.

## Capability naming

A capability name is **verb first, snake_case**: an imperative verb, then the
thing it acts on, joined by underscores. Two or three words is the norm; a
fourth appears only when it is the only way to keep the name unique.

| Shape | Examples |
|---|---|
| `verb_noun` | `list_conversations`, `execute_code`, `upload_asset` |
| `verb_noun_qualifier` | `list_agent_tools`, `cancel_background_task`, `set_plugin_secret` |

Names are globally unique across the registry, and a capability's name is the
same string everywhere — REST route dispatch, MCP tool name, model-facing tool
name, IAM grants, audit records, and metering. There is no separate
model-facing spelling. The agent engine's primitive tools (`read_file`,
`bash`, `code_graph`, …) already read as verb-first names and keep them.

**Names are stable, and there is no alias layer.** If a capability is ever
renamed, the old name stops resolving — the registry does not carry a
compatibility alias, so a rename is a breaking change and ships in a new API
version. Pin your integration to the names in the table below, and read the
release notes before upgrading across a version boundary.

## REST route convention

Capability routes live under `/v1/{orgSlug}/{workspaceSlug}/`, and the path is chosen per capability rather than derived from the name. For example, `list_agent_tools` is mounted at `/v1/{orgSlug}/{workspaceSlug}/agent/tools` and `revoke_api_key` at `/v1/{orgSlug}/{workspaceSlug}/api-keys/revoke`.

Two rules hold everywhere:

- **The org and workspace slug segments are required on every capability route.** Use the slugs that your API key is scoped to.
- **Most capability routes are `POST`,** including ones that only read. The request body is the capability's input, so even a list call sends a JSON body (`{}` when there is nothing to pass).

Run `pnpm check:manifest --json` in the monorepo to print the full route/tool parity table. There is no runtime `/v1/capabilities` endpoint.

## Parity caveat

These flows only exist in the app UI. They have no contract, so you cannot reach them from the API or MCP:

- In-stream plan approval. It needs the chat UI's live stream — call `approve_plan` afterwards instead.
- The Stripe Customer Portal redirect. For programmatic upgrades, use `start_subscription_upgrade`.
- OAuth plugin credential flows, which require a browser redirect.

This list is maintained by hand. When a contract lands for one of these flows, it moves into the capability list above.
