Secure code execution sandboxes

Policy-gated execution backends for agent-authored code. A vendor-neutral policy module governs what runs; swappable drivers — Docker (local), Vercel Sandbox, and Modal — handle the actual isolation. Agents never execute code outside this boundary.

internal package agent-runtime / security @oxagen/sandbox @vercel/sandbox 2.0 dockerode

What this is

@oxagen/sandbox is the execution boundary for agent-run code. When an agent produces code that needs to run, it goes through this package — never directly to a shell, a Docker socket, or a cloud function. The policy module decides whether the execution is permitted; the driver handles the actual isolation.

agent code→ policy check→ driver→ docker / vercel / modal→ captured result
⟐

Policy layer

Execution requests pass through policy.ts before reaching any driver. Policy is vendor-neutral — it does not know which backend will run the code.

⇄

Swappable drivers

Docker for local development, Vercel Sandbox for edge/serverless, Modal for heavy compute. Each driver implements the same interface — swap without changing call sites.

◎

Captured results

All drivers return a typed ExecutionResult with stdout, stderr, exit code, and timing — uniform regardless of which backend ran the code.

Usage

import { execute } from "@oxagen/sandbox"

// Run a snippet through the policy + active driver
const result = await execute({
  code:     `print("hello from agent")`,
  language: "python",
  timeout:  10_000,   // ms
})

console.log(result.stdout)   // "hello from agent\n"
console.log(result.exitCode) // 0

The active driver is selected via the SANDBOX_DRIVER env variable (docker | vercel | modal). In local dev, Docker is the default. On Vercel deployments, the Vercel Sandbox driver is used automatically.

Source layout

  • src/policy.ts — execution policy; validates requests before they reach any driver; enforces language allow-list, timeout caps, and resource limits
  • src/docker.ts — Docker driver; uses dockerode to spin up a container, write the code via tar-stream, execute, and capture output
  • src/vercel.ts — Vercel Sandbox driver; thin wrapper over @vercel/sandbox 2.0
  • src/modal.ts — Modal driver; routes to Modal compute for GPU-heavy or long-running execution
  • src/images.ts — Docker image registry; maps language to the appropriate base image
  • src/types.ts — ExecutionRequest, ExecutionResult, and the SandboxDriver interface all drivers must implement
  • src/index.ts — execute() entry point; selects driver from config and routes the request

FAQ & gotchas

▸ What does the policy module actually check?

Before any driver executes code, policy.ts validates the ExecutionRequest against a set of rules: the language must be on the allow-list, the timeout must not exceed the per-tier cap, and the code size must be within limits. The policy is the only place these rules live — drivers are not responsible for enforcement. This means you can swap drivers without weakening the security posture.

▸ How does the driver model work — Docker vs Vercel Sandbox vs Modal?

All three drivers implement the SandboxDriver interface from src/types.ts. The active driver is selected at startup from the SANDBOX_DRIVER env variable. Docker is the default in local development — it requires Docker Desktop to be running. The Vercel Sandbox driver is the production default on Vercel deployments because it does not require a persistent container daemon. Modal is available for workloads that need GPU access or longer runtimes than Vercel Sandbox allows. Switching drivers is a config change, not a code change.

▸ Can agents call execute() directly?

Agents call through @oxagen/agent, which owns the tool definitions. @oxagen/agent calls @oxagen/sandbox internally. Agents do not import from @oxagen/sandbox directly — keeping the boundary in the agent package means the sandbox interface stays stable and execution telemetry is instrumented in one place.
