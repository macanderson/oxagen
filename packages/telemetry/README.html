What this is

⊞ Instrument everything

This package is the implementation of Oxagen's core observability mandate: every agent, LLM, and tool call records token usage + execution time + surface origin. No AI boundary crosses the platform without emitting an event here. This is how billing is metered, how performance is tracked, and how costs are attributed per workspace and surface.

@oxagen/telemetry is the ClickHouse layer of Oxagen's four-store data model. It exports a ClickHouse client factory, a schema migration runner, and typed event-insert helpers. The package is intentionally write-heavy and read-light — rows are inserted at high frequency and queried in bulk for analytics and billing aggregation, never point-looked-up by primary key.

Store boundary

⟁ What belongs in ClickHouse

This store owns append-only runtime events — data that is written once and never updated. If the question is "what happened, when, and how much did it cost?", the data belongs here. ClickHouse is optimised for this shape; Postgres is not.

Belongs here

  • LLM invocation events (tokens, model, latency, cost)
  • Tool call execution events (tool name, duration, surface)
  • Agent step completion events
  • HTTP request logs and error events
  • Structured traces and spans
  • Token usage for billing metering
  • Historical performance and runtime telemetry

Must never go here

  • Transactional state (user rows, billing records, configs) → @oxagen/database (Postgres)
  • Graph relationships or entity topology → @oxagen/ontology (Neo4j)
  • Data that needs to be updated in-place → use Postgres
  • Binary file content → @oxagen/storage

Events are immutable by definition. If you find yourself wanting to UPDATE a row in ClickHouse, the data model is wrong — that datum should live in Postgres instead.

Usage

Record an LLM invocation event. The three required dimensions — tokens, execution time, and surface origin — must always be present. Additional fields are additive.

import { recordEvent } from "@oxagen/telemetry/client"

// Record a completed LLM call with the three required dimensions
await recordEvent({
  type:              "llm.invoke",
  // dimension 1 — token usage
  promptTokens:      1240,
  completionTokens:  382,
  model:             "claude-sonnet-4-6",
  // dimension 2 — execution time
  durationMs:        1830,
  // dimension 3 — surface origin
  surface:           "in-app",   // "in-app" | "api" | "mcp"
  // context identifiers
  orgId:             orgId,
  workspaceId:       workspaceId,
  traceId:           traceId,
})

The recordEvent call is fire-and-forget in hot paths — it buffers and flushes in the background. In test environments it is synchronous and awaitable.

Apply schema.sql and any pending migrations/ delta files to the configured ClickHouse instance.

# Apply schema + pending migrations
pnpm --filter @oxagen/telemetry migrate

# Equivalent direct invocation
tsx src/migrate.ts

The runner is idempotent. Tables and columns that already exist are skipped. Always run this before starting the API or app locally if the ClickHouse schema has changed.

Import the client and event types directly. The root import re-exports everything.

import { recordEvent, queryEvents } from "@oxagen/telemetry/client"
import type { LlmInvokeEvent, ToolCallEvent } from "@oxagen/telemetry"

// Or use the root import for everything at once
import { recordEvent } from "@oxagen/telemetry"

FAQ & conventions

▸ Why append-only? Why not update rows in place?

ClickHouse's storage engine (MergeTree and its variants) is optimised for high-throughput sequential writes and column-oriented analytics. It does not support efficient in-place row updates — mutations are expensive, asynchronous, and discouraged by the engine design.

More importantly, append-only semantics are the right model for events: an LLM call that happened at a given timestamp is a fact. Facts do not change. If the billing amount derived from that fact changes (e.g. due to a pricing correction), that correction is expressed as a compensating event, not a mutation of the original row.

▸ The three required dimensions on every call

Every event emitted through this package must carry exactly three required dimensions:

  • Token usage — promptTokens and completionTokens (for LLM calls) or a cost proxy (for tool calls). This feeds the billing meter.
  • Execution time — durationMs. This is the wall-clock time from invocation to completion. Required for latency analysis and SLA tracking.
  • Surface origin — surface: one of "in-app", "api", or "mcp". This is how usage is attributed to the correct billing dimension and how drift across surfaces is detected.

Omitting any of the three is a type error. The TypeScript types for each event shape enforce their presence at compile time.

▸ Can I query ClickHouse directly for a dashboard?

Bulk analytical queries are the correct use of this store — that is what ClickHouse is for. Use the queryEvents helper from @oxagen/telemetry/client, which applies tenant-scope filtering via the security helpers before returning results. Do not construct raw queries that bypass the security layer.
