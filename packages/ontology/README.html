What this is

@oxagen/ontology is the Neo4j layer of Oxagen's four-store data model. It exports a typed driver session factory, a Cypher migration runner, graph schema constraints, and the TypeScript types that describe nodes and relationships. Every package that needs to traverse or write the knowledge graph depends on this package.

Store boundary

⟁ What belongs in Neo4j

This store owns graph data — structured relationships between entities where the connection itself carries semantic meaning and traversal is a first-class operation. If the question "what is this connected to, and how?" is central, the data belongs here.

Belongs here

  • Ontology type hierarchy and entity taxonomy
  • Typed relationships between entities (owns, depends-on, calls, references)
  • Workflow execution graphs and lineage chains
  • Agent memory nodes and topology
  • Semantic retrieval indices (entity embeddings as node properties)
  • Entity resolution and deduplication edges

Must never go here

  • Analytics or aggregated metrics → @oxagen/telemetry (ClickHouse)
  • Transactional state (users, billing, configs) → @oxagen/database (Postgres)
  • Append-only event streams or logs → @oxagen/telemetry
  • Binary file content → @oxagen/storage

The graph is the deterministic source of truth for entity resolution. When the same real-world concept appears under different names or IDs across integrations, the graph owns the canonical merge node and the edges to all aliases.

Source layout

  • src/client.ts — Neo4j driver factory; returns a typed session with auto-close
  • src/migrate.ts — reads schema.cypher and runs constraint/index creation against the configured Neo4j instance
  • src/schema.cypher — the authoritative graph schema: node labels, uniqueness constraints, and property indices
  • src/types.ts — TypeScript node and relationship types inferred from the Cypher schema
  • src/index.ts — package entry; re-exports the public surface

Usage

Open a session, run a Cypher statement, and let the helper close the session automatically on completion or error.

import { withSession } from "@oxagen/ontology/client"
import type { EntityNode } from "@oxagen/ontology/types"

// withSession opens a Neo4j session, runs the callback, then closes it
const results = await withSession(async (session) => {
  const { records } = await session.run(
    `MATCH (e:Entity {publicId: $id})-[r:RELATES_TO]->(t)
     RETURN e, r, t LIMIT 50`,
    { id: publicId }
  )
  return records.map((rec) => rec.get("t") as EntityNode)
})

Apply the Cypher schema constraints and indices to the Neo4j instance. Run once on initial setup and after any schema.cypher changes.

# Apply schema.cypher constraints and indices
pnpm --filter @oxagen/ontology migrate

# Equivalent direct invocation
tsx src/migrate.ts

The migration runner is idempotent — running it against an already-configured instance is safe. Constraints that already exist are skipped.

Import types for use in graph query results or when authoring new node/relationship definitions.

import { withSession, driver } from "@oxagen/ontology/client"
import type { EntityNode, RelationshipEdge } from "@oxagen/ontology/types"

// Or use the root import for all public exports
import { withSession } from "@oxagen/ontology"

FAQ & conventions

▸ What lives in the graph vs the other stores?

The graph owns relationships and topology. An entity's identity and transactional attributes (name, timestamps, owner) live in Postgres via @oxagen/database. The graph holds edges that say "entity A depends on entity B" or "workflow run X produced artifact Y". Metrics produced by those workflows live in ClickHouse via @oxagen/telemetry.

A practical test: if you need to traverse hops to answer the question, the data lives in Neo4j. If you need ACID guarantees and point lookups by primary key, it lives in Postgres.

▸ Why is the graph the source of truth for entity resolution?

Integrations frequently surface the same real-world concept under different names, IDs, or schemas. The graph stores a canonical merge node for each resolved entity and attaches alias nodes (one per integration identity) as edges. Any query for "what is this thing?" resolves through the graph first, so consumers never need to know which integration coined the original identifier.

This is a hard architectural rule: entity resolution logic must not be duplicated in Postgres or in application code. If two integration records represent the same entity, the merge edge lives here.

▸ How do I add a new node label or relationship type?

Edit src/schema.cypher to add the CREATE CONSTRAINT or CREATE INDEX statements for the new label. Add the corresponding TypeScript type to src/types.ts. Run pnpm migrate locally to verify the migration applies cleanly, then commit both files together — schema and types must stay in sync.
