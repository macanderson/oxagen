Capability handler implementations

The actual business logic behind every contract declared in @oxagen/oxagen. Each handler lives in exactly one place, calls one or more downstream services (database, AI, storage, billing), and is the only implementation of that capability across all surfaces.

internal package Node.js runtime @oxagen/handlers import path packages/handlers

What this is

@oxagen/handlers is the implementation layer that sits beneath the contracts. When the kernel in @oxagen/oxagen resolves a capability and passes IAM, it dispatches to a handler from this package. The handler receives typed, validated input (the Zod schema from the contract) and returns typed output. It may call the database via @oxagen/database, generate AI output via @oxagen/ai, store files via @oxagen/storage, or record billing events via @oxagen/billing — but never all four at once without a good reason.

contract (oxagen)→ handler→ database · ai · storage · billing
⊞

Solve once

Each capability is implemented in exactly one handler file. No parallel implementations, no shadow logic in app server actions or API routes.

⟐

Typed end-to-end

Input and output types flow from the contract's Zod schemas. The handler never widens to any or re-declares a schema that already exists in the kernel.

◎

Instrumented by default

Every handler logs entry/exit via pino and reports execution time to @oxagen/telemetry. No handler ships without at minimum a duration trace.

Install / import

Workspace-internal package. Consuming packages register handlers at startup; individual handlers can also be imported directly by subpath for testing or targeted use.

{
  "dependencies": {
    "@oxagen/handlers": "workspace:*"
  }
}
// Import all handlers (typically at process startup)
import "@oxagen/handlers";

// Or import specific named handlers from the barrel
import { orgCreate, workspaceCreate } from "@oxagen/handlers";
// Each handler is importable by its file name
import { handler as chatSend } from "@oxagen/handlers/chat.message.send";
import { handler as billingUpgrade } from "@oxagen/handlers/billing.subscription.upgrade.start";

// Useful in tests to invoke a handler directly with typed input
const result = await chatSend({
  orgId: "org_123",
  workspaceId: "ws_456",
  message: "Hello",
  userId: "u_abc",
});

▸ Which handlers are stubs and what does that mean?

Several document and brand-kit generators — documents.generate, documents.pdf.create, video.generate, and brandkit.apply — are currently typed, no-throw stubs. They are wired into the contract/handler path (not dead code), accept and validate their typed inputs, and console.log that they were invoked. They return a structurally valid output so callers do not break.

This is an explicit policy choice, not an oversight: the user has confirmed stubs are acceptable for document / media generation during the foundations milestone, subject to three guardrails — typed (no any), no-throw, and wired. Linear tickets OXA-1xxx track each stub to full implementation.

If you need to promote a stub to a full implementation, replace the console.log body with real logic and remove the stub comment. Do not leave the console.log in the final implementation.

Data flow

A capability invocation travels through four layers before reaching a handler. The handler is the deepest layer — it owns the I/O. Nothing above it (kernel, registry, surface adapter) touches the database, AI providers, or storage directly.

surface (app/api/mcp)→ kernel + IAM→ contract validation (Zod)→ handler→ { db · ai · storage · billing }
LayerPackageResponsibility

Validation@oxagen/oxagenParse and validate input against the contract's Zod schema

  • src/org.member.invite.accept.ts — accept a pending membership invitation
  • src/org.member.invite.decline.ts — decline a pending membership invitation

  • src/chat.message.send.ts — send a chat message; invokes the agent runtime via @oxagen/agent

  • src/image.generate.ts — generate an image; calls @oxagen/ai image helper, stores via @oxagen/storage

  • src/video.generate.ts — generate a video (stub)
  • src/brandkit.apply.ts — apply a workspace brand kit to a document (stub)

  • src/index.ts — barrel re-exporting all handlers by name

FAQ & design notes

▸ Why are handlers in their own package rather than inside apps/api?

Three surfaces — the app, the REST API, and the MCP server — need to call the same capability with the same logic. If the implementation lived inside apps/api, the app and MCP would have to call the API over the network (adding latency, a failure boundary, and serialization overhead) or duplicate the logic. A shared @oxagen/handlers package means all three surfaces import the same code and no implementation exists more than once.

▸ How do I add a new handler?

1. Declare the contract in @oxagen/oxagen/src/contracts/ using defineContract.
2. Create src/<capability.id>.ts in this package — import the contract's input/output types, implement the handler function, log entry/exit with pino, emit a duration trace to @oxagen/telemetry.
3. Re-export from src/index.ts.
4. Add a test that calls the handler directly with a valid typed input and asserts on the output shape — never stub or skip assertions.
5. Verify that all three surfaces (app, api, mcp) pick up the new handler at their existing registration points — do not add surface-specific wiring code.

▸ Can a handler call another handler?

Only at the kernel level, not by direct import. If handler A needs to trigger capability B as a side effect, it should call kernel.dispatch(contractB.id, input) so IAM is re-evaluated and telemetry is recorded for B independently. Direct import between handlers creates implicit dependencies that bypass the contract/IAM layer and make the execution trace incomplete.
