File and object storage adapter

The fourth store in the Oxagen data model. A vendor-neutral adapter facade for binary file and object content — today backed by Vercel Blob, swappable without touching consumers. Metadata and reference rows live in Postgres.

What this is

@oxagen/storage is the file and object storage layer of Oxagen's four-store data model. It exports a single adapter facade — StorageClient — that exposes put, get, delete, and list operations regardless of which backing driver is active. Today the driver is @vercel/blob. The driver is the only place that knows about the vendor; the rest of the platform does not.

Store boundary

⟁ What belongs in object storage

This store owns binary file and object content — any data that is read and written as an opaque byte stream, not queried by column. If you are storing something that cannot be expressed as a SQL column value, it belongs here.

Belongs here

  • Uploaded files (documents, images, attachments)
  • Agent-generated output files and exports
  • Report PDFs and rendered artifacts
  • Brand-kit assets (logos, fonts, templates)
  • Any binary blob keyed by a path or token

Must never go here

  • File metadata, owner, size, MIME type → reference row in @oxagen/database (Postgres)
  • Transactional state → @oxagen/database
  • Graph relationships → @oxagen/ontology (Neo4j)
  • Event logs or metrics → @oxagen/telemetry (ClickHouse)

The split is deliberate: the blob store is optimised for byte streaming; Postgres is optimised for structured queries. A file's content is never put in a Postgres bytea column, and a file's metadata (name, uploader, created-at) is never embedded in the blob key alone — it lives in the reference row.

Install

This is a workspace-internal package. Reference it with the workspace protocol. Ensure BLOB_READ_WRITE_TOKEN is set in the environment before calling any storage operation.

# package.json in any consuming app or package
{
  "dependencies": {
    "@oxagen/storage": "workspace:*"
  }
}
# Required environment variable
BLOB_READ_WRITE_TOKEN=vercel_blob_rw_...

Usage

Upload a file through the adapter. After a successful put, write the returned URL and metadata to a reference row in @oxagen/database.

import { storage } from "@oxagen/storage"
import { db } from "@oxagen/database/client"
import { files } from "@oxagen/database/schema"

// Step 1 — upload bytes to blob storage
const result = await storage.put(`uploads/${orgId}/${filename}`, body, {
  contentType: mimeType,
  access: "private",
})

// Step 2 — write the reference row to Postgres
await db.insert(files).values({
  orgId,
  path:        result.pathname,
  url:         result.url,
  size:        result.size,
  contentType: mimeType,
})

Retrieve a file by its blob path. The reference row in Postgres gives you the path and authorization context; the adapter gives you the bytes.

import { storage } from "@oxagen/storage"

// Retrieve a blob by path — returns a ReadableStream or Buffer
const { body, contentType, size } = await storage.get(
  `uploads/${orgId}/${filename}`
)

// Stream it directly in a Route Handler response
return new Response(body, {
  headers: { "Content-Type": contentType }
})

Delete a file and soft-delete its reference row. Always remove both atomically so the Postgres row and the blob stay in sync.

import { storage } from "@oxagen/storage"

// Delete the blob
await storage.delete(`uploads/${orgId}/${filename}`)

// List blobs under a prefix
const { blobs } = await storage.list({ prefix: `uploads/${orgId}/` })
blobs.forEach((b) => console.log(b.pathname, b.size))

FAQ & conventions

▸ Vendor-neutral adapter — why and how to swap the driver

The adapter facade in src/client.ts depends on the StorageDriver interface defined in src/types.ts. Today the only implementation is src/vercel-blob.ts, but any module that satisfies the interface can be dropped in as the active driver — S3, R2, GCS, local disk for testing, etc.

To swap the driver: implement the StorageDriver interface in a new file, update src/client.ts to instantiate it, and adjust the relevant env vars. No consumer changes are required because the facade API does not change.

This exists because the product is designed to run on AWS infrastructure long-term. Vercel Blob is the current default because it is the cheapest option at the current scale, not because it is the strategic choice. Keep all @vercel/blob imports inside src/vercel-blob.ts to ensure the migration path stays clean.

▸ The Postgres reference-row split

Every file stored via this package must have a corresponding row in the files table in @oxagen/database. The reference row carries the structured metadata: owner, organisation, content type, size, timestamps, and access-control policy. The blob store carries only the bytes.

This split enables fast filtered queries over file metadata without reading any bytes, consistent soft-delete semantics (the blob can be expired independently of the reference row), and IAM checks that happen entirely in Postgres before any bytes are transferred.

Never store metadata inside the blob key alone (e.g. encoding the owner in the path as the only record of ownership). The reference row is authoritative.

▸ Access control and signed URLs

Access control decisions happen in Postgres before bytes are served — the IAM check reads the reference row, not the blob. For private files, the adapter returns a short-lived signed URL (or streams via the API) rather than exposing the raw blob URL to clients. Never return a @vercel/blob public URL to an authenticated endpoint without first verifying the caller has read permission on the reference row.
