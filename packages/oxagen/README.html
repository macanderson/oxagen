The capability kernel

Every platform capability is declared once here as a typed Zod contract, then exposed identically across the in-app agent, the REST API, and the MCP server. This is the single source of truth that enforces no drift across surfaces.

What this is

@oxagen/oxagen is the capability kernel of the platform. A "capability" is anything the platform can do — create an organization, send a chat message, fill a form, generate a document. Each capability is declared exactly once as a contract using defineContract, with a Zod input schema, a Zod output schema, and an identity. The registry collects all contracts; the kernel wires them to IAM. Downstream, the API routes, MCP tools, and app handlers each import the same contract objects — they never re-declare intent or re-invent schemas.

Install / import

This is a workspace-internal package. Consuming packages declare it as workspace:* in their package.json — no npm install required.

// in the consuming package's package.json
{
  "dependencies": {
    "@oxagen/oxagen": "workspace:*"
  }
}
import { registry, kernel } from "@oxagen/oxagen";
import { defineContract } from "@oxagen/oxagen/define-contract";
import { contracts } from "@oxagen/oxagen/contracts";
import type { CapabilityContract } from "@oxagen/oxagen/types";
// import a specific contract by subpath
import { orgCreateContract } from "@oxagen/oxagen/contracts/organization";

// or from the contracts barrel
import { orgCreateContract, chatSendContract } from "@oxagen/oxagen/contracts";

Declaring a contract

All capability declarations go through defineContract. The function accepts an id, a Zod input schema, a Zod output schema, and optional IAM metadata. It registers the contract in the global registry at module load time.

import { defineContract } from "@oxagen/oxagen/define-contract";
import { z } from "zod";

export const workspaceCreateContract = defineContract({
  id: "workspace.create",
  description: "Create a new workspace within an organization.",
  input: z.object({
    orgId:  z.string().uuid(),
    name:   z.string().min(1).max(64),
    slug:   z.string().regex(/^[a-z0-9-]+$/),
  }),
  output: z.object({
    workspaceId: z.string().uuid(),
    slug:        z.string(),
    createdAt:   z.string().datetime(),
  }),
  iam: { permission: "workspace:write", scope: "org" },
});

The same workspaceCreateContract object is then imported by the API route handler, the MCP tool definition, and the app server action — no schema is ever written twice.

Source layout

  • src/define-contract.ts — defineContract() factory; registers into the registry side-effect-free
  • src/contracts/ — one file per domain (organization, workspace, chat, documents, billing, …); all call defineContract
  • src/contracts.generated.ts — machine-generated barrel re-exporting every contract; regenerated via pnpm codegen
  • src/registry.ts — in-memory contract registry: getContract(id), listContracts(), validateAll()
  • src/kernel.ts — capability kernel: resolves a contract id → handler ref + IAM enforcement before dispatch
  • src/iam/ — permission matchers, scope guards, and role-to-permission maps shared across surfaces
  • src/types.ts — CapabilityContract, ContractInput<T>, ContractOutput<T>, and other shared TS types
  • src/index.ts — root barrel; re-exports registry, kernel, and types

FAQ & design notes

▸ What is the difference between the registry and the kernel?

The registry is a passive catalog: it knows every declared contract by id and can look them up or validate their schemas. It has no opinion about execution.

The kernel is the execution boundary: given a contract id and a caller context, it resolves the handler reference, enforces IAM (checking the caller's permissions against the contract's iam metadata), and returns a typed dispatch function. The kernel is what prevents an API route from accidentally calling a handler the caller is not permitted to reach.

▸ How does IAM enforcement work?

Each contract optionally declares iam: { permission, scope }. When the kernel resolves a contract, it calls the IAM helper from src/iam/ with the caller's session and the required permission. If the check fails, the kernel throws before the handler is ever invoked. This means IAM is enforced at the contract boundary — not scattered across individual handler implementations.

▸ Why is zod the only external dependency?

@oxagen/oxagen must sit at the very bottom of the dependency graph — every other package imports from it. If it pulled in runtime I/O (a database driver, an HTTP client, the AI SDK), circular dependency risk would be severe and cold-start cost would be paid by every surface. Zod provides the schema and validation layer without any I/O. All I/O lives in the packages above (handlers, agent, billing) which import this package, not the other way around.

▸ When should I add a new contract vs. modifying an existing one?

Add a new contract when the operation is semantically distinct — a new intent with a new id. Modify an existing contract only for additive, backward-compatible changes (adding optional fields). Breaking changes to input/output schemas require a version bump in the contract id (e.g. workspace.create.v2) so existing callers on all three surfaces can migrate at their own pace.
