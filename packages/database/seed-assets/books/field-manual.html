    Engineering Deterministic AI Coding Agents

    The industry is optimizing models when it should be optimizing systems. LLMs are probabilistic inference engines — but everything around them (retrieval, orchestration, tooling, context construction, execution, validation, memory) can be engineered to be far more deterministic. This manual explores how, with published evidence at every step.

    PART 01THE ECONOMICS

    AI Agents Are Not Expensive. Bad Architecture Is.

    The majority of token spend isn't caused by the model. It's caused by poor system design.

    When teams complain that AI coding agents are too expensive to run in production, they almost always blame the model. The per-token price. The reasoning overhead. The context window. But when you actually instrument an agent and trace where tokens go, a different picture emerges: the model is doing exactly what it was asked to do. The system asked it to do far too much.

    Measure where tokens actually go

    Run any popular agent framework against a real repository and log every request. You'll typically find that the dominant cost is not reasoning about the problem — it's reconstructing context the system already had. Re-reading files it read two turns ago. Dumping 400-line stack traces when 6 frames mattered. Carrying full conversation history into every tool call. Exploring the filesystem with ls and cat because nothing indexed the repo up front.

    This is not a hypothesis. It's what the published numbers show. Anthropic's engineering team, describing their production multi-agent research system, reported that agents consume roughly 4× the tokens of a chat interaction, and multi-agent systems roughly 15× — and that on their internal evals, token usage alone explained about 80% of performance variance.3 Read that carefully: the single biggest lever in agent performance was not model choice or clever prompting. It was how many tokens the architecture decided to spend.

    Evidence · Simplicity wins the leaderboard

    The strongest single data point in this entire series: Agentless (Xia et al., UIUC). Instead of an autonomous agent choosing its own actions with tools, Agentless runs a fixed three-phase pipeline — hierarchical localization, patch generation, validation. On SWE-bench Lite it became the top open-source approach of its time at 27.3% solved for $0.34 per issue (later 32.0% at $0.70), while contemporary agent-based systems spent roughly 10× more per issue for comparable or worse results.1 The LLM never decided what to do next. The system decided; the model only filled in the intelligent parts.

    Xia et al., "Agentless: Demystifying LLM-based Software Engineering Agents," FSE 2025

    Context construction vs. reasoning cost

    Split your agent's token bill into two buckets. Reasoning tokens: the model thinking about the actual problem — the diff, the root cause, the design decision. Context-construction tokens: everything spent getting the model to the point where reasoning can begin — file dumps, search results, log spew, retries after the model got lost. In naive architectures, the second bucket dominates, often by an order of magnitude. And here's the punchline: almost everything in the second bucket is computable without a model. Parsing, indexing, slicing, and graph traversal are deterministic operations. They cost microseconds of CPU, run identically every time, and never hallucinate.

    Evidence · Cost must be a first-class metric

    Princeton's "AI Agents That Matter" (Kapoor, Stroebl, Siegel, Nadgir, Narayanan) showed that agent research systematically ignored cost — and that when you evaluate on a joint cost–accuracy Pareto frontier, trivially simple baselines (like retrying a model call) matched or beat elaborate agent architectures on HumanEval at a fraction of the price. Their conclusion: accuracy alone cannot identify progress, and "SOTA" agents are frequently needlessly complex and costly.2

    Kapoor et al., "AI Agents That Matter," TMLR 2025

    "Thinking harder" vs. "needing less thinking"

    The industry's default answer to agent failure is to think harder: bigger models, longer reasoning chains, more retries, more sub-agents. Each of these multiplies token spend and adds a new probabilistic step — a new place for variance to enter. The engineering answer is the opposite: shrink the problem before the model sees it. Every ambiguity you resolve deterministically is reasoning the model no longer has to do, tokens you no longer pay for, and variance you no longer ship to production. Determinism isn't a philosophical preference. It's a cost model.

    Takeaway

    Reduce uncertainty before you invoke intelligence. Every token of context your system constructs deterministically is a token the model doesn't have to burn discovering it probabilistically.

    PART 02DETERMINISTIC RETRIEVAL

    Stop Making Agents Read Your Entire Logs

    Logs are databases. Treating them like prompts is fundamentally inefficient.

    Watch a coding agent debug a failing test and you'll see the same ritual everywhere: cat the log file. grep for "error". tail -n 200. Paste the whole thing into context. Then ask a probabilistic model to do what a parser could have done for free — find the relevant frames. We've turned the most expensive component in the stack into a log-reading intern.

    Signal-to-noise is a system property

    A production stack trace of a Python web request can run hundreds of frames, most of them framework internals — WSGI plumbing, middleware, ORM dispatch. The frames that matter for the bug are usually the handful that touch your code. Every irrelevant frame you send isn't neutral padding; it's an active liability. Chroma's "Context Rot" study evaluated 18 frontier models and found performance degrades as input length grows even on simple tasks — and degrades faster when the context contains distractors that are related-but-irrelevant to the target.7 A raw log is, almost by definition, a distractor-maximizing document: hundreds of lines that look exactly like the one line you need.

    The same result shows up in retrieval research. Cuconasu et al. ("The Power of Noise," SIGIR 2024) demonstrated that adding semantically related but non-answer-bearing documents to an LLM's context sharply degrades accuracy — related noise is worse than irrelevant noise, because the model can't cheaply dismiss it.9 Framework frames in a stack trace are precisely this kind of high-similarity distractor.

    Execution slicing: preprocess, don't prompt

    The deterministic alternative is to treat program output as structured data and slice it before inference:

    • Stack trace reduction — parse the trace, keep frames inside your package roots, collapse framework frames to one-line markers, keep the exception type, message, and the innermost user frame's local variables.
    • Dynamic trace extraction — run the failing test under a tracer (sys.settrace, coverage.py, eBPF, OpenTelemetry) and extract only the execution path that actually ran, with the values that flowed through it.
    • Log windowing — anchor on the failure timestamp/request ID and take a bounded, correlated window, not the file.
    # Instead of handing the model a shell and hoping:
#   grep -rn "error" logs/ | tail -500   ← probabilistic archaeology

result = run_code_with_trace(          # deterministic, runs in ms
    cmd="pytest tests/test_billing.py::test_refund -x",
    package_roots=["app/"],           # slice to code you own
    capture=["exception", "locals", "executed_lines", "sql"],
    max_tokens=1200,                   # hard budget, enforced by code
)
context = result.to_prompt_block()     # 1.2k tokens of pure signal

    The difference is architectural, not cosmetic. grep | cat | tail makes the model the filter — you pay tokens for every candidate line, and the filtering itself is probabilistic. run_code_with_trace() makes code the filter — filtering costs zero tokens, is identical on every run, and is testable like any other software. Bash is a fine escape hatch. It is a terrible primary retrieval engine, because every bash round-trip is another model call carrying the full conversation history with it.

    Evidence · The interface is the bottleneck

    SWE-agent (Yang et al., Princeton) showed that agent performance depends heavily on the agent–computer interface: replacing raw shell interaction with purpose-built commands that return compact, structured views of files and search results significantly improved resolution rates on SWE-bench. The model didn't get smarter — the interface got more deterministic about what reached the context window.14 Anthropic's guidance on tool design for agents makes the same point: tools should return concise, high-signal representations and enforce token-efficient defaults, because agents inherit every inefficiency of their tools.20

    Yang et al., "SWE-agent," NeurIPS 2024 · Anthropic engineering, 2025

    Takeaway

    Every line of log your system filters in code is a line the model never pays to read, never gets distracted by, and never misinterprets. Deterministic preprocessing eliminates model work.

    PART 03DETERMINISTIC RETRIEVAL

    Parse the User Prompt Before the Model Ever Sees It

    Your prompt already contains structured information. Extract it.

    A user prompt to a coding agent is not free text. It's a semi-structured document that happens to be written in English. "The POST /api/v2/refunds endpoint throws DecimalConversionError in billing/processors.py after #4821 merged" contains an API route, an exception class, a file path, and an issue reference — four precise retrieval keys, sitting in plain sight, that most agent stacks throw away by handing the raw string to the model and letting it decide what to search for.

    Deterministic extraction is a solved problem

    Long before you need a language model, thirty lines of parsing gets you:

    • File paths — anything matching path grammar; validate against the actual file tree, fuzzy-match near-misses.
    • Symbols & signatures — CamelCase / snake_case identifiers, module.func() call syntax, function signatures; validate against your symbol index (Part 4).
    • Stack traces — pasted tracebacks have a rigid grammar in every language; parse them fully, don't summarize them.
    • Issue/PR references — #4821, JIRA-123; resolve via API into titles, diffs, linked commits.
    • URLs and API endpoints — route patterns map directly to router definitions in the codebase.
    • Version/config literals — package names, versions, env var names, feature flags.

    Every extracted entity is a verified anchor: it either resolves against your index or it doesn't. That binary check — impossible with a purely generative approach — is where hallucinated file paths and invented function names go to die.

    From entities to a retrieval plan

    The output of parsing isn't decoration; it's an execution plan that runs before inference begins:

    plan = build_retrieval_plan(prompt)
# {
#   anchors:   [File("billing/processors.py"), Symbol("DecimalConversionError"),
#               Route("POST /api/v2/refunds"), Issue(4821)]
#   expand:    graph_neighbors(anchors, hops=1)      ← Part 4
#   tests:     tests_covering(anchors)               ← Part 10
#   schema:    tables_touched(anchors)               ← Part 8
#   budget:    8_000 tokens, ranked by relevance
# }

    Now the model's first call already contains the right file, its direct dependencies, the covering tests, and the issue diff — assembled by code, ranked by graph centrality, cut to budget. Compare this to the standard pattern, where the model spends its first five calls (each carrying growing history) rediscovering what a regex knew at millisecond zero.

    Evidence · Structured localization beats free exploration

    This is exactly the design that let Agentless outperform autonomous agents: its first phase is hierarchical localization — a fixed, structured funnel from repository → files → classes/functions → edit locations — rather than letting the model wander with tools. The paper's ablations show this staged narrowing keeps ground-truth edit locations in the candidate set while shrinking the code the model must read, and it's a major reason the pipeline hit top open-source results at ~1/10th the cost of agent baselines.1 Constrained input, focused attention, fewer irrelevant tokens: the localization step is deterministic scaffolding doing the model's foraging for it.

    Xia et al., "Agentless," FSE 2025

    ◌ Prompt as opaque string

    • Model infers what to look for — probabilistically, per session
    • Search terms may be hallucinated; paths unverified
    • 3–8 exploratory tool calls before real work starts
    • Cost scales with model curiosity

    ● Prompt as structured input

    • Entities extracted by parser — identically, every time
    • Every anchor validated against real indexes
    • Retrieval plan executes before the first model call
    • Cost scales with actual task complexity
    Takeaway

    Treat the prompt as the first document your system parses, not the first thing your model reads. Extraction is free, verifiable, and identical on every run — inference is none of those things.

    PART 04DETERMINISTIC RETRIEVAL

    Why Grep Is the Wrong Retrieval Engine

    Searching isn't understanding. Code has structure — use it.

    Grep answers one question: "which lines contain this string?" But the questions a coding agent actually needs answered are structural: Who calls this function? What implements this interface? What breaks if I change this signature? Where does this value originate? Text search can only approximate those answers through many noisy round-trips. A code graph answers them exactly, in one query.

    Code is already a graph. Stop flattening it.

    Compilers have modeled code as structure for seventy years: ASTs, symbol tables, call graphs, dependency graphs, cross-reference indexes. Your IDE resolves "go to definition" in milliseconds using exactly this machinery — no LLM involved. Yet the default agent loop discards all of it and hands the model a shell, forcing it to reconstruct structural knowledge through string matching:

    # The grep loop (typical agent trace, abbreviated):
grep -rn "process_refund" .        # 47 matches, 31 are tests/comments
cat billing/processors.py           # 800 lines into context
grep -rn "RefundProcessor" .        # which of these are real call sites?
cat api/handlers/refunds.py         # another 600 lines
# ... 6 more calls, ~30k tokens, and it still can't SEE the call graph

# The graph query:
g.callers("process_refund", depth=2)         # exact, ranked, 0 tokens
g.slice(symbol="process_refund", budget=6000) # minimal closed subgraph

    One hundred greps approximate what one graph traversal computes. And the grep version isn't just slower — each round-trip is a model call that re-sends conversation history, injects 80–95% irrelevant lines (each one a distractor, per Part 2's evidence), and gives the model another opportunity to take a wrong turn. The graph version is deterministic: same query, same answer, forever.

    The index stack

    • AST layer (tree-sitter) — language-aware parsing; definitions, references, signatures for ~every mainstream language.
    • Symbol index — every definition and every reference site, bidirectionally linked (what LSP/SCIP already standardize).
    • Dependency graph — imports, package boundaries, build targets.
    • Call graph — who invokes whom, with edge weights from reference counts or runtime traces.
    • Centrality ranking — PageRank over the reference graph tells you which symbols matter most for understanding any region of the code.
    Evidence · Graph-ranked context in production tools

    Aider's repo map is the canonical proof this works at tool scale: it parses the whole repository with tree-sitter into definitions and references, builds a graph where files are nodes and symbol references are edges, then runs a PageRank-style algorithm to select the most-referenced identifiers that fit a fixed token budget (default ~1k tokens for an entire repo). The result: the model receives a compressed structural map of the codebase — key signatures, most-referenced symbols — instead of raw file dumps, which Aider's own benchmarking found materially improves code-editing performance on large repos.12

    AutoCodeRover (Zhang et al., NUS) took the same bet in research: it replaced plain text retrieval with AST-based search APIs (search-class, search-method, search-code-in-file), letting the LLM query program structure instead of strings — and reported substantially improved issue-resolution efficacy on SWE-bench versus text-based navigation.13

    Aider, "Building a better repository map with tree-sitter" · Zhang et al., ISSTA 2024

    Filesystem traversal vs. graph traversal

    The deep reason graphs win is precision-per-token. A filesystem is organized for humans and build tools — by directory, not by meaning. Relevant code for one change is scattered across handlers, models, migrations, and tests. Filesystem traversal forces the agent to page through that scatter linearly. Graph traversal follows edges of actual relationship: a 2-hop neighborhood around a symbol is very close to the minimal sufficient context for editing it. You're not searching a haystack; you're following a wire.

    Takeaway

    Grep ×100 approximates what graph query ×1 computes exactly. Build the graph once, deterministically, and let the model spend its tokens on the change — not on reconstructing the compiler's knowledge by string matching.

    PART 05DETERMINISTIC RETRIEVAL

    Build Semantic Memory Once

    Every session shouldn't rediscover your repository.

    Here's an absurdity we've normalized: an agent spends 40,000 tokens on Monday learning that your payments code lives in billing/, that LedgerEntry is the money-movement primitive, and that notifications go through an outbox pattern. On Tuesday, a new session spends 40,000 tokens learning it again. Your organization is paying inference prices, daily, for knowledge that changes monthly.

    Repositories have natural semantic structure

    Any codebase that has survived contact with production organizes into domains — Payments, Authentication, Billing, Notifications, Infrastructure — whether or not the directory tree admits it. These domains are recoverable automatically: embed every file/module summary, cluster the embeddings, and cross-check clusters against the dependency graph from Part 4. Community-detection algorithms (Louvain, Leiden) over the import graph find the same boundaries from pure structure. Where embedding clusters and graph communities agree, you've found a real architectural boundary. Where they disagree, you've often found the tech debt.

    This mirrors Conway's law in reverse: the code's semantic clusters recover the team and domain boundaries that produced it. Once inferred, each domain gets a compact, versioned dossier — entry points, core types, invariants ("money is integer cents everywhere"), owned tables, covering test suites — generated once, refreshed incrementally on merge, and retrieved deterministically at session start.

    Evidence · Index once, query cheaply forever

    Microsoft Research's GraphRAG demonstrates the economics of amortized semantic indexing: an LLM pass extracts an entity graph from the corpus once, the Leiden algorithm detects semantic communities, and community summaries are pre-generated at index time. At query time, answering corpus-level questions from those summaries won 70–80% of head-to-head comparisons against naive RAG on comprehensiveness and diversity — while using roughly 2–3% of the tokens per query that hierarchical source-text summarization would require, because the expensive understanding was paid for once, up front.10,11 The same trade applies to code: indexing is a fixed cost; per-session rediscovery is a tax you pay forever.

    Edge et al., arXiv:2404.16130 · Microsoft Research, 2024

    What goes in the memory layer

    • Embeddings — file, symbol, and doc-chunk vectors for fuzzy entry ("where do we throttle webhooks?") when the prompt has no hard anchors.
    • Domain dossiers — the 300-token expert briefing per domain a senior engineer would give a new hire.
    • Architectural boundary map — which domains may call which; violations flagged deterministically before the model proposes one.
    • Convention registry — error-handling idioms, naming schemes, "we use repository pattern here" — extracted once, injected only when relevant.

    Crucially, this memory is infrastructure with a freshness contract, not a cache of vibes: it rebuilds incrementally from the merge queue, carries the commit SHA it was derived from, and is invalidated by the same CI that validates your code. That is what separates semantic memory from a stale wiki.

    Takeaway

    Understanding your repository is a build artifact, not a conversation. Compute it once, version it, refresh it incrementally — and let every session start from knowledge instead of archaeology.

    PART 06CONTEXT ENGINEERING

    Your Markdown Files Are Becoming Technical Debt

    Prompt engineering doesn't scale. Structured data does.

    It starts innocently. A rules.md to stop the agent doing something dumb. Then architecture.md. Then vision.md, conventions.md, and — I've seen it in the wild — soul.md. Six months later you have 30,000 tokens of prose loaded into every session, nobody knows which rules are still true, and the agent has started ignoring half of them. You didn't build a knowledge base. You built a second codebase, in a language with no compiler, no tests, and no dead-code detection.

    Prompt bloat is measurable harm, not just cost

    The instinct says instructions are free: worst case, the model skims the irrelevant ones. The research says otherwise. Performance degrades as input grows even when the added material is task-relevant in spirit — Liu et al. showed models reliably lose information positioned in the middle of long contexts,6 and Chroma's 18-model study showed degradation with input length is universal and non-uniform across every frontier model tested.7 Anthropic's own context-engineering guidance is blunt about the mechanism: attention is a finite budget, and every token in context depletes it — so the goal is the smallest set of high-signal tokens that achieves the outcome.19 Your 30k tokens of markdown aren't a safety net. They're attention debt, billed per request.

    The caching economics make it worse

    Prompt caching looks like it rescues the giant-prompt strategy: cache reads cost ~10% of base input price on Anthropic's API (with a 25% premium on writes), cutting cost up to 90% and latency up to 85% for long stable prefixes.16 But caching is prefix-exact: edit one character of an early block and everything after it recomputes at full price (plus the write premium). A pile of frequently-tweaked markdown files concatenated into the prompt is the worst possible shape for this — every doc edit is a cache invalidation event across your whole fleet. Caching rewards exactly what markdown sprawl destroys: small, stable, rigorously ordered context. Cache economics are an argument for structure, not for stuffing.

    ◌ vision.md · rules.md · soul.md

    • Loaded whole, every session, relevant or not
    • No validation — rules silently rot as code evolves
    • Conflicting rules resolved probabilistically by the model
    • Every edit invalidates the prompt cache prefix
    • Grows monotonically; nobody dares delete

    ● Schemas · metadata · capability registry

    • Retrieved selectively — only rules matching the touched domain
    • Machine-checkable: rules reference real symbols, validated in CI
    • Conflicts detected deterministically at build time
    • Stable structured core caches cleanly; variable tail stays small
    • Dead rules detected like dead code

    What replaces the prose

    • JSON Schema / typed config for anything that is actually a constraint: allowed dependencies, naming patterns, review requirements. Constraints in schema form can be enforced by validators, not merely suggested to a model.
    • Tool metadata — capabilities, costs, preconditions declared on tools themselves (the direction MCP standardizes), so capability discovery is a lookup, not a paragraph.
    • Rule objects with scopes — {rule, applies_to: "billing/**", verified_by: "lint:no-float-money", since: "a1b2c3"}. The retrieval layer injects the three rules relevant to this diff, not the three hundred that exist.
    • Generated, not hand-written, docs — the Part 5 dossiers, derived from code, carrying their source SHA.

    Keep markdown for what prose is good at: intent, history, taste. Everything that functions as a rule belongs in a representation that can be validated, scoped, versioned, and selectively retrieved. If a rule can't fail CI, it isn't a rule — it's a hope.

    Takeaway

    Natural-language configuration is configuration without a type system. Move constraints into structured, validated, selectively-retrieved data — and let prose go back to being prose.

    PART 07CONTEXT ENGINEERING

    Context Compression Is More Valuable Than Bigger Models

    Removing irrelevant information beats buying a larger model.

    When an agent underperforms, the industry reflex is to upgrade: bigger model, longer window, more reasoning budget. But the evidence keeps pointing at a cheaper lever. The question that predicts success isn't "how much can the model hold?" — it's "what fraction of what it holds is signal?" That's an information-theory question, and information theory is on the side of the systems engineer.

    The Shannon view of a context window

    Shannon's framework18 gives us the right vocabulary. The task has some intrinsic information requirement — the minimal facts needed to produce the correct patch. Everything else in the window is noise relative to that task, and attention is the finite channel through which signal must pass. Two consequences follow directly. First, mutual information, not volume, is what matters: a 4k-token context whose every line bears on the task carries more usable information than 100k tokens where the answer is diluted 25:1. Second, compression is only safe when it's lossless with respect to the task — which is precisely what deterministic slicing (Parts 2–4) achieves and what generic truncation ("keep the first N lines") does not. A stack-trace parser that keeps your frames and drops framework frames is a task-aware compressor with a provable retention property. head -c is a coin flip.

    The empirical record is unambiguous

    U-curve
    Liu et al.: accuracy collapses for facts mid-context; long-context models included6
    18 / 18
    Chroma: every frontier model tested degrades as input grows, even on trivial tasks7
    −dozens of pts
    NoLiMa: when matches are semantic, not literal, most models fall far below short-context accuracy by 32k8
    Related > random
    Power of Noise: semantically related distractors hurt accuracy most9

    Note what these four results jointly imply for coding agents specifically. A repository dump is long (triggering length degradation), full of near-duplicate distractors (the most harmful noise type), and requires semantic rather than lexical matching to use (the NoLiMa condition, where degradation is steepest). Raw-context agent design sits at the intersection of every known failure mode.

    Counterweight — long-context is improving

    Be honest about the trend: newer models post near-perfect scores on simple needle-in-a-haystack retrieval at extreme lengths, and vendors are attacking positional bias directly. But the improvements are strongest on literal retrieval — the easiest case — while semantic reasoning over long, distractor-dense context remains the weak point, which is exactly the regime coding agents live in. And even a model immune to context rot still bills you for every irrelevant token. Compression wins on cost even where it someday stops winning on accuracy.

    Compression as an engineering discipline

    • Retrieval precision over recall-by-default — start from verified anchors (Part 3) and expand along graph edges (Part 4) instead of dumping candidates.
    • Representation changes — signatures instead of bodies (a repo map is a ~100:1 compressor12), schemas instead of migrations, sliced traces instead of logs.
    • Budgets enforced in code — every context assembler takes a token budget and ranks content to fit it; over-budget is a build failure, not a vibe.
    • Measure context utilization — what fraction of provided tokens does the final patch actually depend on? Sub-10% is common in naive stacks; it is the clearest single indicator of wasted spend (Part 13).
    Takeaway

    A bigger model reads your noise more expensively. A better system removes the noise. Between the two, only one compounds: every point of retrieval precision you engineer benefits every model you will ever run.

    PART 08CONTEXT ENGINEERING

    Schema Rot Is the Silent Killer of AI Coding Agents

    Models don't invent duplicate database columns because they're bad. They invent them because they never saw the existing ones.

    Every team running coding agents against a real product eventually meets the same bug report: the agent added a user_email column to a table that already had email. Or wrote a migration duplicating an index. Or built a query against a column renamed two quarters ago. The postmortem instinct is "the model hallucinated." The engineering truth is harsher: the model was never shown the schema. It did exactly what any engineer would do with zero visibility into the database — it guessed.

    Why schema is the worst-served context type

    Schema knowledge is uniquely hostile to text retrieval. The live truth isn't in any one file — it's the fold of an ordered migration history: 400 migration files where the current shape of orders is the sum of 23 of them, interleaved with everything else. Grep for the table name and you get all 23 plus every query that touches it — maximum-similarity distractors, the exact noise profile Part 7 showed is most damaging. ORM models drift from the database. Column semantics ("amount is integer cents, never float") live in tribal memory. No amount of "read the migrations folder" fixes this, because the information the model needs is a computed state, not a document.

    Schema becomes another graph node

    The deterministic fix is to treat the schema like Part 4 treats code — as structure to be indexed, not text to be searched:

    • Schema index — introspect the live database (or replay migrations) into a canonical, versioned snapshot: tables, columns, types, constraints, indexes, foreign keys. This is a solved problem; every ORM ships the machinery.
    • Migration graph — each column carries its lineage: created in 0042, renamed in 0187, backfilled in 0201. "Why is this nullable?" becomes a graph query with commit-linked answers.
    • Code↔schema edges — static analysis of ORM models and query sites links LedgerEntry ↔ ledger_entries ↔ the 14 call sites that write it. Now "what breaks if I drop this column?" is a traversal, not a prayer.
    • Domain mapping — tables attach to the Part 5 domains, so a billing task automatically retrieves billing tables and only billing tables.
    ctx = schema.slice_for(anchors=["RefundProcessor"])
# orders(id, user_id→users.id, amount_cents INT NOT NULL, status ENUM,...)
# refunds(id, order_id→orders.id, amount_cents INT, reason TEXT,...)
# lineage: refunds.amount_cents renamed from amount in 0187 (PR #3122)
# invariant: money columns are integer cents (lint: no-float-money)
# ~600 tokens. Verified against production at SHA 9f31c2.

    Six hundred tokens of verified schema beats sixty thousand tokens of migration files. And because the slice is generated from the live database, the duplicate-column failure becomes structurally impossible to miss: the deterministic layer can literally diff the model's proposed migration against the index and reject collisions before a human ever reviews them. That's the pattern of this whole series in miniature — don't ask the model to remember reality; show it reality, then validate its output against reality.

    Evidence · Grounding beats recall

    The general principle is well-established even where the schema-specific study doesn't exist yet: retrieval-grounding measurably reduces fabrication versus parametric recall, precision of what's retrieved dominates volume (Parts 2 & 7's distractor results7,9), and structured representations of a system outperform prose descriptions of it for machine consumption (Parts 4–612,13). Schema is simply the highest-stakes instance: it's the context type where a hallucination becomes a migration, and a migration becomes an outage.

    Synthesis; see refs 7, 9, 12, 13

    Takeaway

    Your database's current shape is computable, versionable, and sliceable. If the agent ever guesses about schema, that's not a model failure — it's a missing index in your system.

    ← Part 7Part 9: Coordinator agents don't scale →
    PART 09ORCHESTRATION & MEMORY

    Why Coordinator Agents Don't Scale

    Most multi-agent systems are paying a coordination tax and calling it architecture.

    The multi-agent pitch is seductive: a "manager" agent decomposes the task, "specialist" agents execute, everyone collaborates like a little software team. In practice, most of these systems rediscover — at inference prices — every distributed-systems problem we spent decades solving with deterministic tools. The org chart is not an architecture.

    The tax, itemized

    • Token duplication — each sub-agent needs enough context to act, so shared background is re-sent (and re-billed) per agent, and results are re-serialized back through the coordinator's window.
    • Latency amplification — coordinator→worker→coordinator turns serialize model calls; every hand-off is seconds, not microseconds.
    • The telephone game — each hand-off is a lossy natural-language compression of intent. Errors compound multiplicatively across hops.
    • Synchronization by vibes — parallel agents can't see each other's decisions; conflicts are discovered at merge time, adjudicated by another model call.
    • Fan-out without circuit breakers — a misbehaving branch can recursively multiply cost with no deterministic budget enforcement.
    Evidence · Three independent sources, one conclusion

    Anthropic (running multi-agent successfully in production, so hardly biased against it): multi-agent systems consume ~15× the tokens of chat, are economical only where task value justifies it, and are explicitly "not a good fit" for domains with tight dependencies between agents — their example of a poor fit is coding.3

    Cognition (Devin): "Don't Build Multi-Agents." Their production experience: parallel sub-agents with fragmented context make conflicting assumptions, and reliability comes from a single agent with continuous, fully-shared context — context engineering, not agent proliferation.4

    Berkeley (Cemri et al., NeurIPS 2025): across 1,600+ annotated traces from 7 popular multi-agent frameworks, performance gains over single agents were often minimal; the team catalogued 14 recurring failure modes in 3 classes — specification failures, inter-agent misalignment, and verification failures — and found most stem from system design, not model capability, and won't be fixed by better models.5

    Anthropic engineering, 2025 · Cognition, 2025 · Cemri et al., MAST, NeurIPS 2025

    Deterministic orchestration: the boring alternative

    Notice what the coordinator agent is actually doing: routing, sequencing, retrying, aggregating. None of that requires intelligence. All of it has mature, deterministic machinery:

    ◌ Coordinator agent

    • Control flow decided per-run by inference — different every time
    • State lives in a context window; crash = amnesia
    • Retries, timeouts, budgets: improvised in prose
    • Debugging = reading transcripts of a committee

    ● State machine / workflow engine

    • Control flow is code: explicit states, typed transitions, reviewable in a PR
    • State is durable and replayable (Temporal-class engines; LangGraph-style graphs)
    • Retries, timeouts, budgets, circuit breakers: first-class primitives
    • Debugging = inspecting a state machine's history

    The pattern that works is deterministic skeleton, probabilistic muscles: a workflow engine owns the graph — localize → retrieve → patch → test → review — and invokes the model only inside nodes where judgment is genuinely required. Event-driven orchestration handles fan-out where sub-tasks are truly independent (the one regime where even Anthropic's data says parallelism pays3). Even where sub-agents earn their keep, the honest framing — Cognition's — is that reliable ones are mostly read-only context gatherers: closer to expensive tool calls than to collaborating colleagues.4

    Takeaway

    Coordination is a solved, deterministic problem — state machines, workflow engines, queues. Spend inference on judgment inside the nodes, never on the edges between them.

    PART 10ORCHESTRATION & MEMORY

    Tests Should Be First-Class Retrieval Objects

    Tests define behavior better than documentation — and they never lie about being out of date.

    Documentation describes what someone once believed the code did. Tests describe what the code verifiably does, today, in executable form — with setup, inputs, expected outputs, and edge cases spelled out. Yet most agent stacks treat tests as a thing you run after generating a patch, not a thing you retrieve before. That's backwards. The test suite is the best-maintained behavioral specification your repository has.

    Behavioral indexing

    Make tests queryable along the axes that matter:

    • Coverage mapping — run the suite under coverage once per merge and invert the result: for every function, the exact tests that execute it. tests_covering("process_refund") becomes a deterministic lookup.
    • Contract extraction — parse assertions into behavior statements: "refund of a settled order returns RefundResult(status=PENDING); refund exceeding order total raises InvalidRefund." Signatures told the model the shape (Part 4); assertions tell it the meaning.
    • Fixture graph — fixtures encode how valid domain objects are constructed; linking them into the code graph gives the model canonical object-construction knowledge for free.

    Now the retrieval plan from Part 3 gains a behavioral layer: touching process_refund automatically pulls its three covering tests — a precise, executable spec of current behavior, usually far smaller than the docs that would attempt to describe it.

    Evidence · Tests as selection machinery

    Agentless doesn't just run tests at the end — tests are load-bearing in its pipeline. It generates reproduction tests from the issue, uses existing regression tests to filter candidate patches, and re-ranks the survivors — a fully deterministic selection stage that the paper's ablations credit for a substantial share of final accuracy.1 More broadly, SWE-bench itself is the proof that tests are the ground truth of behavior: the entire benchmark — the industry's shared yardstick for agent capability — defines "solved" as nothing more or less than "the fail-to-pass tests now pass."15 If tests are how we judge agents, they should be how agents see.

    Xia et al., FSE 2025 · Jimenez et al., ICLR 2024

    Execution-driven, contract-first loops

    Tests also give the workflow skeleton (Part 9) its cheapest, most reliable validators. A contract-first loop looks like: retrieve covering tests → model writes/extends the failing test first (making intent executable) → model patches → deterministic runner executes → structured failure (sliced per Part 2) feeds the next attempt. Every iteration is graded by a compiler and a test runner — verifiers with zero hallucination rate — instead of by another model reading the diff and emitting an opinion. The loop converges on green, and "green" is not a matter of interpretation.

    Takeaway

    Index your tests like you index your code. They are the only documentation in the repository that is executable, self-verifying, and guaranteed current — which makes them the highest-signal retrieval objects you own.

    ← Part 9Part 11: Working memory →
    PART 11ORCHESTRATION & MEMORY

    Agents Need Working Memory, Not Bigger Context Windows

    Humans don't reread every book they've ever read before solving a problem. Neither should AI.

    The context window is being asked to be four different things at once: attention, notebook, library, and diary. Human cognition separates these — a tiny working memory over vast, indexed long-term stores, with aggressive forgetting as a feature. The append-only transcript that most agents run on is the opposite design: everything ever seen stays maximally "in mind" forever, degrading attention (Part 7's evidence) while billing you for the privilege.

    A memory hierarchy for agents

    • Working memory (the window) — only what the current step needs: the task frame, the active files, the last failure. Small by policy, not by accident.
    • Task memory — durable structured state for this job: the plan, decisions made ("chose option B because migration risk"), files touched, budget consumed. Lives in the workflow engine's state (Part 9), survives crashes, and is selectively paged in.
    • Episodic memory — records of past sessions: "we fixed a similar DecimalConversionError in March; the fix was in serializer config." Indexed by embeddings + entities, retrieved when relevant, absent otherwise.
    • Semantic memory — the durable knowledge layer: code graph (Part 4), domain dossiers (Part 5), schema index (Part 8), test contracts (Part 10).
    Evidence · The OS analogy is a working architecture

    MemGPT (Packer et al., Berkeley) made this concrete: treat the context window as RAM and give the system OS-style virtual memory — paging information between the window and external storage with explicit memory-management operations. The approach let bounded-context models sustain coherent long-horizon behavior — document analysis and multi-session conversation beyond the raw window — by managing what's "resident" rather than growing it.17 The same conclusion arrives from the failure side: Chroma's results imply that even within a large window, keeping stale content resident actively harms performance,7 and Anthropic's context-engineering guidance formalizes the remedies — compaction, structured note-taking outside the window, and just-in-time retrieval — as the standard toolkit for long-horizon agents.19

    Packer et al., arXiv:2310.08560 · Chroma, 2025 · Anthropic engineering, 2025

    Context aging, eviction, retrieval scheduling

    Once memory is tiered, management becomes ordinary systems engineering with ordinary policies. Aging: a file read 30 turns ago decays to its signature; a resolved sub-task collapses to its one-line decision record. Eviction: superseded attempts and dead-end explorations leave working memory entirely — recoverable from task memory if needed, but no longer taxing attention. Retrieval scheduling: each workflow node declares its context contract — the patch node gets code + contracts; the migration node gets schema + lineage; the review node gets diff + invariants. Nothing rides along "just in case," because "just in case" is precisely the distractor mass the research says is most harmful.

    Notice the punchline: every one of these policies is deterministic. What pages in, what decays, what evicts — all decidable by code against declared contracts. The window stops being a junk drawer and becomes what it was always supposed to be: the small, hot set of exactly what this step needs. And a structured memory of entities, relations, and decisions is already most of the way to a knowledge graph — which is where this series goes next.

    Takeaway

    Scale memory, not context. The window is RAM — precious, small, and fast. Everything else belongs in indexed storage with deterministic paging policies.

    PART 12ORCHESTRATION & MEMORY

    Knowledge Graphs Beat Prompt Engineering

    Knowledge should be connected — not concatenated.

    Prompt engineering is the art of concatenation: stack descriptions of your system into a window and hope attention finds the relationships. But relationships are exactly what concatenated text destroys. "RefundProcessor writes ledger_entries, which ReconciliationJob reads nightly, which the finance dashboard queries" — in prose, that chain is three sentences the model must re-derive by attention. In a graph, it's three edges the system can traverse for free.

    One ontology, many sources

    The previous eleven parts each built a specialized index. The knowledge graph is where they federate — a single ontology over your entire engineering reality: code graphs (symbols, calls, imports — Part 4), schema graphs (tables, lineage — Part 8), documentation graphs (ADRs and dossiers linked to the entities they govern — Parts 5–6), test/contract graphs (behaviors linked to covered symbols — Part 10), and runtime graphs (services, traces, incidents from observability). Entity relationships cross the boundaries: this function ↔ writes this table ↔ governed by this ADR ↔ covered by these tests ↔ implicated in that incident. No single tool holds those edges today. That's why every incident review starts with an hour of archaeology — and why every agent session used to.

    Why graph retrieval reduces reasoning complexity

    When the answer requires multi-hop connection, flat retrieval makes the model do the hops: retrieve chunks, hold them in attention, infer the links — probabilistic work, paid in tokens, degraded by every distractor (Part 7). Graph retrieval does the hops in the system — deterministic traversal, then hands the model a pre-connected subgraph. You've converted reasoning (expensive, variable) into lookup (cheap, exact). That is the whole thesis of this series applied to knowledge itself.

    Evidence · Structure wins where connection matters

    Microsoft's GraphRAG is the flagship result: LLM-extracted entity graph + Leiden community detection + pre-computed community summaries. On global sensemaking questions over ~1M-token corpora, it beat vector RAG with ~70–80% win rates on comprehensiveness and diversity, and matched full hierarchical source-text summarization while using roughly 2–3% of the tokens per query — because connection-finding moved from query time to index time.10,11 Vector search finds things that sound like the question; graph traversal finds things that are related to the answer.

    Edge et al., arXiv:2404.16130 · Microsoft Research, 2024

    Counterweight — graphs are not free

    Honest engineering requires the caveat: naive graph-RAG can inflate prompts instead of shrinking them. Comparative studies measured some graph-RAG variants stuffing 40k–100k tokens per query — orders of magnitude above vector baselines — and found that piling on more retrieved subgraph stopped improving answers while adding noise.21 Indexing also costs real money up front and must be maintained. The lesson isn't "graphs always win"; it's that a graph is an index for precise traversal, not a license to dump neighborhoods. Budgets and slicing (Part 7) apply to subgraphs exactly as they apply to logs. For code specifically, you're also in the luckiest possible domain: unlike prose corpora, the graph doesn't need LLM extraction — compilers, parsers, and migrations give you most edges deterministically and nearly free.

    Ontology over vibes

    The practical migration path: define a small ontology (Entity types: Function, Table, Service, ADR, Test, Incident, Domain; Edge types: calls, writes, covered_by, governed_by, caused). Populate it from the deterministic sources you already built in Parts 4, 5, 8, and 10. Add embedding-based entry points for fuzzy queries, but make edges — not similarity — the backbone of expansion. Retrieval becomes: anchor (parsed, Part 3) → traverse (typed edges, bounded hops) → rank (centrality + task relevance) → slice to budget. Every step deterministic except the final generation.

    Takeaway

    Concatenation forces the model to rediscover relationships you already know. Store knowledge as a graph and retrieval becomes traversal — connection-finding moves out of the token bill and into the index.

    PART 13THE ENDGAME

    Measuring Agent Intelligence

    Benchmarking on coding challenges misses what matters in production.

    "Our agent scores X% on SWE-bench" tells you one number about one distribution of tasks under lab conditions — and nothing about what it costs, how long it takes, how much collateral change it makes, or whether it will do the same thing twice. Benchmarks measure capability ceilings. Production needs efficiency, precision, and repeatability — and those require different instruments.

    Evidence · Accuracy-only evaluation misleads

    The Princeton team showed this formally: without cost as a co-equal axis, leaderboards reward scientifically meaningless spend — retry loops and complexity that buy accuracy at any price — and the community drew wrong conclusions about why agents improved. Their prescription, jointly optimizing on a cost–accuracy Pareto frontier, revealed simple designs matching complex ones at a fraction of the cost.2 Agentless made the same point empirically by reporting % resolved, average cost, and average tokens together — and separately audited SWE-bench Lite itself, finding problem-quality issues (like issues whose text leaks the solution) that inflate naive readings of benchmark scores.1 Anthropic's variance analysis completes the picture: if token usage explains ~80% of performance variance,3 then a score reported without token counts is mostly measuring budget, not intelligence.

    Kapoor et al., TMLR 2025 · Xia et al., FSE 2025 · Anthropic, 2025

    The production scorecard

    files_touched / lines_changed

    Surgical vs. shotgun. Two agents both "solve" the ticket; one edits 2 files, the other rewrites 14. Blast radius is review cost, merge risk, and regression surface.

    tokens_consumed / task

    The direct cost of thinking. Tracked per phase (retrieval vs. generation vs. repair), it tells you exactly which part of the architecture is wasteful.

    tool_calls & graph_queries

    The exploration ratio. High tool-call counts with low graph-query counts means the agent is foraging probabilistically for what an index should provide deterministically.

    time_to_green

    Wall-clock from task start to passing CI. The metric users actually feel, and the one latency-amplifying architectures (Part 9) quietly destroy.

    test_pass_rate & first-attempt rate

    Not just "eventually green" but "green in how many attempts" — each repair loop multiplies cost and is a proxy for context quality.

    cost_per_completed_task

    The only number finance cares about — inclusive of retries, abandoned runs, and human rework. Report it like COGS, because it is.

    retrieval_precision

    Of the context supplied, how much did the final patch depend on? Directly measurable: intersect provided spans with edited/read spans. The single best health metric for your deterministic layer.

    context_utilization

    The inverse view: tokens supplied vs. tokens that mattered. Sub-10% utilization means you're paying attention-degradation costs (Part 7) for nothing.

    variance / repeatability

    Run the same task 10×. Determinism-heavy systems cluster tightly on cost and outcome; agent-heavy systems scatter. Variance is risk, and risk is cost.

    These aren't replacements for benchmarks — they're the instrument panel benchmarks can't be. Capability scores tell you which model to buy. This scorecard tells you whether your system is improving: whether this quarter's retrieval work moved precision from 8% to 40%, whether graph queries are displacing exploratory tool calls, whether cost-per-task is falling while pass rates hold. A team optimizing these numbers is doing engineering. A team optimizing only a leaderboard score is doing marketing.

    Takeaway

    Benchmark scores measure the model's ceiling. Tokens, tool calls, blast radius, time-to-green, and retrieval precision measure your architecture. Only one of those is under your control — instrument it.

    PART 14THE ENDGAME

    The Future Isn't Better Models. It's Better Systems.

    LLMs are becoming commodities. The moat is the architecture around them.

    Every capability gap between frontier models closes in months. Prices per token keep falling; open-weight models keep climbing the benchmarks; whatever advantage "we use the smartest model" confers, your competitor rents the same advantage tomorrow with one config change. Model choice is becoming procurement. Architecture is becoming strategy.

    Where the compounding advantage moved

    • Better retrieval — parsed prompts, code graphs, schema indexes, test contracts (Parts 3, 4, 8, 10). Every point of precision benefits every model, current and future.
    • Better orchestration — deterministic skeletons with probabilistic muscles (Part 9); budgets and circuit breakers as primitives, not prompts.
    • Better memory — tiered, indexed, deterministically paged (Parts 5, 11); institutional knowledge that accumulates instead of evaporating per session.
    • Better tooling — interfaces that return sliced signal, not raw exhaust (Part 2); the ACI lesson, generalized.
    • Better observability — the Part 13 scorecard wired into every run, so the system's economics are as visible as its outputs.
    • Better evaluation — cost–accuracy frontiers and repeatability, not leaderboard theater.
    • Better economics — cache-friendly context layouts, amortized indexes, inference reserved for judgment.

    Notice the asymmetry that makes this a durable strategy. Model improvements arrive for everyone simultaneously — including your competitors. System improvements are yours: they encode your repository, your schema lineage, your test contracts, your incident history. They compound with every merge. And they're model-portable — the day a better or cheaper model ships, a well-architected system swaps it in and inherits the gain on top of everything already built, while the prompt-and-pray stack starts re-tuning from scratch.

    There's a precedent for this moment. Databases stopped competing on raw storage and started competing on query planners. Networks stopped competing on bandwidth and started competing on protocols. Compute stopped competing on clock speed and started competing on orchestration. In every case, the commodity layer kept improving — and the value migrated to the systems that used it most efficiently. Inference is following the same curve, and the evidence has been visible all along this series: a $0.34 pipeline out-solving $3+ agents,1 token budgets explaining more variance than model choice,3 simple baselines matching complex architectures at a tenth the cost.2

    The companies that win won't necessarily have the smartest model. They'll have the architecture that asks the model to think the least — and therefore gets the most out of whatever model exists.

    Takeaway

    Models are rented. Systems are owned. Build the layer that makes any model cheaper, faster, and more precise — that's the asset that compounds.

    ← Part 13Closing thought →
    ∎SERIES CLOSING THOUGHT

    Intelligence is expensive.
    Determinism is cheap.
    Great AI systems maximize the latter so they can spend the former only where it creates real value.

    Fourteen parts, one discipline: parse before you prompt, index before you search, traverse before you reason, validate before you trust, and measure everything. The model is the most powerful component in the stack — which is exactly why a serious engineering organization treats its invocations the way it treats any scarce, expensive resource: scheduled deliberately, fed precisely, and audited relentlessly.

    If this series changes one thing about how your team builds, let it be this habit: before every model call your system makes, ask — what part of this could code have done? The answer, far more often than the industry admits, is: most of it.
