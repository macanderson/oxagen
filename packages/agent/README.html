What this is

@oxagen/agent is the execution engine for the Oxagen agent swarm. It receives a dispatch request, spins up the appropriate role (planner, worker, evaluator, coordinator), runs the plan-act-evaluate loop, writes memory back to the Neo4j graph, and invokes capability handlers from @oxagen/oxagen when the agent needs to act on the business. All LLM work is routed through @oxagen/ai — the single AI chokepoint — so metering, IAM, and telemetry are never bypassed.

dispatch→ runtime loop→ plan → act → evaluate→ memory writeback→ graph
⟁

Role-specialized swarm

Planners decompose tasks, workers execute, evaluators score outputs, coordinators route between roles. Each role maps to a different model configuration and prompt strategy.

◎

Graph memory

Agent observations, decisions, and episodic memory are persisted to Neo4j. Memory is graph-structured, not flat — agents retrieve context via graph traversal.

⊹

Lifecycle hooks

Before-dispatch, after-plan, after-act, and after-evaluate hooks allow observability, approval gates, and custom instrumentation without modifying the core loop.

Install / import

Workspace-internal package. Add "@oxagen/agent": "workspace:*" to the consuming package's dependencies.

{
  "dependencies": {
    "@oxagen/agent": "workspace:*"
  }
}
import { dispatch } from "@oxagen/agent/dispatch";
import { createRuntime } from "@oxagen/agent/runtime";
import { registerHandlers } from "@oxagen/agent/register";

// Register capability handlers at startup, then dispatch
registerHandlers();

const result = await dispatch({
  role: "worker",
  task: "Summarize recent activity for org abc123",
  context: { orgId: "abc123", userId: "u_xyz" },
});
import { registerHook } from "@oxagen/agent/hooks";

// Intercept before every dispatch for custom logging
registerHook("before-dispatch", async (ctx) => {
  logger.info({ role: ctx.role, task: ctx.task }, "agent dispatched");
});

Runtime flow

A dispatch request carries a role, a task description, and a caller context. The runtime resolves the role to a model configuration, retrieves relevant memory from the graph, and enters the plan-act-evaluate loop. Each iteration may invoke capability handlers (via the kernel in @oxagen/oxagen) or call LLM completions (via @oxagen/ai). When the evaluator is satisfied, the final output and any new observations are written back to the graph as memory nodes.

dispatch(role, task)→ memory read→ plan → act → evaluate→ memory writeback→ Neo4j graph
PhaseWhat happensLLM call?
PlanPlanner role decomposes the task into steps and selects toolsYes — via @oxagen/ai
ActWorker executes each step, calling handlers and graph queriesYes — per step
EvaluateEvaluator scores the output against the original taskYes — structured output

FAQ & design notes

▸ How does agent memory work?

Memory is stored as nodes and edges in Neo4j, not in a flat key-value store. Each observation, decision, and result produced by an agent run is written as a typed memory node with relationships to the relevant entities (user, org, workspace, prior runs). On subsequent dispatches, the memory module performs a graph traversal from the current context to surface the most relevant prior observations — without full-text search or vector similarity being the only retrieval mechanism.

The ./memory subpath exposes readMemory(ctx), writeMemory(node), and searchMemory(query). All writes are append-only — memory nodes are never mutated, only superseded by newer nodes with a supersedes edge.

▸ What are lifecycle hooks and when should I use them?

Hooks are named extension points fired at fixed phases of the runtime loop: before-dispatch, after-plan, after-act, after-evaluate. They receive a read-only view of the runtime context and can perform I/O (logging, metrics, approval gates) but cannot mutate the loop state.

Use hooks for: custom observability (emit a ClickHouse event on every act), approval gates (pause the loop and wait for a human confirmation before a destructive act), and test instrumentation (record what the planner decided in a test fixture).

▸ Why does all LLM work route through @oxagen/ai?

The single AI chokepoint (@oxagen/ai) is where token metering, performance tracking, IAM enforcement, and customer billing hooks live. If an agent called a provider SDK directly, those concerns would be bypassed. Every streamText or generateObject call in the runtime loop is made through @oxagen/ai's invoke() boundary — this is a hard architectural constraint, not a convention.

▸ How does the role system relate to model selection?

Each role maps to a model configuration in @oxagen/ai's model catalog. Planners and coordinators default to more capable models (Claude Sonnet or above) because their outputs determine the correctness of everything downstream. Workers use faster, cheaper models for execution steps. Evaluators use structured-output-capable models. The mapping lives in the runtime config and can be overridden per-dispatch — it is not hardcoded in the role implementations.
