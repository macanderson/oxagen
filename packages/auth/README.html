packages/auth · @oxagen/auth

Authentication built on Better Auth

The single source of authentication for the Oxagen platform. Provides the Better Auth server instance, the browser client, OAuth token encryption via @oxagen/crypto, and a carefully isolated two-Google-client configuration. Sessions stay server-side; the browser never sees a session token.

@oxagen/auth internal package domain: authentication import: @oxagen/auth better-auth 1.6

What this is

@oxagen/auth owns every authentication concern: session creation, OAuth provider configuration, token encryption, and the client-side auth handle. Business logic that needs to know "who is this user" imports from here; it never re-implements auth. The package is a security boundary — changes require careful review and must not loosen session, cookie, or token-storage guarantees.

browser request→ @oxagen/auth→ Better Auth→ session (server-side)→ @oxagen/database
◈

Server auth instance

The auth.ts export is the Better Auth server config — provider plugins, session options, database adapter, and encrypted token storage.

⊹

Browser client

client.ts exposes the Better Auth client handle for use in React components. It carries no secrets — session state is resolved server-side.

◇

Token encryption

OAuth access and refresh tokens are envelope-encrypted via @oxagen/crypto before they touch the database. Plaintext tokens never persist.

Install

This is a workspace-internal package. It is not published to npm. Add it as a workspace dependency in any app or package that needs authentication.

# in the consuming package's package.json
{
  "dependencies": {
    "@oxagen/auth": "workspace:*"
  }
}
# from the monorepo root
pnpm install

Usage

// apps/api/src/routes/auth.ts  — server only
import { auth } from "@oxagen/auth/server";

// Pass the raw Request; Better Auth returns a Response.
export async function handleAuth(req: Request): Promise<Response> {
  return auth.handler(req);
}
// apps/app/src/components/sign-in-button.tsx  — client component
"use client";
import { authClient } from "@oxagen/auth/client";

export function SignInButton() {
  return (
    <button onClick={() => authClient.signIn.social({ provider: "google" })}>
      Sign in with Google
    </button>
  );
}
// Server component — auth stays on the server
import { auth } from "@oxagen/auth/server";
import { headers } from "next/headers";

export async function getSession() {
  const session = await auth.api.getSession({
    headers: await headers(),
  });
  return session; // never passed to a client component
}

Session data is resolved in Server Components and passed as props or via server actions. The session token itself is never forwarded to client code.

Security details

▸ OAuth token encryption

OAuth access tokens and refresh tokens returned by Google (and any future provider) are sensitive credentials. Before being written to the database they are envelope-encrypted by @oxagen/crypto: a per-token data key is generated, the token is encrypted with that key, and the data key is in turn wrapped by the KMS master key. The ciphertext blob is what gets stored.

On read, the blob is unwrapped by the same KMS path. Plaintext tokens exist only in memory for the duration of the request. A compromised database row yields ciphertext, not a usable OAuth credential.

The encryption logic lives in src/token-encryption.ts and depends on @oxagen/crypto. Never bypass it to write a plaintext token, even in tests.

▸ The two-Google-client split

There are two distinct Google OAuth 2.0 client registrations, kept separate for the principle of least privilege:

Variable prefixPurposeStatus
GOOGLE_LOGIN_*User sign-in and session creation only. Scopes: openid email profile.In use
GOOGLE_DATA_*Google Workspace data access (Drive, Docs, Sheets, Calendar). Broader scopes.Reserved — not yet active

Mixing the two clients would grant login sessions an inadvertent claim to Workspace data scopes, violating the principle of least privilege and complicating the OAuth consent screen shown to users. Keep them separate at all times. When GOOGLE_DATA_* is activated it must follow its own consent, token storage, and refresh path — never piggybacking on a login session.

The old GOOGLE_CLIENT_* variable prefix has been removed. Do not reintroduce it.

▸ Session and cookie hardening

Sessions are stored server-side via the Better Auth database adapter. The browser receives a signed, opaque session cookie — HttpOnly, Secure, SameSite=Lax at minimum. The session token value is never accessible to JavaScript running in the page.

Cookie configuration, session duration, and rotation policy are defined in src/auth.ts. Any relaxation of these settings (e.g. removing HttpOnly, extending max-age beyond policy) must be treated as a security change and reviewed accordingly.

FAQ & gotchas

▸ Can I import @oxagen/auth/server in a client component?

No. The server export references the database adapter and environment secrets. Importing it in a client bundle will either fail at build time (tree-shake misses) or expose server-only configuration to the browser. Use @oxagen/auth/client in any file marked "use client" or consumed by a browser bundle.

▸ Where do I add a new OAuth provider?

Add the provider plugin to the Better Auth config in src/auth.ts. If the provider returns tokens that need protecting, wire them through token-encryption.ts using the same envelope pattern as Google. Add the corresponding environment variables to the monorepo .env schema and all relevant Vercel project env configs. Never commit credentials.

▸ How does session resolution work in the App Router?

Call auth.api.getSession({ headers: await headers() }) inside a Server Component or server action. The result is a fully typed session object (or null). Pass only the non-sensitive fields your component needs as props — do not forward the raw session object to a Client Component.

▸ Why was GOOGLE_CLIENT_* removed?

The original variable prefix conflated login and data-access scopes into one OAuth client. The split into GOOGLE_LOGIN_* and GOOGLE_DATA_* enforces least-privilege and makes the consent story cleaner for users. The old prefix is gone — update any local .env files that still reference it.
