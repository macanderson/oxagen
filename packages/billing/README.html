Billing, credits, and margin at the meter

The complete billing and monetization layer for the Oxagen platform. Stripe integration, a credit-denominated economy (1 credit = 1¢ USD), plan tiers from Free to Enterprise, usage metering where margin is realized at the point of consumption, and the low-balance UX that keeps customers in the product.

@oxagen/billing internal package domain: billing · monetization import: @oxagen/billing stripe 17.7

What this is

@oxagen/billing owns every concern that touches money: credit purchase, grant issuance, usage metering, entitlement checks, plan subscriptions, Stripe webhook handling, and checkout flows. The design principle is that margin is realized at the meter — a solved markup is applied when a credit is debited during metering, not at the point of purchase or at sticker price. This keeps pricing logic centralized in pricing.ts and keeps the Stripe catalog clean.

LLM / tool call→ @oxagen/ai usage→ metering.ts→ solved markup→ credit debit→ balance

Credit model

Credits are the customer's currency. Every billable action is priced in credits. One credit equals one cent (USD). Customers top up with real money; agents spend credits. The dollar amount is never displayed to a customer as a billing unit — credits are.

Metering and the markup model

Every AI call and billable tool use passes through the metering layer. The metering flow applies a solved markup — a pre-computed factor from pricing.ts that converts the raw provider cost into a customer credit debit that covers margin. The markup is solved at pricing-definition time, not dynamically per-call.

LLM/tool call→ @oxagen/ai invoke()→ metering.ts→ rawCost × markup→ debitCredits()→ usage event → ClickHouse

The customer-facing credit debit is always based on the metered cost with markup applied. The sticker price in the UI is informational — the authoritative number is what the meter produces. If the two diverge, the meter wins.

▸ pricing.ts is the source of truth — keep it in sync with Stripe

src/pricing.ts defines every price, every tier boundary, every markup factor, and every credit grant. It is the canonical definition of "what things cost." Stripe's product and price catalog is a downstream representation of this file — not the other way around.

When pricing changes, update pricing.ts first, then run the billing:stripe-sync flow to propagate the new prices into Stripe's catalog. Never edit prices directly in the Stripe dashboard and then try to reconcile them back into code — that direction always drifts.

The sync flow creates or updates Stripe Products and Prices to match pricing.ts. It is idempotent and safe to re-run. It does not delete Stripe objects that no longer appear in the file — deactivation is a manual step to avoid accidental billing disruptions.

▸ Credit expiry enforcement at debit time

When debitCredits() is called, the credits module selects buckets in expiry order: promotional grants with the nearest expiry first, then subscription grants, then purchased packs, then free credits (which never expire, so they are last). Each bucket is drawn down until the debit is satisfied.

If the total available balance (across all non-expired buckets) is less than the debit amount, the call fails with an insufficient-balance error. The caller (typically the AI invoke boundary) is responsible for surfacing this to the user or triggering the auto-reload flow.

▸ Low-balance warning and auto-reload

When a customer's total credit balance falls below 500 credits ($5), a dismissable re-up prompt is shown everywhere in the app. The prompt links to the checkout flow for a credit top-up.

If the customer has configured auto-reload (a saved payment method and a reload threshold), the billing system automatically charges the payment method and adds a purchased credit pack when the balance crosses the threshold. On successful auto-reload, the low-balance warning is suppressed and a toast notification confirms the charge. On failed auto-reload, a toast surfaces the failure and the warning is shown.

Free-tier customers (who cannot purchase credits) see a plan upgrade prompt instead of the top-up flow.

Usage

// Called by the AI invoke() boundary — not by individual handlers.
import { debitCredits } from "@oxagen/billing";
import { MARKUP } from "@oxagen/billing";

const creditsToDebit = Math.ceil(rawTokenCost * MARKUP.llm);

await debitCredits({
  tenantId,
  userId,
  amount: creditsToDebit,
  description: "agent:run — gpt-4o 1 200 tokens",
  metadata: { model, inputTokens, outputTokens },
});

The markup factor MARKUP.llm is exported from pricing.ts. Never hardcode a markup value at a call site — the factor may change when pricing is updated.

import { checkEntitlement } from "@oxagen/billing";

// Returns true if the tenant's current plan includes the feature.
// Used by @oxagen/iam to gate capabilities behind plan tier.
const allowed = await checkEntitlement({
  tenantId,
  feature: "acl:custom",  // Enterprise-only feature
});

if (!allowed) throw new EntitlementError("acl:custom requires Enterprise");
import { getCreditBalance } from "@oxagen/billing";

const balance = await getCreditBalance({ tenantId });
// balance.total:    number  — total non-expired credits
// balance.bySource: CreditBucket[]  — broken down by expiry source
// balance.lowBalance: boolean  — true if total < 500 (the $5 threshold)
import { createCheckoutSession } from "@oxagen/billing";

const session = await createCheckoutSession({
  tenantId,
  userId,
  priceId: "price_build_monthly",  // from pricing.ts constants
  successUrl: `${baseUrl}/billing?success=1`,
  cancelUrl:  `${baseUrl}/billing`,
});
// redirect user to session.url

FAQ & gotchas

▸ Can I read a price from the Stripe dashboard and use it in code?

No. The Stripe dashboard is a downstream representation of pricing.ts, not the source of truth. Always read prices, tier definitions, and markup factors from the exported constants in @oxagen/billing. Hardcoding a Stripe price ID or a dollar amount that you looked up in the dashboard will drift the moment the pricing is updated.

▸ Why is the markup applied at the meter rather than at sticker price?

Applying markup at the meter keeps the sticker price and the Stripe catalog clean and easy to reason about. The margin calculation is a single, auditable multiplication step inside metering.ts using the factor from pricing.ts. If the factor changes, it changes in one place and the updated behavior propagates immediately to all metered calls — no Stripe price edits, no UI copy updates.

▸ How do I handle a Stripe webhook in a new app?

Import the handleStripeWebhook function from @oxagen/billing/webhooks and pass it the raw request body and the Stripe signature header. The function verifies the webhook signature (using the STRIPE_WEBHOOK_SECRET env var), deserializes the event, and dispatches to the appropriate handler. Do not re-implement signature verification — always go through this function.

▸ Can Free-tier customers buy credits?

No. The Free tier exists to give new users a no-friction starting point ($5 in non-expiring credits). Purchasing additional credits requires at least the Build tier. The checkEntitlement function returns false for billing:purchase-credits on Free, and the checkout flow will not create a session for a Free-tier customer. Surface a plan-upgrade prompt instead.

▸ What happens to unused subscription credits when a plan is cancelled?

Subscription-granted credits expire at the end of the subscription period regardless of whether the subscription is cancelled mid-period or at natural renewal. Purchased pack credits (1-year expiry) survive the cancellation and remain available until their individual expiry dates. Free credits never expire. This behavior is enforced by the credit bucket expiry rules in credits.ts.
