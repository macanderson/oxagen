packages/iam · @oxagen/iam

Authorization and the audit boundary

The capability-based access control layer for the Oxagen platform. Every action is gated by a capability check. Denials and grants are audited. This package is the SOC 2 audit boundary — changes here require the same scrutiny as security and billing code.

@oxagen/iam internal package domain: authorization · audit import: @oxagen/iam SOC 2 relevant

What this is

@oxagen/iam provides the authorization layer that sits between an authenticated identity and any platform action. It answers: "can this principal perform this capability in this context?" and routes the request to the handler on allow or to a logged denial on deny. Every decision that crosses the authz boundary emits an audit event.

request + principal→ check-iam→ fetch-authz→ allow → handler · deny → denial + emit-audit
⟁

Capability checks

Every action is guarded by a named capability. checkIam is the single gate — no handler runs without passing through it.

⊘

Denial handling

Denials are not silent 403s. They are structured events: logged, audited, and returned with enough context for the caller to surface a meaningful error.

◎

Audit emission

Every authz decision emits an event to the audit log via emit-audit.ts. The audit trail is append-only and never mutated after write.

Usage

// apps/api/src/routes/agent-run.ts
import { checkIam } from "@oxagen/iam";

export async function handleAgentRun(req: Request, ctx: RequestContext) {
  // checkIam throws IamDenialError on deny — the handler never runs.
  await checkIam({
    principal: ctx.principal,
    capability: "agent:run",
    tenantId: ctx.tenantId,
    workspaceId: ctx.workspaceId,
  });

  // ... handler logic runs only on allow
}

The guard is not optional. An action that calls a handler without first calling checkIam is an authorization hole regardless of how well the handler is written.

import { fetchAuthz } from "@oxagen/iam/fetch-authz";

const authz = await fetchAuthz({
  principalId: session.userId,
  tenantId: ctx.tenantId,
});
// authz.capabilities: Set<string>
// authz.role: "owner" | "editor" | "viewer" | ...
import { emitAudit } from "@oxagen/iam/emit-audit";

// called automatically by checkIam; only call directly for custom events
await emitAudit({
  type: "iam.access.denied",
  principalId: ctx.principal.id,
  capability: "billing:manage",
  tenantId: ctx.tenantId,
  reason: "capability not granted",
});

Audit events are append-only. Never update or delete an emitted event. The events land in ClickHouse via @oxagen/telemetry.

import { bootstrapTenant } from "@oxagen/iam/bootstrap";

// called once when a new tenant is provisioned
await bootstrapTenant({
  tenantId: newTenant.id,
  ownerUserId: ownerUser.id,
});

Wired, not just written

▸ An authz layer that exists but is not called is dormant

The canonical failure mode for an IAM layer is: the code compiles, the tests pass, but the guard is never invoked on the actual request path. A dormant authorization layer provides zero protection — it is strictly worse than no layer because it creates false confidence.

The definition of "done" for any feature that touches protected resources is:

  • checkIam is called before the handler logic, not after, not conditionally
  • The denial path is tested — a test that only tests the allow path proves nothing about the guard
  • An audit event is verifiable — the audit trail has a record of the check
  • The guard is on the live request path — middleware, route handler, or server action; not a unit test only

The request flow is not negotiable:

request→ check-iam→ allow→ handler
request→ check-iam→ deny→ denial()→ emit-audit
▸ SOC 2 relevance

This package is in scope for SOC 2 Type II. The audit log produced by emit-audit.ts is evidence of access control enforcement. Auditors will look for: completeness (every action is guarded), correctness (denials are not swallowed), and integrity (the log is append-only and tamper-evident).

Changes to check-iam.ts, emit-audit.ts, or fetch-authz.ts are security-critical and require a review that includes the SOC 2 blocker backlog context. See Linear for the current open IAM blockers (OXA-1414..1433).

FAQ & gotchas

▸ Can I skip checkIam and call fetchAuthz directly?

No. fetchAuthz only loads the authz record — it does not evaluate the capability, emit an audit event, or throw on denial. Calling it directly and then writing your own evaluation logic creates a parallel, un-audited authz path. Always go through checkIam.

▸ What happens if emit-audit fails?

The audit emit is not allowed to be the reason a legitimate request fails. If the telemetry sink is unavailable, the error is logged (not swallowed) and the request proceeds. However, the missed event must be recoverable — the telemetry layer buffers and retries. Never catch and discard the error silently; surface it to the observability stack.

▸ How do I add a new capability?

Define the capability name as a typed constant (no magic strings at call sites). Add it to the capability registry. Update bootstrap.ts if the capability should be granted to new tenants by default. Write tests for the allow and deny paths. The capability name should follow the domain:action convention, e.g. agent:run, billing:manage, workspace:create.

▸ How does billing interact with IAM?

@oxagen/iam depends on @oxagen/billing to gate capabilities behind entitlements. A principal may have the capability in their role, but if their plan does not include the entitlement, checkIam denies. This keeps billing enforcement inside the authz boundary, not scattered across individual handlers.
