# ADR-189: A gateway call a hooked session makes seals one frame on that session's chain

Status: Accepted
Date: 2026-09-25
Amended: 2026-09-30 (#4355): decision 7, and decisions 5 and 6 narrowed to fit it. 2026-09-30 (#4601, ADR-231): the queues decisions 5 and 7 name. 2026-10-02 (#4355): a captured `tools/call` pins the `_meta` key
Owners: platform
Amends: ADR-140 (one tool call seals one frame), the sentence "A `tool_call` with no `tool_use_id`, which is what the MCP gateway seals for a connected client, has nothing to join on and always seals"
Related: #3944 (G-11 in the 2026-09-23 Tacho audit), #4355 (a call served before its hook was handled), ADR-078 (the local MCP gateway), ADR-095 (the tier ladder), ADR-168 (one ledger per session family)

## Context

The local MCP gateway seals each `tools/call` it forwards as a `tool_call` frame on the daemon's own chain, with no `tool_use_id`. ADR-140 accepted that: the frame has nothing to join on, so it always seals.

That fits Claude Desktop, which has no hooks and no session. It does not fit a hooked harness that uses the gateway as one of its MCP servers. Claude Code with the gateway added to its MCP servers recorded each such call twice. The gateway sealed a `tool_call` on the daemon's chain, and the `PostToolUse` hook sealed another on the session's chain. The two frames named one call under two identities, on two chains, and nothing joined them. The session's own record also showed no sign that Oxagen served the call.

Claude Code names the call in every MCP `tools/call` request it sends, under `params._meta["claudecode/toolUseId"]`. The 2.1.283 binary spreads that key into the request's `_meta`, and a request Claude Code 2.1.287 sent carries it (`packages/tacho/fixtures/claude-code/mcp/tools-call-2.1.287.json`). The call reaches the gateway after its `PreToolUse` and before its `PostToolUse`, because Claude Code waits on the hook before it calls the tool, and waits on the tool before it sends the `PostToolUse`.

## Decision

1. The gateway reads `params._meta["claudecode/toolUseId"]` from a `tools/call` and hands it to the daemon with the call. It forwards the request unchanged. It ignores an id that is not a string of 1 to 512 characters, the length the envelope accepts.
2. A `PreToolUse` that seals a `tool_requested` frame claims the call's `tool_use_id` in the session family's `ToolCallLedger`, the way a subagent's hooks already claim its calls. The claim registers no sighting.
3. When a gateway call names an id that a live session has claimed and no source has sealed yet, the daemon seals the gateway's frame on that session's chain, or on the chain of the subagent that made the call. The frame carries the `tool_use_id`, the gateway's body and digests, and `oxagen.enforcement_tier: gateway`. The ledger judges it as the `gateway` source. It is the first sighting, so the `PostToolUse`, OTel, and transcript sightings of the same call seal nothing.
4. A call the control plane refused seals its `policy_decision` on that chain with the `tool_use_id`. A refusal is not a sighting of the call, so the hook's `PostToolUseFailure` then seals the call's one `tool_call` beside it.
5. The daemon seals a session's gateway frame on that session's hook queue (ADR-231), where its hooks are handled, without holding the client's answer for it. The frame lands before the call's `PostToolUse`, because the queue runs in order and the harness sends that hook only after the answer. A failed write is logged and rolled back, which leaves the call claimed, so the `PostToolUse` seals it instead.
   For a call a live session awaits, the daemon picks the session when the gateway answers, not when the frame is written. A task already on the queue, such as a tick reading the call's `tool_result` from the transcript, can seal a sighting of the call first. The ledger then judges the gateway's frame on the session's chain: it seals stamped `oxagen.tool_call_duplicate_of` when it brings a body the chain lacks, and seals nothing when it repeats one. The frame falls back to the daemon's chain only when the session closed before it was written, and the daemon logs that with the `tool_use_id`.
6. A gateway call seals on the daemon's chain, as before, when it sends no id, when its id's first call still waits on the queue, or when a session has met its id and no longer awaits it, because a frame already holds the call or the session closed. The ledger would otherwise judge those second calls repeats and drop them. A call whose id no session has met waits for its hook under decision 7.
7. A call whose id no session has met was served before the daemon handled its `PreToolUse`. `tacho-hook` gives a `PreToolUse` 10 seconds, then spools it and answers, and Claude Code calls the tool while the live request still waits on its session's queue. A daemon that was down when the hook fired holds the hook only in the spool. The gateway's frame does not seal when the gateway answers. It waits on the host queue (ADR-231), which starts once every task queued before it has settled, so it runs after the hook's live request on whichever session's queue that request waits. At its turn the daemon drains the spool and looks for the session whose `PreToolUse` claimed the id since. The frame takes the host queue because nothing names that session before the hook is handled, and because a drain of the spool replays hooks of any session and runs only there. The frame seals on that session's chain under decisions 3 to 5, and the family ledger judges it against any sighting sealed in between.
   When no session has claimed the id and the spool still holds a `PreToolUse` naming it, because its replay failed or because the daemon is stopping and drains nothing, the frame seals nothing and the daemon logs it. That replay claims the call later, and the call's `PostToolUse` seals its one `tool_call` on the session's chain. A refusal still seals its `policy_decision` on the daemon's chain, because a refusal is not a sighting and nothing else records it. A call that no hook claims and the spool does not name, such as one from a session without hooks, seals on the daemon's chain.
   The rule holds across a restart because, after the answer, it reads only state that survives one: the spool and the persisted tool-call ledger. A daemon that dies with the frame still queued loses the frame, not the call. The next start replays the spooled `PreToolUse`, and the `PostToolUse` seals the call's one `tool_call` on the session's chain. A stopping daemon that refuses the queued hook ends the same way. In both cases the local record loses the gateway's frame, as it does under decision 5 when the frame's write fails. The control plane keeps its own record of the call.
   The other way to settle it is for the later hook to find the call already sealed on the daemon's chain and reconcile. A sealed frame cannot move to another chain, so the call's one `tool_call` would stay on the daemon's chain, and the daemon would have to persist every id its own chain sealed for the check to survive a restart.

ADR-140's rule, as ADR-168 widened it, now reads: one `tool_call` frame per `tool_use_id` per session family, sealed by whichever of the hook, the OTel export, the transcript tailer, or the gateway reports the call first.

## What this loses

The surviving frame is the gateway's, so it differs from the frame the hook would have sealed:

- It names the tool as the gateway knows it (`tool_name: query_ontology`, `mcp_server_name: oxagen`), not as the harness does (`mcp__<server>__query_ontology`, under whatever server name you gave the gateway). The `tool_requested` frame of the same `tool_use_id` keeps the harness's name.
- It carries none of the hook's classification: `effect_kind`, `tool_is_mutating`, `effect_id`. The `network` effect frame the `PostToolUse` seals for an MCP call still carries `effect_id`.
- Its output digest covers the JSON-RPC result the control plane sent, not Claude Code's `tool_response`.

Letting the hook's frame win instead would keep those facts and drop the gateway's evidence from the session's record: that Oxagen served the call and could have refused it. That fact is the reason the gateway tier exists.

## Consequences

- The forwarded request still names the daemon's chain in `x-tacho-gateway-session`. The control plane files its record of the call against that chain, and the session that made the call gains no `gateway` tier from it. Naming the session's chain instead would change that session's tier under ADR-095, which needs a decision of its own.
- The id is the client's word. The gateway takes no credential from a local client, so a local process that sends the id of a call a session is waiting on puts its frame on that session's chain, and the hook's report of the real call then seals nothing. The process has to name the id between that call's `PreToolUse` and its `PostToolUse`. ADR-095 makes no claim against the machine's operator, and this stays inside that limit.
- Tacho writes the gateway's MCP entry only into Claude Desktop's configuration today. This applies once you add the gateway to a hooked harness yourself.
- Sessions recorded before this change keep both frames.
- A gateway call from Claude Code that no session has met reaches its chain through the host queue, after a spool drain (decision 7). Its answer does not wait for either. Every hook queued after that task waits for it, so such a call costs the host one barrier. When no hook claims it, the daemon reads the spool directory once more to look for its `PreToolUse`.
- *Amended 2026-10-02 (#4355).* A `tools/call` Claude Code 2.1.287 sent pins the `claudecode/toolUseId` key and the shape of its value: `toolu_01` and 22 more letters and digits. It was captured over stdio, from one `claude -p` session against a server that logs what it reads, and it sits in `packages/tacho/fixtures/claude-code/mcp/tools-call-2.1.287.json` with the id replaced by a synthetic one of the same shape. `mcp-gateway.test.ts` reads the id from it. The gateway serves HTTP, and no capture covers that transport yet, so the HTTP path rests on the hand-built call in the same test file. The capture also shows 2.1.287 sending a `server/discover` request before `initialize`. The gateway forwards it to the control plane like any other method.
- The witness is `packages/tacho/src/collector/daemon-bodies.test.ts`: a hooked session's `PreToolUse`, its gateway call, and its `PostToolUse` seal one `tool_call`, on the session's chain. A second test fails the gateway frame's write and finds the `PostToolUse` sealing that one `tool_call` instead (decision 5). Three more hold the session's queue ahead of the frame: the transcript's sighting lands first and the gateway's frame is stamped as its duplicate on the session's chain, a second call naming the queued id seals on the daemon's chain, and a session whose `SessionEnd` is queued ahead of the frame sends the frame to the daemon's chain with a log line. Three cover decision 7: a `PreToolUse` whose live request waits behind a held session queue while its spool copy exists, with the frame on neither chain until the hook runs, a `PreToolUse` that is only in the spool, and a spooled `PreToolUse` whose replay the WAL refuses. Each finds one `tool_call`, on the session's chain. `packages/tacho/src/claude-code/recorder-tool-call.test.ts` covers the subagent chain, the refusal, and the claim across a restart and a rollback.
