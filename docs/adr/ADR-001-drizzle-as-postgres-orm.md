# ADR-001 — Drizzle as Postgres ORM

**Date:** 2026-05-27
**Status:** Accepted
**Epic:** Foundations

## Context

The foundation schema spans 13 domains and ~40 tables with reusable mixins
(`idMixin`, `auditMixin`, `tenantScopeMixin`, etc.), citext/ltree/bytea
columns, and a UUIDv7 default function. Migrations must be hand-editable
per spec §10.

## Decision

Use **Drizzle ORM** for Postgres. Drizzle Kit generates SQL migrations
that we hand-edit; the schema source of truth is TypeScript via
`pgSchema()` per domain.

## Alternatives considered

- **Prisma.** Schema DSL has no mixin concept — each table repeats the
  same eight columns. `Unsupported(...)` escape hatches required for
  citext, ltree, and UUIDv7 defaults. Migrations auto-generated and
  tightly coupled to the schema diff; hand-editing fights the tool.
- **Kysely.** Query builder only, no schema layer; we'd be hand-writing
  every CREATE TABLE alongside hand-writing every query. Strong DX for
  the query side but doubles the schema-management surface.
- **Hand-rolled SQL + a thin client.** Honest but slow. Loses the typed
  insert/select surface that materially helps in capability handlers.

## Consequences

- Mixins are TS functions that spread columns into a table definition.
- Migrations are SQL files (`0000_init.sql`, `0001_agent_runtime.sql`)
  generated by Drizzle Kit and then reviewed/tightened by hand.
- Cross-domain foreign keys are app-enforced per CLAUDE.md storage
  boundaries; within-domain FKs live in the migration.
- Drizzle's runtime is lean (no client generation step blocking dev).
- Tradeoff: less batteries-included than Prisma Client. No arbitrary
  `include` joins; we lean on `relations()` plus explicit SQL where
  needed.
