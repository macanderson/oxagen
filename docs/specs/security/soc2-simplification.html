03 — Recommendations
Prioritised simplification opportunities

Each recommendation addresses a concrete duplication, gap, or over-complex flow identified in this codebase. Existing OXA tickets are referenced where applicable; net-new tickets (N-1 through N-5) are proposed below and filed as sub-issues of the parent epic.

1
Consolidate audit emit into one call-site registry
P0 M (3) New ticket: OXA-N1 Blocks OXA-1523
Problem

SECURITY_EVENT_TYPES is defined identically in two files: packages/database/src/schema/security.ts and packages/telemetry/src/security.ts. Adding a new event type requires a three-way sync: the TS union, the DB CHECK constraint DDL, and now also the Inngest partition cron comment. Call sites are found via grep — there is no registry, no lint rule, and no way to know which mutations are missing without reading every handler. OXA-1523 enumerates 5 missing call sites; there are at least 3 more (API-key routes, MCP middleware, capability kernel denied path enrichment with IP/UA).

Proposed change
  • Create packages/compliance/src/audit-events.ts as the single source of truth for SECURITY_EVENT_TYPES. Both the Drizzle schema and the telemetry helper import from here. One edit = one place.
  • Add an ESLint rule (or a vitest invariant test in packages/compliance) that enumerates all handlers registered in packages/handlers and packages/billing and asserts each calls recordSecurityEvent or is explicitly exempted with a reason comment.
  • Add a useSecurityEmit() wrapper in the call-site registry that injects the inserter from DI context so callers do not need to construct it manually — reducing the per-call boilerplate from 3 lines to 1.
  • Wire the remaining 5+ missing call sites (billing grants, Stripe webhooks, API key create/revoke, MCP middleware api_key.used) as part of this ticket, consolidating OXA-1523 into this work.
Risk

Low. Additive; existing emit paths are unchanged. The lint rule is warn-only until all call sites are wired.

2
Replace stub audit UI with filterable viewer + signed export
P0 L (5) OXA-1558 (Backlog)
Problem

The current audit page (apps/app/src/app/[orgSlug]/security/audit/page.tsx) renders exactly 50 rows with no filter controls, no pagination, and no export. An auditor asking "show me all failed sign-ins from CIDR 10.x in Q1" cannot answer that from this UI. The compliance page is a "Coming soon" badge. There is no SIEM export path. This is the most visible SOC2 gap for any enterprise buyer doing due diligence.

Proposed change (already detailed in OXA-1558)
  • Replace static RSC page with filterable interactive viewer: event_type multi-select, actor_id picker, date-range, free-text. Cursor pagination (100/page), URL-encoded filter state.
  • Row drill-down panel showing full event context including ip, user_agent, request_id.
  • Signed NDJSON/CSV export endpoint gated to owner/admin role; HMAC-SHA256 signature header enables auditors to verify export integrity without trusting the download channel.
  • Reuse the same filter components in the workspace-scoped audit view and in the admin cross-org view (OXA-1559).
Simplification angle

Build the viewer components once in apps/app/src/app/[orgSlug]/security/audit/_components/, then reuse in the admin app's audit route. Avoid duplicating the filter/pagination logic. The compliance and incidents stub pages can be wired to the same event stream with different default filters (e.g. compliance = billing.* events; incidents = capability.invoke_denied + auth.sign_in_failed spikes) rather than building three separate data fetching paths.

3
Build the admin app auth gate + access-review surface first
P0 XL (8) OXA-1559 (Backlog)
Problem

apps/admin is a landing-page stub with no authentication, no routes, and no operator tooling. SOC2 CC6.2 / CC6.3 explicitly require periodic access reviews — "who has what privileges, are any grants stale, are any accounts over-privileged?" Today answering those questions requires direct Postgres queries against principal_role_assignments. OXA-927 (quarterly access-review automation) has been in the backlog since May 2026.

Proposed change (already detailed in OXA-1559)
  • Phase 1: Edge proxy + login page + assertAdminUser() helper gated to @oxagen.ai emails.
  • Phase 2: /access-review — paginated table of all orgs, per-org principal+role list, stale-grant flagging (last_active_at > 90 days), CSV export as SOC2 evidence artifact. Satisfies OXA-927 without building a separate email job.
  • Phase 3: Admin audit viewer (uses the same components as the tenant-side viewer from Rec 2).
  • Phase 4: RBAC within admin (owner/editor/viewer, mac@oxagen.ai hardcoded owner).
Simplification: consolidate OXA-927 into OXA-1559

The quarterly access-review email (OXA-927) can be replaced by the admin access-review page: instead of generating and emailing a report, the admin app surfaces the same data on-demand and the quarterly "drill" becomes "log in, export CSV, sign it, attach to the audit." One surface, no email infrastructure, same evidence. Close OXA-927 as superseded by OXA-1559 Phase 2.

4
Automate evidence-bundle generation via existing Inngest cron
P1 M (3) New ticket: OXA-N2
Problem

OXA-835 (cap.governance.export_compliance_bundle) is a Medium-priority backlog ticket proposing a manual, on-demand evidence export. OXA-930 (SOC2 readiness epic) has no automated evidence collection — an auditor asking for "the last 12 months of access reviews, audit logs, and control-check outputs" requires manual assembly. The partition rollover cron already runs monthly — it is the natural hook for automated evidence snapshot generation.

Proposed change
  • Extend packages/inngest-functions/src/functions/security.audit-partition-rollover.ts with a Step 3 that, after partition management, runs a monthly evidence snapshot: count of auth events, denied invocations, billing mutations, and access-review CSV for all active orgs.
  • Upload the snapshot to Vercel Blob (via @oxagen/storage) with a signed URL and write a reference row to a new compliance_snapshots table (Postgres, security schema, append-only).
  • The admin app's compliance page links to the last 12 snapshots — one-click download for auditors.
  • This replaces the proposed OXA-835 on-demand export with an automated one; OXA-835 can be closed as superseded.
Risk

Low-medium. The cron already runs monthly with withSystemDb; adding a Step 3 is additive. The compliance_snapshots table is a new append-only table — no migration risk to existing data.

5
Add a control-posture dashboard as the Security section landing page
P1 S (2) New ticket: OXA-N3
Problem

The Security section of the app currently redirects immediately to the audit tab. There is no top-level summary of the org's compliance posture — no at-a-glance view of "MFA enabled?", "SSO configured?", "last audit export date?", "recent auth failures count?", "open incidents?". The compliance page is a "Coming soon" stub. Customers on enterprise plans will open this page during their own security review; a stub destroys trust before a contract is signed.

Proposed change
  • Replace the redirect(org.security.audit) in security/page.tsx with a real control-posture dashboard (mock shown below in Section 4).
  • Display: MFA status, SSO status, active API key count, last 7-day auth failure count (from security_events), last export date, open incidents (count). All data available via existing DB queries — no new schema.
  • Wire the compliance tab to show control framework mappings (SOC2 CC6/CC7 control table) with a "pass/partial/fail" status derived from the live data — e.g. "CC6.1 Logical Access: PASS (MFA enabled, RLS enforced, rate-limit active)".
  • One RSC page pulling 5 cheap COUNT queries — zero backend complexity.
Risk

Very low. Pure read path. No new schema. Existing security_events index on (org_id, occurred_at) makes the 7-day count query fast.

6
Consolidate dual SECURITY_EVENT_TYPES definitions into packages/compliance
P2 XS (1) New ticket: OXA-N4
Problem

SECURITY_EVENT_TYPES and SecurityEventType are copy-pasted identically in two packages: packages/database/src/schema/security.ts:32 and packages/telemetry/src/security.ts:49. Adding a new event type requires editing both files AND the migration SQL CHECK constraint. One of these will drift from the other under time pressure. Both packages re-export the type but import from their own local definition — there is no cross-package dependency that would make a mismatch a compile error.

Proposed change
  • Move the const-union and type into a new packages/compliance/src/security-event-types.ts. Both @oxagen/database and @oxagen/telemetry import from @oxagen/compliance.
  • The migration SQL CHECK constraint is generated programmatically from the TS union via a migration helper in packages/compliance/src/db-check.ts — eliminates the third copy.
  • Add a unit test in packages/compliance that asserts the generated CHECK clause matches the live DB constraint — catches drift before it reaches prod.
Risk

Very low. Pure refactor — no behaviour change, no schema change. New package is a thin dependency of both existing packages.

7
Add structured SIEM webhook push from Inngest (Splunk / Datadog / generic)
P2 S (2) New ticket: OXA-N5
Problem

Enterprise buyers running their own SIEM (Splunk, Datadog, Chronicle, Panther) will ask for a push integration — they do not want to pull CSV exports manually. OXA-1558 specifies the signed NDJSON export endpoint but explicitly defers "actual Splunk/Datadog push connectors". Without this, the audit trail is only useful to Oxagen operators, not to the enterprise customer's own security team.

Proposed change
  • Add a new Inngest function security.siem-push triggered by each insert to security_events (via Inngest event from the DB insert hook, or a micro-batch cron every 5 minutes).
  • Org-level config in Postgres (siem_webhooks table: url, format, signing_secret, enabled). The function reads the config and POSTs NDJSON batches with HMAC-SHA256 signatures.
  • Supported formats: generic NDJSON (default), Splunk HEC, Datadog Logs API. Config screen in the Security > Compliance tab.
  • No external service dependency at build time — the webhook URL is user-supplied. Zero new infrastructure for Oxagen to manage.
Risk

Medium. Outbound webhook to user-supplied URLs is an SSRF surface — must validate the URL against an allowlist of schemes (https only, no private IP ranges) using new URL() + CIDR check. Retry logic needed for transient failures.

05 — Consolidated Roadmap
Proposed sequencing — SOC2 simplification

Phases are parallelisable within each wave. Dependencies: Rec 1 (emit consolidation) unblocks evidence quality for all downstream work. OXA-1558 and OXA-1559 share components and should be built together. Rec 4 extends existing Inngest cron — zero new infra.

  • OAuth tokens encrypted (OXA-1420)

  • SQL injection fixed (OXA-1421)
  • Sandbox digest-pinned (OXA-1423)
