# Credential custody

`tacho enroll` puts a machine under Oxagen's governance (`packages/tacho/src/cli/enroll.ts`). Once enrolled, a wrapped harness session is recorded, gated at four hook events, and has its model calls routed through a loopback proxy (ADR-094). Since ADR-143 the proxy also holds the model vendor's key for Claude Code and Codex, and the harness holds a run token in its place. None of that reaches the rest of what the harness process can read from the machine it runs on. A Claude Code, Codex, or Cursor session started today still carries the operator's laptop-level secrets in its environment and its filesystem: a `gh` CLI token backed by the OS keychain, AWS credentials, an SSH key, and whatever an MCP server's `env` block embeds. Oxagen governs the agent's actions. It holds one of the credentials those actions use.

This spec inventories every credential class a wrapped harness run can read today, classifies each one by whether an existing or proposed Oxagen mechanism moves it out of the harness's hands, and records the two mechanisms this task scopes: the model proxy's custody of the vendor key, which shipped, and a GitHub App token scoped to one run, which is designed here and partly built. It states plainly what remains on the laptop after both land, so onboarding and security copy never claims more custody than the record can back.

ADR-101 names Claude Code, Codex, Cursor, and Stella as the four harnesses `tacho enroll` wraps (`WRAPPED_HARNESSES` in `packages/tacho/src/wire.ts`). This inventory covers the three the task names and notes Stella where its credential path differs.

## The four classes

**Model proxy (a)** routes a call the harness makes to its model vendor through `tachod`'s loopback proxy (`packages/tacho/src/collector/model-proxy.ts`), which observes usage, prices it, can refuse a call against a budget, and, for a provider with a credential in custody, verifies the run token the harness presents and swaps in the vendor key it holds. Custody is live for Claude Code and Codex API keys (ADR-143). Stella and a ChatGPT-login Codex are routed and observed but cross `harness_held`.

**GitHub App (b)** replaces a personal token, whether a `gh` CLI token, an exported `GH_TOKEN`, or a cached git-over-HTTPS credential, with a short-lived installation token the GitHub App mints for one workspace's repository. `packages/github/src/workspace-token.ts` already mints and caches these tokens for Oxagen's own ingestion and repository-binding flows, and `createAppInstallationToken` can now narrow one to named repositories and permissions. No code path today mints one for a tacho-enrolled run or places it in the run's environment.

**MCP gateway, mediated (c)** routes an MCP tool call through `tachod`'s local gateway, which holds the real upstream credential (Slack token, Stripe key) encrypted in `mcp.credentials` (`packages/plugins/src/credentials/`) under the workspace's KMS key (`packages/plugins/src/credentials/kms.ts`), so the harness process never sees it. The mechanism is real and server-enforced, but `CONNECTED_HARNESSES` names only Claude Desktop. A wrapped harness's own MCP servers, configured directly in `.mcp.json`, `~/.claude.json`, `~/.codex/config.toml`, or `.cursor/mcp.json`, connect straight to their upstream with whatever credential is embedded in that config, and nothing in `tacho enroll` touches those files.

**No path today (d)** covers everything neither mechanism reaches: cloud infrastructure credentials (AWS, GCP), an SSH key used for git push, database connection strings a dev shell exports, and Cursor's model credential, which the loopback proxy does not route at all.

## Model proxy design

This design shipped in #3725 (ADR-143). The four questions the task asks are answered from the code.

**Where the key lives.** In the gateway daemon's custody on the machine, never on Oxagen's servers. `tacho enroll` reads the key off the harness's own file, or off `TACHO_BROKER_<PROVIDER>_API_KEY` in the enrolling shell, and seals it before it edits anything (`brokerCredentials` in `packages/tacho/src/cli/credential.ts`). The sealed store is `credentials.json` under `TACHO_HOME`, AES-256-GCM under a key in `credentials.key` beside it, both mode 0600 (`packages/tacho/src/host/credential-store.ts`, paths in `packages/tacho/src/host/paths.ts`). A copy of one file decrypts nothing. `tacho unenroll` puts each key back in the file it came from, then shreds the store and the signing key.

**How the run authorizes use.** The harness holds an `oxrt_` run token (`packages/tacho/src/host/run-token.ts`): JCS-canonical claims naming the host enrollment, the harness, the provider, a placement, and an expiry, HMAC-SHA256 signed by a key in `run-token.key` that never leaves the host. The ceiling is fifteen minutes. A caller may ask for less and never for more. Claude Code re-runs `tacho credential issue --harness claude-code` every five minutes and on any 401. Codex, which has no helper, holds a `static` token bounded by the enrollment's expiry, and the daemon renews it. Only the daemon mints (`issueRunToken` in `packages/tacho/src/collector/credential-issuer.ts`), and it refuses when the host is not `active` or when custody holds nothing for the provider. On every call the proxy verifies signature, expiry, host, and provider, then checks host status, so a revoked host refuses a valid token too. Rotating the signing key invalidates every token this host ever issued.

**What the record shows per use.** Every frame the proxy seals carries `oxagen.credential_basis`, `gateway_brokered` or `harness_held` (`TACHO_CREDENTIAL_BASIS_ATTR` in `wire.ts`), and a brokered call carries `oxagen.run_token_id`. Every mint seals a `token_issued` frame on the host's chain with the token's id, expiry, placement, provider, and signing-key id, never the token. The `llm_call` frame still carries the priced usage and the request and response digests as under ADR-094. The daemon's health report names which providers are brokered, and `tacho credential status` says where each key came from and when, by provider, kind, and source, without printing a secret.

**What the agent sees instead of the secret.** The loopback base URL it already saw under ADR-094 (`http://127.0.0.1:<port>/anthropic` or `/backend-api/codex`), and a run token where it used to hold the key: Claude Code sends the helper's output as `X-Api-Key`, Codex sends `auth.json`'s value as `Authorization: Bearer`. The token authenticates at this machine's gateway and nowhere else. A call that brings a vendor key of its own is refused as `foreign_credential`. A call with none is refused as `run_token_required`. Pointing the harness back at the vendor no longer reaches it, because the harness has nothing the vendor accepts.

**What this does not claim.** ADR-143's own limit stands: the person who owns the machine can read `credentials.key`, decrypt `credentials.json`, and call the vendor. The tier stays `gateway`, not `enforced`. Custody makes the bypass a key recovery rather than a one-line base URL edit. Only the contained tier (ADR-096) closes the rest.

## GitHub App design

### What exists today

`packages/github/src/app-auth.ts` mints and caches GitHub App installation access tokens: `getInstallationToken()` builds an RS256 JWT from `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY`, exchanges it for a token scoped to one installation, and reuses the cached token until 60 seconds before its one-hour expiry. `createAppInstallationToken` accepts optional `repositories` and `permissions` and posts them as the mint body, so a token can be narrowed to one repository and the permission set a caller names. The cache key includes the narrowing, so a full-grant token never answers a narrowed request and a narrowed one never answers a full request. `packages/github/src/workspace-token.ts`'s `resolveGitHubToken(ctx)` resolves a token for one workspace's connected repository, in the order ADR-020 records: installation token first, a KMS-decrypted per-workspace OAuth token second, an env-var personal access token last, for local development only. ADR-088 confirms the App's private key lives in the server environment, provisioned to the `api`, `mcp`, and `app` services through `packages/config/src/registry.ts`, never on a laptop.

The narrowing is a primitive, not a run path. `resolveGitHubToken` still asks for the installation's full grant, because ingestion and repository binding need it. Nothing in `packages/tacho` calls either function: no file under `packages/tacho/src` reads or writes `GH_TOKEN`, `GITHUB_TOKEN`, `~/.netrc`, `~/.git-credentials`, or a git credential helper. Minting a token for a tacho-enrolled run's own use, and placing it where the run's `gh` and `git` read it, is the work that remains.

### The run-scoped mint

- **Where the App's private key lives.** Unchanged: the server-side environment ADR-088 describes, never distributed to a host.
- **How a run authorizes minting.** The enrolled host already carries an `api_key` and, where the gateway applies, a `gateway_api_key` (`host.json`, `packages/tacho/src/host/host-file.ts`). A new capability, minting a token scoped to one run and one repository, takes the host's key and the session identity the model proxy already correlates as its authorization, and reads the installation id from the workspace's `source_connections` row the way `resolveGitHubToken` does. The ledger's own `create_run_token` (`packages/handlers/src/run.token.issue.ts`) shows the authorization shape: a run-scoped key row with a `purpose`, a run id, and an attempt id, refused for an API-key caller and for a sealed attempt.
- **What scopes the token.** The `repositories` list names the one repository the run's workspace binds, and `permissions` names the narrowest set the run's actions need, `contents: read` and `pull_requests: write` for a run that opens a pull request. Both ride the existing mint body. The one-hour GitHub expiry is the ceiling; the capability asks for no longer.
- **What the record shows per use.** ADR-050 established the pattern: `plugin.credential_set` and `plugin.credential_revoked` write `security_events` rows for a credential's lifecycle, and `secret.revealed` covers a privileged read. A new `github.run_token_minted` event carrying the run id, the repository, the permission set, and the token's expiry, never the token, follows the same rule. On the host, the mint seals a `token_issued` frame the way a model run token does, with `oxagen.provider` set to `github`. Mission Control spec §6.8 calls this a credential grant: connection id, scope, TTL, call id, recorded on the receipt.
- **What the agent sees instead of a PAT.** A short-lived token, minted for this run and this repository, set as `GH_TOKEN` and `GITHUB_TOKEN` in the run's own environment, not the operator's shell. `gh` reads `GH_TOKEN` before its keyring, and `git` reads a credential helper enrollment points at the daemon, so neither the `gh` OAuth token nor the `osxkeychain` entry is consulted for the run. Enrollment writes nothing permanent to `~/.config/gh/hosts.yml` or `~/.git-credentials`.

### What remains before it ships

The mint primitive exists. The run path does not, and it needs three pieces and one decision:

- [ ] A capability contract and handler, `issue_run_github_token`, over `createAppInstallationToken` with `repositories` and `permissions`, authorized by the host's key and a live session, emitting `github.run_token_minted`.
- [ ] A tacho side that asks for the token at `SessionStart` (ADR-094's hook events), sets `GH_TOKEN` and `GITHUB_TOKEN` for the harness process, and installs a git credential helper that answers from the daemon.
- [ ] Renewal for a session longer than an hour: the same helper cadence Claude Code's `apiKeyHelper` uses, or a refusal with a reason when the session outlives the token and the daemon cannot re-mint.
- [ ] The decision the maintainer owns: whether a workspace can require the run path, refusing a run whose `gh` still reaches the operator's own token, or whether it stays opt-in per host the way brokered model credentials do (ADR-143's rejected bundle field).

## What stays on the laptop

Classes (c) and (d) are not closed by the two designs above, and class (b) is not closed until the run path ships.

**Class (b), until the run path ships:** the `gh` OAuth token in the keychain, the `osxkeychain` git credential, and any `GH_TOKEN` a shell exports stay readable by every wrapped harness. The narrowing primitive changes nothing on the laptop by itself.

**Class (c), where the mechanism exists but does not reach a wrapped harness:** a Claude Code, Codex, or Cursor session that configures its own MCP servers in `.mcp.json`, `~/.claude.json`, `~/.codex/config.toml`, or `.cursor/mcp.json` holds whatever credential that config embeds, in plain text, on disk. The MCP gateway and its KMS-backed credential store are real, but only for Claude Desktop. Extending mediation to a wrapped harness's own MCP configuration is a further design this spec does not scope: it needs the same displace-and-restore contract `model-credential.ts` uses for the vendor key, applied to each harness's MCP config format.

**Class (d), where nothing in the current or proposed architecture reaches the credential:**

- AWS, GCP, and other cloud infrastructure credentials. No App-token or gateway equivalent exists for infrastructure providers. A run that does infrastructure work still runs with the operator's own IAM credentials in its environment. Mission Control spec §6.8 names STS session policies as the target shape, and nothing is built.
- An SSH key used to push over `git@github.com`. The GitHub App design mints HTTPS tokens. It has no bearing on an SSH remote, and GitHub Apps do not issue SSH credentials.
- Database connection strings and other dev-shell secrets (`DATABASE_URL`, `NEO4J_URI`, `CLICKHOUSE_URL`) that a local development shell exports.
- Cursor's model provider credential. Cursor is not routed through the loopback model proxy (ADR-101 decision 4).
- A `~/.netrc` entry for a non-GitHub host, or any credential a personal dotfile holds for a service this spec's two mechanisms do not cover.

`packages/tacho/src/arp/transfer.ts` refuses to copy a credential-shaped file, `.env`, `.mcp.json`, `credentials.*`, `id_rsa`, `id_ed25519`, or a harness config directory, into a local checkpoint capture, and `rejectSecrets` fails a capture that contains a recognized credential pattern. That is a safeguard against one kind of leak, an operator's own capture carrying a secret into an external run. It is not custody: the credential still lives on the laptop, and ARP declines to move it.

Docs, onboarding material, and any security-posture claim about Oxagen must not say a wrapped harness run holds zero credentials on the laptop, or that model-proxy and GitHub-App custody together close the gap. Model custody closes one class for two harnesses and keeps the key on the machine. The GitHub path closes a second once it ships. The other two remain, and the copy should name them the way this section does rather than imply a blanket guarantee the record cannot back.

## ADR

Class (a) is decided. ADR-094 fixed the vendor credential on the machine and chose the harness as the process holding it. ADR-143 amended that on 2026-09-22: the credential still stays on the machine, and the gateway daemon holds it rather than the harness. That record landed as a second ADR-138, beside the tool-identity record #3723 merged the day before, and this spec's change renumbers it to ADR-143 (ADR-142 went to cost-center chargeback in #3732 while this change was open) and indexes it. Nothing here supersedes ADR-143. The proposal an earlier draft of this spec made, a server-side key provisioned per workspace, is the shape ADR-094 rejected and ADR-143 kept rejected, and it is withdrawn.

Class (b) needs one new record. ADR-020 (the GitHub App token-resolution chain) and ADR-088 (a credential follows the service that reads it) describe how the App's private key and the installation-token mint behave. Neither decides whether a wrapped harness's run receives a token minted from them. The record that does, ADR-146 at the time of writing (ADR-145 went to enterprise SSO in #3735), would extend ADR-020 and ADR-088 to a run, cite Mission Control spec §6.8's row for installation tokens limited to the repositories in the call, and settle the opt-in question the checklist above names. This repo runs many concurrent sessions across a shared checkout, so its author should re-check `docs/adr/` rather than assume 146 is still free.
