Stripe / Billing Integration

How Oxagen turns Stripe into a hybrid subscription + usage-credit billing system: plans & seats, prepaid usage credits, metering at the AI chokepoint, dunning, auto-reload, disputes, tax, and the idempotent webhook spine that keeps it all in sync.

Package: @oxagen/billing  ·  Stripe SDK 17.7.0  ·  API version 2025-02-24.acacia  ·  Webhook receiver: apps/api  ·  UI: apps/app

Overview

Oxagen monetises on two axes that share one Stripe customer per organisation:

  • Subscription — a per-org plan (free / build / scale / enterprise) billed monthly or annually, with a seat (license) quantity.
  • Usage credits — prepaid balance (1 credit = 1¢) that every AI/LLM/tool call draws down through a single metering chokepoint. Plans grant included credits each cycle; customers top up with credit packs or automatic reload.

The customer's currency is credits. Plans set the floor and included allotment; real usage is metered and debited from credit lots. The system is USD-only by product decision (no FX).

Design invariant: every capability that costs money or moves Stripe state is reachable identically from the in-app agent, the REST API, and MCP, and is metered + authorized at exactly one place.

Subscriptions

Stripe owns the lifecycle; our subscriptions table mirrors it via syncSubscriptionFromStripe(stripeSubId), invoked from every subscription.* webhook so our row matches the provider within one round-trip.

Plan changes — changeOrgPlan(orgId, slug, interval)

  • No active subscription (free) → returns a Stripe Checkout URL; caller redirects.
  • Active subscription → swaps the price in place (no second subscription). The direction is decided by previewing the invoice the change would raise and reading its sign — invoices.createPreview under proration_behavior: create_prorations, which produces the same proration lines always_invoice would and issues no invoice, so asking the question charges nobody. Stripe computes the prorated credit for unused time on the old price, the prorated charge for the new one, and applies the customer's discounts; the net is the answer. Positive → always_invoice (charge the proration now) and a prorated grant of the new plan's extra included credits (grantProratedPlanUpgradeCredits). Zero or negative → none (keeps access until renewal, no proration line). A preview that cannot be taken settles as always_invoice, never none — an invoice raised the wrong way is a credit the customer can see and we can refund; a charge never raised is simply gone.
  • An interval change is never a downgrade. Changing the recurring interval resets the billing-cycle anchor at the provider, which invoices the new period immediately, prorations disabled or not. An annual subscriber moving to a monthly plan previews a NEGATIVE proration (credit for the unused year) and would otherwise take the none branch — quoting $0 while a full month was charged. So when the interval moves, the change is billed under always_invoice and quoted from the whole invoice rather than the proration lines: the anchor-reset charge is a non-proration line, which amountCents cannot see. The figure quoted is amount_due, not total — see What the customer is asked for below.
  • The quote is what will be collected, not what the invoice comes to. total is the invoice; amount_due is what the provider will actually take, after it applies whatever credit sits on the customer's account from a refund, an overpayment or a credit note. The two agree for a customer carrying no balance and part company for one who does, and the interval-change figure is presented to a person as what happens to their card now — so quoting the total overstated the charge by the whole balance. The preview exposes both (totalCents, amountDueCents), the quote reads the second, and the swap logs both so a quote can be reconciled. This is the same distinction the adapter already drew for issued invoices.
  • No preview, no quote. The two paths diverge deliberately when the provider cannot answer. changeOrgPlan settles an unknown direction as always_invoice, because the provider bills the true difference either way. previewPlanChange raises PlanChangePreviewUnavailableError instead, because it is answering a person about to confirm and there is no safe default: coercing an unavailable amount to 0 promises "nothing to pay" and then lets always_invoice charge the real figure.
  • Why a preview and not a price field. Three figures have stood in for "what this subscriber pays", and all three inverted (#3157):
    • the entitlement tier rank — until Enterprise was priced below Scale;
    • the billing.plans row — until a reprice left grandfathered subscribers on an older, immutable price while the catalogue row moved;
    • price.unit_amount — until a discount. allow_promotion_codes is set on both checkout paths, so a $200 price discounted to $100 moving to an undiscounted $150 read as a decrease and dropped the charge.
    Each fix replaced a stand-in with a closer stand-in, and each closer one had its own inversion. The preview is not a closer stand-in; it is the money. Do not reintroduce a stored or catalogued amount here — billing.subscriptions deliberately records stripe_price_id (which price, an identity) and no amount, so there is nothing to decide from.
  • A retried change is a no-op. If the subscription is already on the target price id, the swap already happened and the call returns without touching the provider. Re-deciding would compare the subscription against its own current price, read no movement, and send none where the first attempt sent always_invoice — under the same idempotency key (subscription + target price + optional requestId), which Stripe rejects rather than replaying. The swap is a no-op on a retry; the rest of the operation is not. A retry re-emits the audit event and finishes the prorated credit grant if the first attempt died before reaching it — but only when there is evidence that a mutation really happened, because the same branch is reached by somebody submitting the plan they are already on. See What counts as evidence of a mutation below.
  • What counts as evidence of a mutation. One predicate decides both the audit event and the grant recovery, because they answer the same question and two conditions that must agree is how this last went wrong. Either a standing pending_upgrade_from_plan_id — written before a swap, retired only once its grant settled, so unfinished work from a real attempt — or a recorded stripe_price_id that disagrees with the provider, which is a swap that was never written down. Steady state has neither.

    A NULL stripe_price_id is not a disagreement. The column was added nullable with no backfill, so every subscription predating it carries NULL and reading that as a mismatch made the test true for the whole legacy population — recording a privileged mutation on requests that changed nothing. It cannot be backfilled in SQL, and must not be derived from billing.plans: the catalogue holds today's price while a grandfathered subscriber sits on an older immutable one, so the derived identity would be wrong in exactly the way this page warns about above. The column fills itself as syncSubscriptionFromStripe runs, including from the repair on this branch.

    Emitting is still inferred rather than recorded: a first attempt whose swap and audit both succeeded and whose grant then failed leaves the intent standing, so a retry writes a second event for one mutation. Recording the emission durably needs a column on the intent and is tracked separately.
  • The plan being left is written down before the swap. The prorated upgrade grant is sized from the allowance of the plan moved from, and the swap destroys that: upgradeSubscription syncs the subscription synchronously and the sync repoints plan_id at the target. A call that died between the two therefore left a customer upgraded and uncredited, with nothing left to recompute the grant from. billing.subscriptions.pending_upgrade_from_plan_id is that record: written before the provider is asked to do anything, read by the retry, and cleared only once the grant has settled — so a grant that fails leaves it standing for the next attempt. It is deliberately absent from syncSubscriptionFromStripe's conflict SET, so a provider sync cannot erase an intent whose work is unfinished. It is an identity, not an amount: the rule above still holds.
  • Only this preview's prorations are summed. proration === true selects every proration on the upcoming invoice, including ones this change did not create — a seat decrease recorded earlier under create_prorations leaves a pending credit sitting there. Summed together, a large enough pending credit makes a real upgrade read as nonpositive, the caller ships none, and the upgrade charge is dropped: the same inversion as the tier rank and the catalogue row, one level further in. Stripe stamps period.start of each proration it creates with the proration_date the preview was anchored at, so that anchor is what separates this change's lines from the rest of the invoice — once it has been established that the anchor is ours alone. proration_date is Unix SECONDS, so a change committed in the same second as a preview stamps its proration with the same period.start, and timestamp equality is not ownership. Nothing in the payload settles it either: type names the line's source rather than the request that made it, subscription_item is the same item for both, and proration_details.credited_items exists only on credit lines. So the adapter reads every line before deciding anything — Invoice.lines is an ApiList that embeds only the first page and sets has_more, and a change whose credit and charge straddle that boundary is otherwise priced from one side, so an upgrade reads as a downgrade with no concurrency involved. Paging is bounded, and past the bound the quote is refused rather than computed from a set known to be incomplete. It then takes a baseline preview — the invoice as it stands, with no change simulated, paged the same way — and refuses with AmbiguousProrationAnchorError if a proration already sits at that second, rather than guessing at a field that might mean ownership. Both preview paths do this, because both derive their anchor the same way. A refusal on a same-second collision is recoverable; summing a stranger's credit makes a real upgrade read nonpositive, ships none, and the charge is never raised. The preview is the money; which part of it answers the question is a separate question. Three cases are distinguished on purpose: no proration lines at all is a true zero; lines carrying the anchor are summed (and may legitimately net to zero); lines present with none carrying the anchor cannot be attributed and raise ProrationAttributionError rather than a fabricated zero — the ?? 0 lesson one layer down. The invoice-level figures used for interval changes are deliberately unfiltered: the invoice the anchor reset raises really does collect everything on it. Of those, amountDueCents is the one quoted, for the reason given above.
  • The credit grant is decided by the allowance delta, never by the invoice. Whether the customer owes money and whether their included allowance went up are different questions. grantProratedPlanUpgradeCredits is delta-guarded on includedCreditCents and idempotent on (org, target plan, period), so every completed swap is offered to it and it declines the ones that earn nothing. Gating it on the previewed direction meant a preview that could not be taken — direction: "unknown", which answers neither question — charged the customer for a real upgrade and withheld the credits.
  • The already-applied guard asks the provider, not our record of it. subscriptions.stripe_price_id is written by syncSubscriptionFromStripe, which runs after the provider mutation — so it is blind to the one failure the guard exists for, a swap that reached Stripe whose response was lost. The active price is read from the provider, and when the two disagree the stale row is resynced rather than left wrong.

    There is no fallback to the local row. There used to be, justified as: if the provider cannot be reached the swap cannot be issued either, so refusing would trade a wrong answer for an outage. That holds for an outage and not for a transient failure of this one read — the case where the preview and the update then succeed and the operation runs on the very row the guard exists to distrust. The fallback had no case in which it helped and one in which it silently did harm, so resolveActiveProviderState now raises SubscriptionStateUnavailableError and the caller retries. It is raised before any provider mutation and before the durable upgrade intent is written, so a refusal leaves nothing half-done.
  • The interval is read from the provider for the same reason, and by the same call. subscriptions.billing_interval is written by that same post-mutation sync and is stale in the same failure — and what it decides is worse to get wrong, because it is what says whether this change resets the billing-cycle anchor. After a monthly→annual swap whose sync was lost, the column still reads month, so a move back to monthly looks same-interval: its negative proration reads as a downgrade, none is selected, and the quote is $0 while the provider resets the anchor and invoices the new month regardless. resolveActiveProviderState returns the price and the interval from the one subscription read, and both the swap path and the quote path take the interval from it, so the confirmation screen and the charge are decided by the same subscription. The local column is not a fallback for this either — the same refusal applies — and the swap logs both the provider's interval and the recorded one, so a row drifting from the provider is visible before its consequences are.
  • The entitlement tier ordering (TIER_ORDER / meetsMinimumTier) answers a different question — does this plan include that feature — and is never read as a price direction. The two disagree in the live catalogue: Enterprise outranks Scale on features and costs half as much, so deciding proration from the rank under-billed every Enterprise→Scale move and over-billed every Scale→Enterprise one (#3157).

previewPlanChange takes the same preview changeOrgPlan takes, so the quote and the change cannot disagree. It reports what the customer will actually be asked for now: the previewed proration when the bill rises, and zero when it falls or holds — because that swap ships none, which writes no proration line, so nothing is owed at the moment of the change however large the previewed credit was. An org with no active subscription has no invoice to preview; its quote is the full catalogue price for the interval, which is the one place billing.plans figures are read on this path.

Cancel / reactivate set cancel_at_period_end (access continues to period end; reversible).

Seats & proration preview → confirm

Seat count = subscription quantity = license count. Pending invitations consume a seat. A seat change never charges silently — it is a preview → confirm flow.

UI "Update" ─▶ previewSeatsAction ─▶ subscriptions.previewSeatChange(orgId, seats) │ ├─ resolve active sub + default card ├─ provider.previewSeatChange ── Stripe invoices.createPreview │ proration_behavior = increase ? always_invoice : create_prorations └─ sum proration line items ─▶ { amountCents, isCharge, card, direction } UI dialog: increase ─▶ "Adding N seats will charge $X now to Visa ••4242" [Cancel] [Change card] [Confirm & pay] decrease ─▶ "Removing N seats credits $X to your next invoice" [Cancel] [Confirm] On confirm ─▶ setSeatsAction ─▶ subscriptions.setSubscriptionSeats(orgId, seats)
  • Increase → proration_behavior: "always_invoice" (invoice the proration immediately).
  • Decrease → proration_behavior: "create_prorations" (a credit toward the next invoice, never a surprise refund).
  • Floor guard — SeatLimitError blocks dropping below provisioned headcount (active members + pending invites).
  • All mutating Stripe calls carry an idempotency key (e.g. seats:<sub>:<n>, plan_change:<sub>:<price>:<10s-bucket>) so a double-submit can't double-invoice.

Proration line items are summed net of discounts (amount minus the line's discount_amounts); amount alone is what the price lists, which overstates the charge for every discounted subscriber.

The exact charge figure comes from summing the proration line items of stripe.invoices.createPreview({ subscription, subscription_details:{ items, proration_behavior, proration_date } }).

Credits & metering

Lots, expiry, consumption

Every grant creates a lot. Consumption drains soonest-expiring-first with row-locking and no overdraft (consumeCredits in credits.ts). Expiry by source:

SourceGranted byExpires
free_grantSignup (grantFreeCredits, 500¢)Never
subscriptionPlan renewal on invoice.paid (grantPlanCreditsForInvoicePaid)End of grant month (use-it-or-lose-it)
purchaseCredit pack / auto-reload+1 year

All grants are atomic + idempotent via INSERT … ON CONFLICT DO NOTHING on the credit_ledger idempotency index — webhook retries never double-grant.

The metering chokepoint & admission gate

Text, image, and video usage all funnel through one DB-charging chokepoint in metering.ts (chargeUsageCredits / chargeImageCredits / chargeVideoCredits → chargeCostUsd): provider cost × solved markup → credits → atomic debit. Before any model runs, the admission gate assertCanStartTurn(orgId) runs:

assertCanStartTurn(orgId) 1. assertOrgCanConsume(orgId) ── throws BillingSuspendedError if dunning state = suspended 2. maybeAutoReload(orgId) ── best-effort: top up if low + auto-reload on (never blocks the turn) 3. effectiveBalance(orgId) > 0 ── else throw InsufficientCreditsError
Wiring (critical): the gate is injected into the single AI boundary kernel.invoke() (packages/oxagen/src/kernel.ts) via setBillingAdmissionGate. Each surface calls bootstrapBillingRuntime() at startup — apps/api/src/bootstrap.ts, apps/app/instrumentation.ts, apps/mcp/src/middleware.ts — the same pattern as the IAM gate. Without that call the gate is dormant.

Auto-reload & low-balance

Configured per org in org_billing_settings. maybeAutoReload(orgId) (in autoreload.ts), called from the admission gate:

  1. Skip unless enabled AND effective balance < threshold AND not reloaded in the last hour (idempotency window).
  2. Charge autoReloadAmountCents off-session (provider.chargeOffSession, PaymentIntent off_session: true, confirm: true) on the saved PM or customer default. Idempotency key bucketed per hour.
  3. On success, grant a purchase lot (reason grant_auto_reload, +1yr) and stamp last_auto_reload_at.
Charge-but-grant-fail safety: if the grant write fails after a successful charge, we log a critical reconcile alert (alert: auto_reload_charged_but_not_granted, with the paymentIntentId), do not stamp last_auto_reload_at, and return grant_failed_after_charge without throwing. The next turn retries the grant against the same idempotency-deduped charge — so a transient DB error self-heals and never crashes the user's turn.

The dismissible low-balance banner (low-balance-banner.tsx) renders when balance < the configured threshold; auto-reload suppresses it.

Tax

Stripe Tax is wired into all checkout sessions but ships dark behind STRIPE_TAX_ENABLED. The flag exists so the code path is complete and can be activated by a single env flip once Stripe Tax is registered in the dashboard (a true external action). With the flag off, automatic_tax.enabled = false and checkouts behave exactly as before. Addresses are collected at checkout and persisted to the customer (customer_update: address: auto) so renewals compute tax correctly.

Webhooks idempotent

Receiver: apps/api/src/routes/stripe.ts → POST /webhooks/stripe. It reads the raw body, calls verifyStripeSignature(rawBody, sig) (provider verifies against STRIPE_WEBHOOK_SECRET), then processStripeEvent(event).

Three-phase idempotency (webhooks.ts)

1. INSERT raw event into stripe_events (ON CONFLICT DO NOTHING — immutable audit anchor) 2. A true duplicate only if stripe_event_processing.processed_at is already set; a prior FAILED attempt re-dispatches (every handler is idempotent, so self-heals) 3. dispatch(event) ─▶ upsert stripe_event_processing with the outcome (processed_at | error)

Dunning (failed-payment recovery)

State machine on org_billing_settings.dunning_state (dunning.ts):

active ──(invoice.payment_failed)──▶ grace delinquent_since=now, grace_ends_at=now+7d grace ──(invoice.paid)────────────▶ active cleared (onInvoiceRecovered) grace ──(grace_ends_at passed)────▶ suspended sweepDunning() daily cron, usage hard-gated suspended ──(invoice.paid)─────────▶ active
  • assertOrgCanConsume throws BillingSuspendedError while suspended — enforced at the admission gate.
  • sweepDunning() runs as a daily Inngest cron (0 2 * * *) — packages/inngest-functions, function billingDunningSweep.
  • UI: dunning-banner.tsx surfaces grace (with deadline) and suspended states.

Disputes & refunds

Disputes (chargebacks): Stripe reverses the funds automatically, so we do not refund — we claw back the credits funded by the disputed charge. onDisputeCreated records a billing_disputes row (idempotent on stripe_dispute_id) and consumes credits (reason clawback_dispute); onDisputeClosed updates status. If the org can't be resolved from the charge metadata, it logs a critical dispute_org_unresolved alert rather than silently dropping the clawback.

Refunds: issued by an operator in the Stripe dashboard (or API); reconciled automatically via the charge.refunded webhook → onChargeRefunded, which claws back credits proportional to the refunded amount (reason refund, idempotent on the charge id). There is intentionally no unwired programmatic refund-issuer in domain code.

  # … through charge.refunded …
# Capture the returned `secret` (whsec_…) and store it as STRIPE_WEBHOOK_SECRET
# on the api (+ app) production env, then REDEPLOY api so the new secret loads.

The signing secret is only returned at creation — capture it then. Env changes apply to the next deployment, so a redeploy of oxagen-v2-api is required to activate it.

Activate Stripe Tax

  1. Register / enable Stripe Tax in the Stripe Dashboard (set origin address, nexus). No safe API path.
  2. Set STRIPE_TAX_ENABLED=true on oxagen-v2-api + oxagen-v2-app (production); redeploy.
  3. Verify a checkout shows tax and the address is saved to the customer.

Switch to live keys

  1. Set live STRIPE_SECRET_KEY / STRIPE_PUBLISHABLE_KEY / NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY.
  2. Re-provision the catalog against the live account (billing:stripe-sync).
  3. Recreate the webhook endpoint on the live account + update STRIPE_WEBHOOK_SECRET (the steps above).
  4. Redeploy; confirm billingDunningSweep appears in the Inngest dashboard (needs INNGEST_* keys).

Rotate the webhook secret

Roll the secret in the Stripe Dashboard (or recreate the endpoint), update STRIPE_WEBHOOK_SECRET, redeploy api. Mismatched secret ⇒ all events 400 (signature verification fails) until the deploy lands.
