Stripe / Billing Integration

How Oxagen turns Stripe into a hybrid subscription + usage-credit billing system: plans & seats, prepaid usage credits, metering at the AI chokepoint, dunning, auto-reload, disputes, tax, and the idempotent webhook spine that keeps it all in sync.

Package: @oxagen/billing  ·  Stripe SDK 17.7.0  ·  API version 2025-02-24.acacia  ·  Webhook receiver: apps/api  ·  UI: apps/app

Overview

Oxagen monetises on two axes that share one Stripe customer per organisation:

  • Subscription — a per-org plan (free / build / scale / enterprise) billed monthly or annually, with a seat (license) quantity.
  • Usage credits — prepaid balance (1 credit = 1¢) that every AI/LLM/tool call draws down through a single metering chokepoint. Plans grant included credits each cycle; customers top up with credit packs or automatic reload.

The customer's currency is credits. Plans set the floor and included allotment; real usage is metered and debited from credit lots. The system is USD-only by product decision (no FX).

Design invariant: every capability that costs money or moves Stripe state is reachable identically from the in-app agent, the REST API, and MCP, and is metered + authorized at exactly one place.

Data model — Postgres billing schema

Transactional billing state lives in Postgres only (runtime usage events go to ClickHouse; nothing billing-related lives in Neo4j). Tables defined in packages/database/src/schema/billing.ts:

Subscriptions

Stripe owns the lifecycle; our subscriptions table mirrors it via syncSubscriptionFromStripe(stripeSubId), invoked from every subscription.* webhook so our row matches the provider within one round-trip.

Plan changes — changeOrgPlan(orgId, slug, interval)

  • No active subscription (free) → returns a Stripe Checkout URL; caller redirects.
  • Active subscription → swaps the price in place (no second subscription). Upgrade → always_invoice (charge the proration now) and a prorated grant of the new plan's extra included credits (grantProratedPlanUpgradeCredits). Downgrade → none (keeps access until renewal).

previewPlanChange simulates the change first (see Seats — same invoices.createPreview mechanism), so the UI shows the prorated charge + card before committing.

Cancel / reactivate set cancel_at_period_end (access continues to period end; reversible).

Seats & proration preview → confirm

Seat count = subscription quantity = license count. Pending invitations consume a seat. A seat change never charges silently — it is a preview → confirm flow.

UI "Update" ─▶ previewSeatsAction ─▶ subscriptions.previewSeatChange(orgId, seats) │ ├─ resolve active sub + default card ├─ provider.previewSeatChange ── Stripe invoices.createPreview │ proration_behavior = increase ? always_invoice : create_prorations └─ sum proration line items ─▶ { amountCents, isCharge, card, direction } UI dialog: increase ─▶ "Adding N seats will charge $X now to Visa ••4242" [Cancel] [Change card] [Confirm & pay] decrease ─▶ "Removing N seats credits $X to your next invoice" [Cancel] [Confirm] On confirm ─▶ setSeatsAction ─▶ subscriptions.setSubscriptionSeats(orgId, seats)
  • Increase → proration_behavior: "always_invoice" (invoice the proration immediately).
  • Decrease → proration_behavior: "create_prorations" (a credit toward the next invoice, never a surprise refund).
  • Floor guard — SeatLimitError blocks dropping below provisioned headcount (active members + pending invites).
  • All mutating Stripe calls carry an idempotency key (e.g. seats:<sub>:<n>, plan_change:<sub>:<price>:<10s-bucket>) so a double-submit can't double-invoice.

The exact charge figure comes from summing the proration line items of stripe.invoices.createPreview({ subscription, subscription_details:{ items, proration_behavior, proration_date } }).

Credits & metering

Lots, expiry, consumption

Every grant creates a lot. Consumption drains soonest-expiring-first with row-locking and no overdraft (consumeCredits in credits.ts). Expiry by source:

SourceGranted byExpires
free_grantSignup (grantFreeCredits, 500¢)Never
subscriptionPlan renewal on invoice.paid (grantPlanCreditsForInvoicePaid)End of grant month (use-it-or-lose-it)
purchaseCredit pack / auto-reload+1 year

All grants are atomic + idempotent via INSERT … ON CONFLICT DO NOTHING on the credit_ledger idempotency index — webhook retries never double-grant.

The metering chokepoint & admission gate

Text, image, and video usage all funnel through one DB-charging chokepoint in metering.ts (chargeUsageCredits / chargeImageCredits / chargeVideoCredits → chargeCostUsd): provider cost × solved markup → credits → atomic debit. Before any model runs, the admission gate assertCanStartTurn(orgId) runs:

assertCanStartTurn(orgId) 1. assertOrgCanConsume(orgId) ── throws BillingSuspendedError if dunning state = suspended 2. maybeAutoReload(orgId) ── best-effort: top up if low + auto-reload on (never blocks the turn) 3. effectiveBalance(orgId) > 0 ── else throw InsufficientCreditsError
Wiring (critical): the gate is injected into the single AI boundary kernel.invoke() (packages/oxagen/src/kernel.ts) via setBillingAdmissionGate. Each surface calls bootstrapBillingRuntime() at startup — apps/api/src/bootstrap.ts, apps/app/instrumentation.ts, apps/mcp/src/middleware.ts — the same pattern as the IAM gate. Without that call the gate is dormant.

Payment methods Stripe Elements

Cards are managed in-app; the PAN never touches Oxagen servers.

"Add / change card" ─▶ createSetupIntentAction ─▶ payment-methods.createPaymentMethodSetupIntent └─ provider.createSetupIntent(customerId) (usage: off_session) Browser ─▶ <StripeElementsProvider clientSecret> <PaymentElement> ─▶ stripe.confirmSetup({ redirect:"if_required" }) On success ─▶ syncPaymentMethodsAction ─▶ syncPaymentMethodsFromStripe(orgId) (pull list + default, upsert mirror)

Backend domain (payment-methods.ts): listOrgPaymentMethods, setOrgDefaultPaymentMethod (provider default + DB flag flip, in one transaction so a reader never sees zero defaults), removeOrgPaymentMethod (detach + soft-delete; refuses to remove the last card on an active subscription — LastPaymentMethodError). Components: payment-methods.tsx, stripe-elements-provider.tsx. Deps: @stripe/stripe-js, @stripe/react-stripe-js.

Auto-reload & low-balance

Configured per org in org_billing_settings. maybeAutoReload(orgId) (in autoreload.ts), called from the admission gate:

  1. Skip unless enabled AND effective balance < threshold AND not reloaded in the last hour (idempotency window).
  2. Charge autoReloadAmountCents off-session (provider.chargeOffSession, PaymentIntent off_session: true, confirm: true) on the saved PM or customer default. Idempotency key bucketed per hour.
  3. On success, grant a purchase lot (reason grant_auto_reload, +1yr) and stamp last_auto_reload_at.
Charge-but-grant-fail safety: if the grant write fails after a successful charge, we log a critical reconcile alert (alert: auto_reload_charged_but_not_granted, with the paymentIntentId), do not stamp last_auto_reload_at, and return grant_failed_after_charge without throwing. The next turn retries the grant against the same idempotency-deduped charge — so a transient DB error self-heals and never crashes the user's turn.

The dismissible low-balance banner (low-balance-banner.tsx) renders when balance < the configured threshold; auto-reload suppresses it.

Checkout flows

FlowRouteMode
New subscriptionPOST /api/v1/stripe/checkout → createCheckoutSessionStripe Checkout, mode: subscription. Guards against a second subscription when one is active.
Usage credits (dynamic $)POST /api/v1/stripe/credits → createDynamicCreditCheckoutInline price_data, mode: payment; volume discount applied; credits deposited on checkout.session.completed.

Both routes set automatic_tax: { enabled: STRIPE_TAX_ENABLED } and (when on) customer_update: { address: "auto" }, and both require the billing-manager role (see Authorization). Subscription credits arrive via invoice.paid; one-off pack credits via checkout.session.completed.

Tax

Stripe Tax is wired into all checkout sessions but ships dark behind STRIPE_TAX_ENABLED. The flag exists so the code path is complete and can be activated by a single env flip once Stripe Tax is registered in the dashboard (a true external action). With the flag off, automatic_tax.enabled = false and checkouts behave exactly as before. Addresses are collected at checkout and persisted to the customer (customer_update: address: auto) so renewals compute tax correctly.

Webhooks idempotent

Receiver: apps/api/src/routes/stripe.ts → POST /webhooks/stripe. It reads the raw body, calls verifyStripeSignature(rawBody, sig) (provider verifies against STRIPE_WEBHOOK_SECRET), then processStripeEvent(event).

Three-phase idempotency (webhooks.ts)

1. INSERT raw event into stripe_events (ON CONFLICT DO NOTHING — immutable audit anchor) 2. A true duplicate only if stripe_event_processing.processed_at is already set; a prior FAILED attempt re-dispatches (every handler is idempotent, so self-heals) 3. dispatch(event) ─▶ upsert stripe_event_processing with the outcome (processed_at | error)

Dunning (failed-payment recovery)

State machine on org_billing_settings.dunning_state (dunning.ts):

active ──(invoice.payment_failed)──▶ grace delinquent_since=now, grace_ends_at=now+7d grace ──(invoice.paid)────────────▶ active cleared (onInvoiceRecovered) grace ──(grace_ends_at passed)────▶ suspended sweepDunning() daily cron, usage hard-gated suspended ──(invoice.paid)─────────▶ active
  • assertOrgCanConsume throws BillingSuspendedError while suspended — enforced at the admission gate.
  • sweepDunning() runs as a daily Inngest cron (0 2 * * *) — packages/inngest-functions, function billingDunningSweep.
  • UI: dunning-banner.tsx surfaces grace (with deadline) and suspended states.

Disputes & refunds

Disputes (chargebacks): Stripe reverses the funds automatically, so we do not refund — we claw back the credits funded by the disputed charge. onDisputeCreated records a billing_disputes row (idempotent on stripe_dispute_id) and consumes credits (reason clawback_dispute); onDisputeClosed updates status. If the org can't be resolved from the charge metadata, it logs a critical dispute_org_unresolved alert rather than silently dropping the clawback.

Refunds: issued by an operator in the Stripe dashboard (or API); reconciled automatically via the charge.refunded webhook → onChargeRefunded, which claws back credits proportional to the refunded amount (reason refund, idempotent on the charge id). There is intentionally no unwired programmatic refund-issuer in domain code.

Operational runbook

Recreate the webhook endpoint (e.g. for a new account)

# enabled_events must list EVERY event the dispatcher handles (see Webhooks table)

  -d url=https://oxagen-v2-api.vercel.app/webhooks/stripe \
  -d api_version=2025-02-24.acacia \
  -d "enabled_events[]=customer.subscription.created" \
  # … through charge.refunded …
# Capture the returned `secret` (whsec_…) and store it as STRIPE_WEBHOOK_SECRET
# on the api (+ app) production env, then REDEPLOY api so the new secret loads.

The signing secret is only returned at creation — capture it then. Env changes apply to the next deployment, so a redeploy of oxagen-v2-api is required to activate it.

Activate Stripe Tax

  1. Register / enable Stripe Tax in the Stripe Dashboard (set origin address, nexus). No safe API path.
  2. Set STRIPE_TAX_ENABLED=true on oxagen-v2-api + oxagen-v2-app (production); redeploy.
  3. Verify a checkout shows tax and the address is saved to the customer.

Switch to live keys

  1. Set live STRIPE_SECRET_KEY / STRIPE_PUBLISHABLE_KEY / NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY.
  2. Re-provision the catalog against the live account (billing:stripe-sync).
  3. Recreate the webhook endpoint on the live account + update STRIPE_WEBHOOK_SECRET (the steps above).
  4. Redeploy; confirm billingDunningSweep appears in the Inngest dashboard (needs INNGEST_* keys).

Rotate the webhook secret

Roll the secret in the Stripe Dashboard (or recreate the endpoint), update STRIPE_WEBHOOK_SECRET, redeploy api. Mismatched secret ⇒ all events 400 (signature verification fails) until the deploy lands.
