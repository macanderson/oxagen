Blockers (FAIL — 11 items)

  • Check 4: Dead schema (~19 orphan tables). Tables executions, executionSteps, toolCalls, executionArtifacts, documents, playbooks, triggers, and others have migrations + Drizzle relations but zero CRUD. The live agent runtime persists to subagentRuns/subagentFanouts and telemetry to ClickHouse, bypassing these tables entirely. Recommend deletion per prefer-deletion directive or completing the vertical slices that use them.
  • Check 5: Append-only hygiene (storage model violation). toolCalls is high-volume append-only telemetry living in Postgres instead of ClickHouse (per storage matrix); no time-based partitioning exists. executionArtifacts carries mutation columns (updated_*) on a conceptually append-only record. Migrate telemetry to ClickHouse or add partition/retention strategy to Postgres tables.
  • Check 7: RLS / tenant scoping (data isolation gap). Zero row-level security policies on ~50 tenant-scoped tables. Isolation relies entirely on per-handler discipline to add eq(org_id)/eq(workspace_id) predicates by hand. One concrete leak: chat.message.send final conversation UPDATE filters by conversation_id only (no org/workspace). Implement OXA-1515: centralized RLS + withTenant() GUC wrapper. Until then, data isolation is vulnerable to hand-written query errors.
  • Check 11: Skill adherence (business logic duplication). createOrgAction in apps/app/.../new-organization/actions.ts re-implements org-create + workspace-create DB transactions, slug-conflict guards, IAM bootstrap, and billing grants that already exist in organizationCreateHandler + workspaceCreateHandler (tested in @oxagen/handlers). This violates prime-directive "Business logic lives in /packages/, never reproduced in a service." Extract or delegate to handlers.
  • Check 12: Headless parity (API token create/revoke). The /[org]/developer/tokens UI page says "Tokens can be created via the Oxagen API" but no api.key.create or api.key.revoke route exists in apps/api or apps/mcp. Capability is advertised with no agent path. Add API route + MCP tool or update copy to say "coming soon".
  • Check 13: Test coverage — actions.ts untested. apps/app/.../new-organization/actions.ts has 196 lines of business logic and zero unit tests. Error paths (slug conflict, missing fields, race conditions) are untested. E2E covers happy path UI only. Add unit tests or extract logic to @oxagen/handlers where it can be tested in isolation.
  • Check 13: Test coverage — thresholds unconfigured. @oxagen/handlers and @oxagen/telemetry have no coverage.thresholds in their vitest.config.ts. Policy requires ≥85% line / ≥80% branch enforced in config. Add thresholds to all 23 packages (only 4 have them today).
  • Check 14: E2E coverage — member invite flow. org.member.invite.accept and org.member.invite.decline MCP tools and API routes exist but no e2e spec covers the invitation flow (send → accept/decline → membership state). Critical surface untested end-to-end.
  • Check 14: E2E coverage — API token create/revoke. No e2e spec covers API token creation or revocation. Critical developer credential surface is entirely untested (compounded by check 12: no API/MCP route exists).
  • Check 18: Test lane separation (e2e missing from PR gate). Policy mandates "e2e tests on PR open and update." The PR-gate ci.yml has zero test:e2e step; e2e runs only nightly. A PR that breaks org-create (exactly what this diff touches) can merge with green CI before nightly catches the regression 12 hours later.
  • Check 20: Stale docs (CLAUDE.md middleware.ts claim). CLAUDE.md line 269 says "middleware.ts is no longer recognized." This is factually wrong — Next.js 16 recognizes both middleware.ts and proxy.ts. The project chose proxy.ts as convention, not because middleware.ts is deprecated. This language will cause agent thrash when ecosystem examples or errors reference middleware.ts. Fix the documentation.

Warnings (WARN — 13 items)

  • Check 5: executionArtifacts audit columns. Carries updated_at/updated_by_user_id on a conceptually append-only record. Soft-delete on immutable records also implies mutation that shouldn't happen. Use dedicated appendOnlyAuditMixin() like usageRecords.
  • Check 6: PII logging. Raw user emails logged in three sites: apps/app/.../members/actions.ts:69,78 and packages/handlers/src/org.member.add.ts:91. Not secrets (no FAIL), but GDPR data-minimization best practice: hash or drop raw emails.
  • Check 6: IAM-table fallback graceful degradation. fetch-authz silently swallows Postgres 42P01 (missing IAM tables) and returns empty authz, falling back to contract defaults. A dropped/un-migrated IAM schema disables authz resolution org-wide without failing the request. Comment says "Remove after pnpm db:migrate is standard" — tighten or remove before GA.
  • Check 6: IAM enforcement stale comment. Kernel comment at line 14 says "flag can be off during initial seeding period" but IAM_ENFORCEMENT_ENABLED defaults to true/fail-closed. Update comment to reflect secure-by-default design.

  • Check 12: Profile update / avatar upload (app-internal only). Handled in apps/app/src/app/api/v1/upload/avatar/route.ts (app-internal) with no apps/api route or MCP tool exposing profile update to agents.
