Oxagen Platform — Internal Architecture Guide

How the platform is wired today: one capability definition fanned out across three surfaces, who is allowed to do what, how tenants are kept apart, what SOC 2 controls exist, and how the app is laid out. Written for engineers, security, and anyone onboarding. It is honest about what is half-built.

Platform overview

Oxagen is a place where AI agents do real work inside a company’s walls — answering questions, generating content, running playbooks — while staying metered, governed, and logged. The same set of abilities is reachable however you knock on the door: a chat window, a REST API, or an MCP client like Claude or Cursor.

Analogy

Think of Oxagen as an office building. The lobby is the chat. The workers are AI agents. Behind the scenes there’s a records room, a corkboard of who-knows-what, a security-camera tape that can never be erased, and a supply closet for big files. A front desk checks everyone’s badge before they do anything. The rest of this guide is a tour of that building.

The four data stores

Oxagen uses four different databases on purpose. Each one holds exactly one kind of thing, and nothing else. This isn’t just tidiness — it’s a security control. Keeping money, camera tape, and big files in separate cabinets means a mistake in one place can’t leak the others.

Analogy — four filing cabinets

A records room for official paperwork, a corkboard with string for connections, a locked camera-tape archive you can add to but never edit, and a supply closet for bulky items. Put a thing in the wrong cabinet and the whole system gets confusing and unsafe — so the rule is one-thing-per-cabinet.

PostgreSQL Live

@oxagen/database

The records room — the single source of truth. Users, orgs, workspaces, permissions, billing, chat, config. Anything that must be correct and changeable.

Neo4j Partial

@oxagen/ontology

The corkboard — graph relationships, agent memory, ontology, lineage. “What connects to what” and “what does this agent know.”

ClickHouse Live

@oxagen/telemetry

The camera tape — append-only runtime events, logs, traces, token usage, and the tamper-evident audit trail. Write once, never edit.

Blob storage Partial

@oxagen/storage → Vercel Blob

The supply closet — avatars, generated images/video, documents. The big file lives here; its reference row lives in Postgres.

The hard rule: never put analytics in Neo4j, never put graph relationships in Postgres, never put transactional state in ClickHouse, and never put a binary blob in any of the three databases. Each store has one job.

Clarification

When this guide says “the surfaces stay in parity,” it means API + MCP + in-app agent — all three funnel through the same kernel, so an ability is either available on all of them or on none.

The contract spine: how the surfaces stay in sync

The single most important idea in the platform.

Every governable action the platform can take is written down exactly once as a capability contract in the @oxagen/oxagen package. There is no path to action that bypasses it. That one definition is what keeps the API, MCP, and the in-app agent from drifting apart — they don’t each implement the feature, they all point at the same definition.

Analogy — one recipe, many kitchens

Imagine a restaurant with three kitchens (API, MCP, app). Instead of letting each kitchen invent its own version of a dish, there’s one recipe box. Every kitchen cooks from the same card. If a dish isn’t on a card, nobody is allowed to make it. Change the card once and all three kitchens serve the new version. That recipe box is the capability registry.

What a capability is

Each capability is one file in packages/oxagen/src/contracts/ registered with registerCapability(). The fields are checked by TypeScript at compile time, so you can’t register a half-defined ability:

FieldMeaning (plain English)
nameThe dotted id, e.g. image.generate.
surfacesWhich doors expose it: "api", "mcp", "agent". A wrong-door call is rejected.
input / outputZod schemas. Inputs are validated before the work runs; outputs after.
sensitivitylow → destructive. Feeds the access rules.
defaultEffectThe fallback answer when no rule matches — almost always "deny".
defaultRolesWhich roles get this ability out of the box.
agentFor agent-exposed abilities: risk level + whether a human must approve first.
layersWhich artifacts should exist: schema, api, mcp, unit, e2e, docs — used by the parity checker.

There are ~42 capabilities registered today — 4 foundation, 16 agent-runtime, plus chat, billing, conversation, org-member, and media abilities. Each has a one-page contract in docs/capabilities/ generated from the same source, so the docs cannot drift from the code.

The single doorway: kernel.invoke()

No surface cooks the dish itself. Each one hands the request to one function — invoke() in packages/oxagen/src/kernel.ts — and that function is the inspection window every request passes through, in this order:

1Right door?Is this surface even allowed to call this capability? (surface_denied if not.)
2Right ingredients?Validate the input against the Zod schema.
3Allowed to?Run the IAM check — allow, deny, or require-approval.
4Can you afford it?Billing admission gate — enough credits / not suspended.
5Right room.Run the handler inside the tenant scope so the database isolates rows.
6Right plate.Validate the output schema.
7Stamp the logbook.Emit a security audit event — for allow, deny, and error.

Because all three real surfaces funnel through this one window, metering, permissions, tenant isolation, and the audit trail are applied identically no matter which door you used. That is what “parity” really means here: not three copies of a feature, but three thin doors onto one governed core. A second, narrower chokepoint exists for the AI itself — streamAgentReply(), generateImageFor(), and the video path in @oxagen/ai are the only places that actually call a model, so every token is counted and billed in one spot.

How each surface re-exposes the same capability

REST API — Live

Hono. One hand-written file per capability under apps/api/src/routes/v1/. It parses the body with the contract’s own schema, builds the context, and calls invoke(name, body, ctx, {surface:"api"}). No code generation — the route is glue.

MCP server — Live

xmcp. One tool file per capability under apps/mcp/src/tools/, each calling the same invoke(..., {surface:"mcp"}). Context comes from an Authorization: Bearer API key — the key carries the org + workspace scope, so no org/workspace path segment is needed.

In-app agent — Live

The chat stream route asks materializeTools() for every capability whose surfaces include "agent", hands them to the model as tools, and routes each tool-call back through invoke(). Token-by-token output is streamed to the browser as typed SSE events.

Is parity enforced, or just convention?

Mostly convention, backed by one hard check and one soft check. Worth being clear-eyed about:

Known parity gaps — fix these
  • Missing register import on API & MCP. Only the in-app agent imports @oxagen/handlers/register + @oxagen/agent/register. Without it, invoke() throws no_handler at runtime. This is a latent boot bug on two of the three surfaces.
  • Two server actions in apps/app call handlers directly (user-preferences write, video generate), skipping the IAM check, billing gate, and audit stamp that invoke() provides.
  • MCP tool schemas are hand-duplicated rather than imported from the contract — they can silently drift from the source schema.
  • Tools from user-registered MCP servers skip IAM. They are metered but not policy-checked even when enforcement is on.
  • agent.code.execute is hidden from the model unless SANDBOX_ENABLED=true.

Access control — who is allowed to do what

ACL / IAM — packages/iam, packages/oxagen/src/iam

Analogy — a bouncer with a rulebook

Every time someone tries to use a capability, a bouncer checks a rulebook. The rulebook is read top to bottom, most-specific and most-restrictive first. If nothing in the book says “yes,” the answer is “no.” The bouncer stands inside the same doorway as everything else — kernel.invoke() — so you can’t sneak past.

One badge for everyone: principals

Humans, AI agents, and service accounts (API keys) are all principals — the same shape, governed by the same rules. That’s why an agent can be given exactly the abilities a junior teammate has, no more. Principals live in org.principals with a kind of human, agent, or service.

Three scopes

Personalthe human
→
Orgthe customer — billing & governance
→
Workspacethe team room where agents work

Permissions follow an inherit-with-override rule: the org sets the rails, a workspace owner can tighten within them but can never loosen what the org locked. The URL shows the scope you’re in: /{org}/{workspace}/….

The four kinds of rule

Roles

Job titles. Org: Owner, Admin, Compliance, Billing. Workspace: Owner, Member, Viewer. Custom roles are supported in the schema.

Grants

A specific yes/no/ask sticker on one capability for one principal, at org or workspace scope.

Policies

Org-wide rules that can be marked enforced — these win over workspace grants, so an org can hard-block something everywhere.

Access requests

Just-in-time “please grant me X” flow, with an approval step. The plumbing exists; the editor UI is still stubbed.

How the bouncer decides — 8 rules, in order

The resolver in resolve.ts checks these top to bottom and stops at the first match. Notice the most restrictive wins, and the very last fallback is the capability’s own defaultEffect — which is deny for everything. Default answer: no.

1  Workspace explicit DENY        ← a flat no here ends it
2  Org enforced DENY
3  Workspace explicit ALLOW
4  Org enforced ALLOW
5  Workspace REQUIRE-APPROVAL     ← pause for a human
6  Org default grant (allow → require-approval → deny)
7  Role-inherited grant           ← "because you're an Admin"
8  Contract defaultEffect         ← almost always DENY

Is it actually on?

Wired Both the API and MCP run bootstrapIAMRuntime() at startup, which injects the check into the kernel. IAM_ENFORCEMENT_ENABLED defaults to on — a denied call throws; with the flag off it would only log. So unlike RLS (next section), the permission layer is live, not dormant.

Important nuance — the full rulebook is an Enterprise feature today

The fine-grained grant/role/policy resolver fully engages for Enterprise-tier orgs (canAccessACL). Lower tiers fall back to simple role membership plus each capability’s defaultEffect. So smaller orgs get coarse role checks; the matrix-style ACL is the paid, advanced control.

Known ACL gaps
  • Condition language not built. The conditions column exists, but anything non-empty currently fails closed — time-windows and IP-ranges aren’t evaluated yet.
  • Old orgs aren’t seeded. Orgs created before bootstrapOrgIAM() have no IAM rows; with enforcement on they fall to deny on everything. New orgs are seeded correctly.
  • New members get no role by default (least-privilege) — role assignment is a separate explicit step, and the assignment UI is still a stub.
  • Permission-change events aren’t logged (see SOC 2 below) — a real audit hole for CC6.

Row-level security — keeping tenants apart

RLS — packages/tenancy, packages/database

Analogy — tinted glass on every drawer

The bouncer (ACL) decides whether you may open a drawer. Row-level security is tinted glass on the drawer itself: even with it open, you only see your own company’s papers. The other tenants’ rows are physically hidden by the database — so even if app code forgets a “WHERE my-company” filter, the leak can’t happen.

The three seams

There are exactly three sanctioned ways to touch tenant data. Using the raw database handle is banned by ESLint so nobody opens a drawer without the glass.

withTenantDb() — the normal way

Stamps each transaction with your org_id + workspace_id (Postgres SET LOCAL session variables) so the glass knows who you are. Fails closed if you have no scope.

withSystemDb() — the master key

An audited bypass for jobs that run before we know who you are: login, API-key lookup, Stripe webhooks, writing the audit log, org bootstrap. Every use carries a // tenancy: system bypass comment.

scopedSession() — the graph version

The same idea for Neo4j. The raw session() is banned; callers must scope. Spec’d; landing in the ontology package is still in progress.

oxagen_app — a deliberately weak login

The database role the app connects as is not a superuser — superusers see through tinted glass. A startup guard refuses to boot if it detects a superuser while enforcement is on. Provisioned by infra, not by a migration.

The policies

FORCE ROW LEVEL SECURITY is declared on ~55 tenant-owned tables. A policy manifest lists every table and its isolation class, and a CI test asserts that any table with an org_id column appears in that manifest — so a new tenant table can’t silently escape the glass. Global identity tables (auth.users, auth.sessions) have no org_id and are intentionally excluded; they’re protected by the login resolvers instead.

The big honest caveat — the glass is installed but transparent

Flag off TENANT_RLS_ENFORCEMENT_ENABLED defaults to false in every environment today. When off, withTenantDb still stamps the org/workspace ids but also sets rls_bypass = on, so the policies exist and are correct but do not yet filter rows. Until the flag is flipped, tenant isolation rests entirely on the hand-written org_id filters in queries plus the scope seams. The flip is gated on telemetry (the db.query.unscoped counter) reading zero, and is tracked as OXA-1515.

Defense in depth — three layers, not one

ACL and RLS aren’t alternatives; they stack. Each layer assumes the one above it might fail.

1IAM / bouncerapp layer — may this principal call this capability? On
2Tenant scope seammiddleware layer — is there a valid org+workspace badge before any DB call? Fails closed. On
3RLS glassdatabase layer — the DB itself hides other tenants’ rows, even on a buggy query. Built, off

Today layers 1 and 2 are doing the real isolation work. Layer 3 is the belt-and-suspenders that becomes a hard wall the moment the flag flips.

SOC 2 & security posture

What auditors care about — and where we honestly stand.

Analogy — a report card you have to earn

SOC 2 isn’t a feature you install; it’s a report card that says “this company actually does the safe things it claims, and here’s a year of proof.” That means two things: the controls have to exist (mostly built) and there has to be evidence they ran over time (we have almost none yet, because there are no live customers). Both halves matter.

The audit trail — a tape you can’t rewind

There are two complementary audit surfaces, both append-only:

Postgres security.security_events Live

The primary SOC 2 trail. The schema forbids edit/delete columns outright. Every capability call (allowed / denied / error) plus sign-in and sign-out are recorded. Written via the master key so the log succeeds even before a tenant scope exists.

ClickHouse audit_events Live

A second, tamper-evident copy: each event carries a SHA-256 hash chain linking it to the previous one, kept for 7 years. Inputs are hashed, never stored raw, so no PII lands in the tape.

Secrets & encryption — packages/crypto

Sensitive secrets (OAuth tokens, integration credentials) are sealed with AES-256-GCM envelope encryption — a fresh data key per value, wrapped by a master key, with a version byte so keys can rotate without re-encrypting old rows. Production refuses to boot without the master key set.

Today the master key is a “local KEK” held in an encrypted environment variable, not a cloud HSM/KMS. The adapter interface is built so swapping to a real cloud KMS needs no application change — but that swap is required before SOC 2 GA.

SOC 2 gap register — the honest list
  • RLS enforcement is off (OXA-1515) — the confidentiality control exists in SQL but isn’t the hard wall yet.
  • Permission-change events never fire. org.member_invited / removed / role_changed are typed but no handler emits them — breaks CC6.2/CC6.3 evidence for privileged mutations.
  • Failed sign-ins aren’t recorded. auth.sign_in_failed is declared but never emitted — brute-force attempts are invisible to the trail (and there’s no rate limiting to stop them).
  • Plaintext OAuth tokens persist beside the encrypted copies — Better Auth’s adapter rewrites the plaintext columns on each callback. Low-scope login tokens, but still plaintext-at-rest.
  • The Postgres audit table has no partitioning or retention policy — a cost/perf problem once traffic starts (the ClickHouse tables do have TTLs).
  • No audit-viewing UI and no SIEM export — the tapes exist but there’s no read path (deferred to Wave 6).
  • Blob storage is public-URL only — fine for avatars today, must be hardened before user documents land.
  • Admin app is a stub — SOC 2 usually expects an admin surface for access reviews and incident investigation.
  • No operating evidence yet — pre-launch, so the time-based proof an auditor needs hasn’t accumulated.

Information architecture of the app

apps/app — the interactive agent UI.

The whole app is auth-gated. proxy.ts (Next 16’s renamed middleware, running at the edge) bounces any request without a session cookie to /login, and also rewrites a few legacy v1 URLs to their v2 homes. Everything else lives under one of three scopes, visible right in the URL.

Three scopes, one URL shape

/(auth)/{login,signup,verify}        public — no session
/(onboarding)/new-organization       signed in, no org yet
/account/…                           personal scope (via avatar menu)
/{orgSlug}/…                         org scope     (governance)
/{orgSlug}/{workspaceSlug}/…         workspace scope (daily work)
Analogy — building, floor, room

The org is the company that rents the building (billing, governance). A workspace is a room on a floor where a team and its agents actually work. Your account is your personal locker, reached from the avatar menu — never from the sidebar. The two dropdowns at the top let you walk between buildings and rooms.

The shell & sidebar

A floating, collapsible left sidebar (no glass, neutral styling) plus a content panel whose header carries the org switcher / workspace switcher, the universal Ask bar, and a notifications bell. The sidebar swaps between three modes automatically based on the URL: workspace, org, and account.

├─ Automation                       ├─ Security   (audit + stubs)
├─ Activity                         ├─ Billing

└─ Settings                         └─ Settings

The Ask bar & the conversation surface

The Ask bar is the universal input. It classifies intent: a navigation phrase pushes a route, a “fill this form” phrase triggers generative form-fill over the current page, and a question opens the chat drawer. /ask and /chat render the same shared conversation component; ?c=<id> selects a thread, its absence starts a blank one.

Under the hood, one endpoint — POST /api/v1/chat/stream — is the single LLM caller per turn. It streams typed SSE events (text, tool-call-*, approval-required, plan-proposed, component, usage…) which the hand-rolled use-tool-stream.ts hook turns into live UI. Generative UI works without React Server Components: a tool result names a component id, and a client-side registry maps it to a lazy-loaded React component (image preview, install steps, video form, etc.). The model streams data, never server-rendered React.

The one-paragraph takeaway

The platform’s spine is solid and real: one capability registry, one governed doorway (invoke()), three thin surfaces onto it, an active permission layer, an installed (if not yet switched-on) tenant-isolation wall, and a working tamper-evident audit tape. The work that remains is mostly turning built things on (RLS), closing audit holes (member events, failed logins), and filling in leaf UI — not re-architecting. Knowing exactly which is which is the point of this document.
