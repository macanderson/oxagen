### 1. 🔴 `apps/api/src/routes/v1/webhook.ts:98`

- **Severity:** CRITICAL  
- **Category:** `silent-default`  
- **Scan target:** `api`  
- **Verifier confidence:** high

**What's wrong:** The optional-chain on `verifyWebhook` falls back to `true` when the method is absent. Any connector that does not implement `verifyWebhook` implicitly accepts all incoming payloads as verified, regardless of signature.

**Impact:** A connector registered without a `verifyWebhook` implementation (any new or incomplete connector) silently accepts all webhook deliveries without any HMAC check. This is a security gate that defaults open instead of closed — an attacker who knows the connectionId can inject arbitrary entity payloads into the ingestion pipeline.

```ts
const verified = connector.verifyWebhook?.(payload, headers, webhookSecret ?? null) ?? true;
```

<details><summary>Adversarial verification reasoning</summary>

The vulnerability is confirmed. The `?? true` fallback at `/home/macanderson/Workspaces/oxagen-platform/apps/api/src/routes/v1/webhook.ts:98` is a real security gate that defaults open.

The interface at `/home/macanderson/Workspaces/oxagen-platform/packages/ingestion/src/connectors/types.ts:128` declares `verifyWebhook?` as optional. Three first-party webhook-delivery connectors — `google-drive` (packages/ingestion/src/connectors/google/drive.ts), `google-calendar` (packages/ingestion/src/connectors/google/calendar.ts), and `google-gmail` (packages/ingestion/src/connectors/google/gmail.ts) — all set `deliveryMethod: "webhook"` but implement no `verifyWebhook` method. When the route evaluates `connector.verifyWebhook?.(...)`, the optional-chain short-circuits to `undefined`, and `?? true` makes `verified = true`. The signature check is skipped entirely.

The comment on lines 20-21 of webhook.ts explicitly names HMAC validation as "the security boundary." That boundary is non-functional for all three Google connectors. An attacker who knows (or guesses) any `connectionId` UUID — a public identifier, not a secret — can POST arbitrary JSON to `/webhooks/google-drive/<connectionId>` and have it injected into the Inngest ingestion pipeline as a verified entity delivery, potentially poisoning org knowledge-graph data with attacker-controlled content.

The five connectors that do implement `verifyWebhook` (github, slack, linear, zoom, custom-webhook, microsoft) are unaffected. The poll-only connectors (salesforce, google-bigquery, google-meet, google-tasks, google-contacts, custom-sql) never receive webhook POSTs so the fallback is moot for them.

The correct fix is to invert the default: `?? false` instead of `?? true`, and either require all webhook-delivery connectors to implement `verifyWebhook` (enforced at registration time or by making the method non-optional when `deliveryMethod === "webhook"`), or add stub implementations that return `false` when no secret is configured (matching the existing behavior of `custom-webhook` when a secret IS configured). The three Google connectors use Google's push notification channel system which does not provide HMAC signatures — the correct behavior for them is to check the `X-Goog-Channel-Token` header against the stored channel secret, not to accept all deliveries unconditionally.

</details>

<details><summary>Adversarial verification reasoning</summary>

**What's wrong:** The Pass A (exact naturalKey) deduplication query references `$orgId` in the Cypher pattern but the parameter object on line 53 only provides `naturalKey`. Neo4j treats an unbound parameter as `null`, so the match predicate becomes `{naturalKey: ..., orgId: null}` which never matches any node because no EntityNode has `orgId: null`. **Impact:** Every re-ingested entity (polling overlap, webhook retry, duplicate delivery) bypasses the exact-match fast path and runs a full embedding similarity search. This wastes embedding API calls on every event, and because Pass B uses fuzzy scoring, entities that should be de-duplicated by exact key may instead receive spurious ALIAS_OF edges or be stored as duplicate principal nodes. Graph queries that follow ALIAS_OF will surface split entity records instead of the unified view users expect. This is a correctness defect affecting every connector.


<details><summary>Adversarial verification reasoning</summary>
